#### 1. 计算平面与 Python 彻底解耦
在 DeepInfer 中，Python 代码不参与底层的张量数学计算，仅充当宿主侧的设备代理（Device Proxy）。在 [`models/deepseek.py`](https://github.com/deepseek-ai/DeepInfer/blob/main/deepinfer/model_executor/models/deepseek.py) 与 [`v4_modules/mlp.py`](https://github.com/deepseek-ai/DeepInfer/blob/main/deepinfer/model_executor/models/v4_modules/mlp.py) 内部，所有密集的矩阵乘法与注意力计算，均直接交由底层高性能算子执行：

```python
# deepinfer/model_executor/models/v4_modules/mlp.py
# 稠密与专家矩阵乘直接交由 DeepGEMM 底层 SASS 汇编算子执行
deep_gemm.m_grouped_fp8_fp4_gemm_nt_contiguous(
    hidden_states, self.weight, out, scales, recipe=(1, 1, get_fp8_casting_granularity())
)
```

- **MoE 专家计算与稠密矩阵乘**：调用 [DeepGEMM](https://github.com/deepseek-ai/DeepGEMM)（经 SASS 汇编级极致调优的 FP8/FP4 GEMM 库）；
- **MLA 注意力计算**：调用 [FlashMLA](https://github.com/deepseek-ai/FlashMLA)（专为多头潜在注意力打造的 CUDA/C++ 高性能算子）；
- **跨卡跨机通信**：调用 [DeepEP](https://github.com/deepseek-ai/DeepEP)（经 NVLink 与 RDMA 的低延迟通信算子）；
- **融合采样与调度辅助核函数**：由 TileLang 编写并在运行时 JIT 编译为底层硬件机器码。

#### 2. Scheduler 下沉 C++：消除 CPU 调度瓶颈
调度和显存管理属于典型的 CPU 密集型与离散结构操作。在自回归解码单步只需数毫秒的场景下，如果在 Python 里遍历几百个序列对象、频繁操作字典或触发垃圾回收（GC），很容易产生数百微秒甚至毫秒级的延迟抖动，导致 GPU 处于算力饥饿状态。
因此，DeepInfer 将 [Scheduler](https://github.com/deepseek-ai/DeepInfer/blob/main/csrc/engine/scheduler.hpp) 与 [BlockManager](https://github.com/deepseek-ai/DeepInfer/blob/main/csrc/engine/block_manager.hpp) 移至 C++20，并引入 `ObjectPoolPyObject` 预分配内存池，将整轮调度决策确定在数十微秒以内。

#### 3. ModelRunner 保留 Python：CUDA Graph 消除解释器开销
在自回归解码阶段，Python 逐层下发算子的解释器开销可以通过 [CudaGraphRunner](https://github.com/deepseek-ai/DeepInfer/blob/main/deepinfer/worker/cuda_graph_runner.py) 彻底抹平。在预热阶段捕获完整的静态计算图后，解码过程中的模型前向不再逐层解释执行：

```python
# deepinfer/worker/model_runner.py: execute_main_model()
with cpu_timer.record("launch_forward"), forbid_cuda_sync():
    if run_cuda_graph:
        # 解码阶段：直接触发底层静态图，CPU 单步开销 < 2 微秒
        model_output = self.cuda_graph_runner.replay(cuda_graph_used)
    else:
        # 仅在非 Graph 的预填阶段走常规逐层调用
        model_output = self.model(kv_caches=kv_caches, input_metadata=input_metadata)
```

底层只对应单次 `cudaGraphLaunch` 调用（CPU 耗时低于 2 微秒）。这种划分既保留了对 Hugging Face Safetensors 权重与 PyTorch 生态的原生兼容，又极大降低了对 YOCO 跨层投影、Engram 等前沿网络结构进行快速迭代的开发成本。

#### 4. 零拷贝张量原地组装
为了避免 C++ 调度器向 Python 传递元数据时产生序列化损耗，ModelRunner 会提前预分配静态张量内存。C++ 原生函数 [`prepare_tensor_input_v4.cpp`](https://github.com/deepseek-ai/DeepInfer/blob/main/csrc/engine/input_metadata/prepare_tensor_input_v4.cpp) 直接向这批底层缓冲区原地写入变长请求的偏移量、块表映射与注意力元数据，在执行热路径上做到了零内存分配与零数据搬运：

## 2. 引擎执行主循环与状态机解耦

从请求进入到结果交付，单步执行经历清晰的时序分发：

在 [entrypoints/llm.py](https://github.com/deepseek-ai/DeepInfer/blob/main/deepinfer/entrypoints/llm.py) 中，`LLM.generate()` 逐个将请求推入引擎。若调用方未预先提供 Token IDs，分词在入队前由 `tokenizer.encode()` 一次性完成；输出侧由 `_run_engine()` 收集 `RequestOutput` 后按需执行 `tokenizer.decode()`。分词完全独立于核心步进循环之外。

调度主循环位于 [engine/llm_engine.py](https://github.com/deepseek-ai/DeepInfer/blob/main/deepinfer/engine/llm_engine.py) 的 `step()`：
1. 引擎调用原生 `self.scheduler.schedule(self.sequence_metadata_pool)` 获得本步候选序列及调度决策；
2. 若调度器返回克隆或清零状态的指令，通过 Worker 触发底层显存重置，并利用 `DeferredRelease` 延迟解引用；
3. 执行 `post_schedule()` 推进结构化输出与多模态数据准备；
4. 调用 `_execute_model_async_step()` 驱动 Worker 步进；
5. 处理返回的采样 Token 并更新序列终结状态。

### 三类核心状态的生命周期隔离

阅读执行流时，不能将运行时上下文笼统地理解为单一的“批次状态”。源码严格划分了三种生命周期各异的核心结构：

<StateDiagram title="三类异构状态在 step 循环中的流转契约" states={[
{ label: 'SchedulerOutputs', detail: 'C++ 调度器生成的决策快照，记录本步选中的序列集、Token 预算及显存操作指令', next: '下发给 Worker', tone: 'amber' },
{ label: 'seq_metadata_list', detail: 'Worker 消费的序列上下文视图，ModelRunner 据此直接装配硬件输入张量', next: '启动设备计算', tone: 'teal' },
{ label: 'WorkerStepState', detail: '封装硬件执行产物、采样结果与 CUDA 事件；在 ZOS 解码下延迟到下一步处理', next: '跨步重叠消费', tone: 'rose' },
]}/>

- **`seq_metadata_list`**：本轮实际分发给 Worker 的序列上下文，ModelRunner 据此准备张量输入；
- **`SchedulerOutputs`**：C++ 调度器生成的单步决策快照，记录被选中的序列集合、Token 预算统计以及显存操作指令；
- **`WorkerStepState`**：Worker 保留的单步执行结果包，封装了序列元数据、调度输出、采样结果、CUDA Event 及静态图尺寸。

在常规执行中，这三者同生共灭；但在下文分析的异步调度模式下，`WorkerStepState` 会跨步存活，形成跨越步进边界的状态流水线。

### C++ 调度器内部机制：GIL 释放、分布式步型对齐与 LCFS 抢占

深入看 [csrc/engine/scheduler.hpp](https://github.com/deepseek-ai/DeepInfer/blob/main/csrc/engine/scheduler.hpp) 的 `_schedule()` 实现，可以看到调度器在微秒级决策上面对的真实系统约束：

#### 1. 入口释放 GIL，解绑 Python 解释器
在 `_schedule()` 入口的第一行，代码立即执行：
```cpp
// csrc/engine/scheduler.hpp: 释放 GIL，使微秒级调度决策脱离 Python 全局解释器锁
py::gil_scoped_release release;
BlockManagerMutexAcquire acquire{block_manager, state_manager};
```
这使得调度器在 C++ 内部执行微秒级决策（遍历数百个序列、做显存分配）时，完全不需要占用 GIL，外部的 Python 线程（如 HTTP 请求接收、异步 IO 与文法编译）可以真正并行运行。

#### 2. 三种引擎部署模式的物理隔离
调度器在启动时通过 `EngineType` 严格划分职责：
- **`NORMAL`**：标准混部模式，依据分布式投票统一步型；
- **`PROMPT`**：纯预填节点，仅消费 waiting 队列；
- **`COMPLETION`**：纯解码节点。构造函数强制断言 `stop_preempted_request=true`——由于纯解码节点没有 Prefill 算力通道，一旦发生显存溢出抢占，无法在本地重算，必须直接终止报错。

#### 3. 分布式数据并行（DP）步型对齐与双轮 AllReduce 投票
在多卡数据并行（DP）环境下，同一进程组内的所有卡在单步必须保持步型一致（要么全做 Prompt，要么全做 Decode），否则不同的算子与通信流会直接挂死集合通信：
- **ALL 检查点 vs ANY 检查点**：系统在 `prefill_attempt_interval` 步（ALL 点：全员均有 Prefill 需求才触发，杜绝单个卡干活、其余卡空转陪跑）与 `prefill_any_attempt_interval` 步（ANY 点：任一卡有活即触发，作为孤立卡请求的防饥饿兜底）之间动态决策；
- **双轮 AllReduce 投票防死锁**：首轮检查显存利用率（`get_gpu_cache_usage() <= 0.9` 水位线）与 waiting 状态；第二轮在各卡执行完 `_schedule_prefill` 后再次投票确认。若因显存紧绷导致全组最终“空手”，全组立刻降级回转 Decode，坚决避免在空 prompt 步上陷入死循环；若组内确有卡调度出 prompt，无活的卡则发射占位步（Placeholder Step）保持物理对齐。

#### 4. 显存紧绷下的 LCFS 抢占与重算复位
在 Decode 调度过程中，当 `block_manager` 显存不足时，调度器会按已输出长度对运行中序列进行排序，优先挑选当前显存开销最大（`output_len` 最长）的序列作为牺牲者执行 `_preempt()`。被抢占的序列调用 `seq->reset_for_recompute()` 复位状态并归还全部物理块，随后重新插回 `waiting` 队列头部（`waiting.push_front(seq)`），待显存压力缓解后优先重算恢复。

## 3. Zero-Overhead Scheduling 异步重叠机制

在传统的自回归解码中，单步执行包含 `Schedule → Forward → Sample → Post-process` 四个阶段。因为后处理依赖采样结果，CPU 与 GPU 之间往往存在强同步等待，导致 GPU 在 CPU 执行调度与后处理期间处于空闲等待状态。

[worker/worker.py](https://github.com/deepseek-ai/DeepInfer/blob/main/deepinfer/worker/worker.py) 的 `execute_model_step()` 实现了零开销异步调度（Zero-Overhead Scheduling, ZOS）：

### 跨步状态修正与源码流水线

ZOS 的核心设计并非单纯的异步发射，而是**将解码后处理延迟到下一步模型前向的执行阴影中**：

```python
# deepinfer/worker/worker.py: execute_model_step() 异步流水线核心
# 1. 发射当前 step 前向 (GPU 硬件计算开始)
main_model_output = self.model_runner.execute_main_model(
    seq_metadata_list, self.gpu_cache, metadata_zos=metadata_zos, total_q=total_q
)

# 2. 处理上一 step 保存的输出 (CPU 在前向计算的等待窗口内重叠执行)
if self.is_driver_worker and not is_placeholder and prev_step_state is not None:
    post_process_outputs = self.callbacks.post_process_fn(prev_step_state)

# 3. 发射当前 step 采样
sampler_output = self.model_runner.execute_sample(
    seq_metadata_list, input_metadata, model_output, self.gpu_cache
)

# 4. ZOS 解码将当前状态延迟保留到下一步；Prompt 步骤则就地同步完成
if is_prompt or not envs.DEEPINFER_ZERO_OVERHEAD_SCHEDULING:
    return self.callbacks.post_process_fn(curr_step_state)
self.prev_step_state = curr_step_state
```

### 显存内就地序列长度修正（_correct_seqlens_qk）

这种机制改变了状态可消费的确定性时机：由于在发射第 $N+1$ 步时，第 $N$ 步的采样结果仍在设备端流转，CPU 侧记录的序列长度（`seqlens_q/k`）存在滞后。

若在 CPU 端强行等待第 $N$ 步的采样子结果回传，ZOS 的重叠优势将荡然无存。DeepInfer 在 [worker/worker.py](https://github.com/deepseek-ai/DeepInfer/blob/main/deepinfer/worker/worker.py) 的 `_correct_seqlens_qk()` 中给出了直接的工程实现：

```python
# deepinfer/worker/worker.py: 显存内就地修正序列长度元数据
remap_cpu, seqlens_q_cpu, seqlens_k_cpu, has_overlap = prepare_zos_inputs(
    seq_metadata_list, prev.seq_metadata_list, n_seq_with_padding, self.nextn
)
if has_overlap:
    remap = remap_cpu.cuda(non_blocking=True)
    seqlens_q = seqlens_q_cpu.cuda(non_blocking=True)
    seqlens_k = seqlens_k_cpu.cuda(non_blocking=True)

    # 在 GPU 显存内直接调用专用核函数根据上步采样的真实接受数量修正，完全不阻塞发射
    if self.nextn > 0:
        compute_seqlens_k_zos(
            seqlens_k[:n_seq], seqlens_q[:n_seq], remap[:n_seq],
            prev.sampler_output.num_accepted_tokens_gpu, nextn=self.nextn,
        )
```

系统没有选择在 CPU 端做阻塞等待，而是将两批序列的映射关系异步推入 GPU，直接在显存内通过专用核函数依据上一轮采样的实际接受数量计算真实的 `seqlens_k`。随后仅利用 `d2h_evt = torch.cuda.Event()` 进行非阻塞跟踪，彻底消除了 Host-Device 数据依赖导致的流水线断流。

## 4. CacheEngine：从模型元数据到物理显存字节

[worker/cache_engine.py](https://github.com/deepseek-ai/DeepInfer/blob/main/deepinfer/worker/cache_engine.py) 为 DeepSeek-V4.1 特有的混合注意力体系构建了显存布局管理器 `GPUCacheInterface` 与 `KVCacheManager`。

该缓存体系依据每层的配置差异，将单一显存切分为多种异构视图：
- **`ica_cache` / `ica_state`**：索引注意力（Index Attention）的 Key 缓存与状态；
- **`ca_cache` / `ca_state`**：压缩注意力（Compressed Attention）的 Key-Value 缓存与边界累加状态；
- **`swa_cache`**：滑动窗口注意力（Sliding Window Attention）缓存。

### 显存物理块的侵入式双向链表管理

在 C++ 调度器底层，显存块与状态缓冲管理由 [csrc/engine/block_manager.hpp](https://github.com/deepseek-ai/DeepInfer/blob/main/csrc/engine/block_manager.hpp) 接管。

面对每秒数万 Token 的高频分配与回收，标准的 STL 容器（如 `std::list`）存在明显的性能短板：每次插入节点都会触发堆内存申请（`malloc`），在微秒级的调度热路径上容易引发分配器锁竞争与内存碎片；且散落在堆中的节点会导致严重的 CPU 缓存失效。DeepInfer 借鉴了操作系统内核管理物理页帧的做法，设计了一套**基于预分配连续数组的整数索引侵入式双向链表**：

```cpp
// csrc/engine/block_manager.hpp
struct Blocks {
    struct block {
        int ref_count{0}; // 引用计数，支持前缀缓存与推测解码多分支共享
        int next{0};      // 侵入式链表：指向后继空闲块的数组下标
        int prev{0};      // 侵入式链表：指向前驱空闲块的数组下标
    };

    std::vector<block> _blocks; // 一次性预分配全量连续元数据数组
    int _head, _tail, _size;

    // 0 代表 NULL 哨兵：源码约定 gpu blocks 0 不参与业务分配
    Blocks(int _n) : _blocks(_n), _head(1), _tail(_n - 1), _size(_n - 1) {
        for (int i = 1; i < _n; ++i) {
            _blocks[i].prev = i - 1;
            _blocks[i].next = i + 1;
        }
        _blocks[_n - 1].next = 0;
    }

    int allocate() {
        int block_id = _pop_front();
        _blocks[block_id].ref_count += 1;
        return block_id;
    }

    void free(int block_id) {
        auto &block = _blocks[block_id];
        block.ref_count -= 1;
        if (block.ref_count == 0) {
            _push_back(block_id); // 引用计数归零时 O(1) 挂回空闲链表尾部
        }
    }
};
```

这一结构为高并发调度带来了四项直接的工程收益：
1. **热路径零堆内存分配（Zero Runtime Malloc）**：初始化时根据显存总量一次性预分配 `_blocks`，运行期所有的分配与回收纯为数组索引赋值，完全规避了系统级内存分配器的调用开销；
2. **极小内存占用与 CPU 缓存常驻**：单个 `block` 仅占 12 字节（对齐后 16 字节）。即便管理 20,000 个物理显存块（对应数十至上百 GB 显存），全部元数据总共只有约 320 KB，能够**长期完整常驻在单个 CPU 核心的 L2 缓存（通常 1~2 MB）中**，极大降低了访问延迟；
3. **免哈希的确定性 $O(1)$ 定位**：`block_id` 直接充当 `_blocks` 数组下标，无需通过 `std::unordered_map` 进行哈希反查，在已知 ID 时能在原子时间内完成双向链表的摘除（`_erase`）与放回（`_push_back`）；
4. **原生支持前缀共享与引用计数**：`pin_block` 与 `free` 负责维护引用计数，多请求并发共享前缀时只做计数增减，直到计数归零才以 $O(1)$ 速度归还至空闲链表。

在工程评估中，绝对不能以“层数 × Token 数 × 标称字节”粗暴估算显存占用。源码中的多组底层计算函数展示了极为细致的物理约束：

- `_kv_bytes_per_token()`：计算单 Token 交织 KV 数据及缩放因子的实际字节数，检查维度对齐；
- `_get_qk_topk_bytes()`：计算索引器 FP4 格式的打包字节与 UE8M0 格式的尺度因数开销；
- `_state_bytes()`：按照 `[num_state_token, 2, head_dim]` 计算全精度浮点状态缓冲尺寸；
- **硬件对齐约束**：代码严格规定，DeepGEMM 索引块跨度必须满足 128 字节物理对齐，多处中间偏移量需满足 32 字节对齐。未对齐部分必须计入填充 Padding；
- **层间共享复用**：通过 `layer_kv_map` 或 `layer_index_module_map` 标记为共享的层，直接复用前序层的物理偏移量，不分配重复空间；纯 SWA 层对应的普通 KV 长度直接置 0。

### SWA 缓存为何大于标称窗口

源码明确定义了两个尺寸函数：
1. `get_inference_swa_block_size(window_size)`：在基础窗口之上，强行叠加 `DEEPINFER_MAX_BACKTRACKING_TOKENS`（最大推测回退历史）；
2. `get_kvstore_swa_block_size(window_size)`：在推理尺寸基础上，进一步增加预填落盘与 YOCO 截断的锚点余量。

系统将存储粒度 `KVSTORE_GRAIN` 硬编码为 128 Tokens，规定持久化写入仅在 128 的整数倍边界处触发。当 Prefill 结束位置未对齐该边界时，必须在显存中保留足量缓冲区以维持上下文完整性。若盲目按照裸窗口分配显存，模型在遭遇推测回退或截断边界时将直接引发越界越权异常。

## 5. SWA Bounded Replay 的截断与重放语义

在 DeepSeek-V4.1 的 YOCO 架构下，Decoder 各层无需对完整前缀进行全局注意力交互，其全局语义通过 Encoder 顶层的隐状态跨层投影获得。因此在解码端，注意力计算退化为局部的滑动窗口（SWA）。

<SwaBoundedReplayExplorer />

**SWA Bounded Replay 绝不等于“粗暴丢弃窗口外的缓存”。**

### 为什么重放开销是常数阶 O(1)

在传统自回归模型的长文本前缀缓存方案中，一旦发生缓存跨节点未命中，必须重新计算完整前缀 $[0, L_1]$，计算复杂度高达 $O(L_1^2)$ 或 $O(L_1)$，在 64K 或 128K 超长上下文下会导致调度完全阻塞。

但在 DeepSeek-V4.1 的 YOCO 体系下，Decoder 阶段放弃了全局自注意力，全量长距离语义由顶层 Encoder 隐状态投影承载。Decoder 各层仅维护一个局部滑动窗口（$W = 128$ Tokens）。

结合 3FS 分布式存储硬编码的 `KVSTORE_GRAIN = 128` 粒度，当某台节点的 SWA 局部状态丢失时：
- 重放起点直接对齐至 $\lfloor L_1 / 128 \rfloor \times 128 - W$；
- 需要重放的区间被严格限制为：
  $$\text{Replay Tokens} = \min(W, L_1) \le 128\text{ Tokens}$$
- **重放代价从依赖上下文总长度的 $O(L)$ 变成了严格的常数阶 $O(1)$**。无论用户输入的上下文是 8K 还是 128K，单次局部重放的计算量上限始终固定且极低。

若要安全恢复解码状态，必须维系三条严格的边界契约：
1. **重放起点对齐**：重放计算截断在最近的 128 Tokens 边界处，将查询向量限定在局部区间，确保恢复代价为常数级；
2. **状态环形缓冲（State Ring）一致性**：YOCO 消费层 SWA 被分为保留区与丢弃区。丢弃区的重建依赖前向重算，而保留区必须完整覆盖 SWA 窗口加上推测解码的最大回溯跨度；
3. **压缩边界无依赖性**：压缩窗口边界与 128 Tokens 粒度自然对齐，避免跨边界引入历史递归依赖。

如果在系统层仅根据前缀命中率估算收益，却忽略了当 SWA 局部缓存缺失时触发的重放开销，实际的端到端吞吐收益可能大打折扣。

## 6. DSpark 变长推测解码与状态推进

DeepInfer 集成了 DSpark 变长推测解码（Speculative Decoding）优化。ModelRunner 针对草稿预测头配置了专用的 `DFlashCudaGraphRunner`。

### 预留槽位管理与动态验证预算

在调度底层，MTP（Multi-Token Prediction）推测解码的槽位管理通过 `allocate_mtp_info_slot` 与 `free_mtp_info_slots` 实现：
- 序列在从 `WAITING` 状态准入（`admit`）至 `RUNNING` 状态瞬间，直接绑定一个预留的 `info_slot`；
- 该槽位在 GPU 显存内映射至静态预分配张量，消除推测头动态写出的内存分配损耗。

在验证预算上，传统的推测解码通常采用固定步长（如每步固定验证 5 个候选 Token），在模型预测置信度较低时容易浪费算力。DSpark 在模型前向中引入 Confidence Head 预测候选 Token 的接受概率，并在调度阶段利用 GPU 上的 TileLang 核函数计算前缀积与 Top-K 排序，动态选取高置信度的 Token 组合投入验证（平均验证长度自适应伸缩在 3.2 至 4.4 之间），在线上实现了 4% 至 11% 的吞吐收益。

### 状态推进与回退链条

在执行循环中，Engine 的 `_process_model_outputs()` 将实际接受的 Token 列表、草稿预测 Token 与置信度传递给原生 `process_MTPInfo()`，再调用 `Scheduler.process_outputs()` 推进序列状态。

当部分草稿 Token 被验证器拒绝时，系统会触发序列回退：
- 序列有效长度截断至最后被接受的 Token 位置；
- KV Cache 与 State Buffer 依赖先前预留的 `max_backtracking_tokens` 缓冲安全恢复；
- 紧随其后的结构化输出文法状态机也必须同步执行 `rollback()`，防止非法语法分支残留，确保状态完全自洽。

## 7. 结构化输出：异步文法编译与回滚一致性

在企业级 serving 场景下，强制模型遵循 JSON Schema、Regex 或 EBNF 是高频刚需。DeepInfer 的结构化输出机制由 [structure_output/so_matcher_builder.py](https://github.com/deepseek-ai/DeepInfer/blob/main/deepinfer/structure_output/so_matcher_builder.py) 与 [matcher.py](https://github.com/deepseek-ai/DeepInfer/blob/main/deepinfer/structure_output/matcher.py) 承载。

### 编译解耦与异步轮询

将 JSON Schema 或正则表达式编译为有限状态自动机（DFA）属于耗时较长的 CPU 计算：
1. 引擎在独立的后台线程池中调用 `XGrammarCompiler` 编译文法，避免阻塞调度主循环；
2. 调度开始前通过 `pump()` 非阻塞检查编译状态，一旦完成便将 Matcher 绑定到对应序列并加入调度；
3. 每轮解码采样前，`matcher.fill_vocab_mask()` 依据当前 DFA 状态计算词表掩码，屏蔽不合规 Token 的 Logits。

### 为什么 Matcher 必须实现 Rollback

在推测解码与结构化输出组合使用的场景下，状态机的一致性变得极为微妙：
- 如果草稿模型连续预测了多个 Token，Matcher 在前向过程中会顺次推进状态；
- 一旦后续验证器判定中间某个 Token 未被接受，序列发生回退；
- 此时若 Matcher 未能同步调用 `rollback()`，文法状态将停留在被拒绝的非法分支上，导致下一步采样生成错误的掩码，甚至误杀合法的语法起点。

因此，源码中 Matcher 的状态回退不是防御性冗余，而是约束解码与推测解码协同工作的数学前提。

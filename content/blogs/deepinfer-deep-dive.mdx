#### 1. 计算平面与 Python 彻底解耦
在 DeepInfer 中，Python 代码从不执行底层张量数学运算，它仅充当宿主侧的设备代理（Device Proxy）。在 [`models/deepseek.py`](https://github.com/deepseek-ai/DeepInfer/blob/main/deepinfer/model_executor/models/deepseek.py) 与 [`v4_modules/mlp.py`](https://github.com/deepseek-ai/DeepInfer/blob/main/deepinfer/model_executor/models/v4_modules/mlp.py) 内部，所有密集的矩阵与向量运算全部直接委托给底层硬件原生算子：

```python
# deepinfer/model_executor/models/v4_modules/mlp.py
# 稠密与专家矩阵乘直接交由 DeepGEMM 底层 SASS 汇编算子执行
deep_gemm.m_grouped_fp8_fp4_gemm_nt_contiguous(
    hidden_states, self.weight, out, scales, recipe=(1, 1, get_fp8_casting_granularity())
)
```

- **MoE 专家计算与稠密矩阵乘**：调用 [DeepGEMM](https://github.com/deepseek-ai/DeepGEMM)（经 SASS 汇编级极致调优的 FP8/FP4 GEMM 库）；
- **MLA 注意力计算**：调用 [FlashMLA](https://github.com/deepseek-ai/FlashMLA)（专为多头潜在注意力打造的 CUDA/C++ 高性能算子）；
- **跨卡跨机通信**：调用 [DeepEP](https://github.com/deepseek-ai/DeepEP)（经 NVLink 与 RDMA 的低延迟通信算子）；
- **融合采样与调度辅助核函数**：由 TileLang 编写并在运行时 JIT 编译为底层硬件机器码。

#### 2. Scheduler 下沉 C++：消除 CPU 调度瓶颈
调度与显存分配属于纯粹的 CPU 密集型与离散数据结构管理。在自回归解码单步仅需数毫秒的极高吞吐下，若在 Python 中遍历几百个序列对象、维护字典并频繁触发垃圾回收（GC），将产生数百微秒至毫秒级的延迟抖动，直接导致 GPU 发生算力饥饿。
因此，DeepInfer 将 [Scheduler](https://github.com/deepseek-ai/DeepInfer/blob/main/csrc/engine/scheduler.hpp) 与 [BlockManager](https://github.com/deepseek-ai/DeepInfer/blob/main/csrc/engine/block_manager.hpp) 移至 C++20，并引入 `ObjectPoolPyObject` 预分配内存池，将整轮调度决策确定在数十微秒以内。

#### 3. ModelRunner 保留 Python：CUDA Graph 消除解释器开销
在自回归生成阶段，Python 解释器的逐层算子下发开销会被 [CudaGraphRunner](https://github.com/deepseek-ai/DeepInfer/blob/main/deepinfer/worker/cuda_graph_runner.py) 彻底抹平。预热阶段捕获完整前向计算图后，ModelRunner 在解码阶段根本不逐层解释 Python 执行流：

```python
# deepinfer/worker/model_runner.py: execute_main_model()
with cpu_timer.record("launch_forward"), forbid_cuda_sync():
    if run_cuda_graph:
        # 解码阶段：直接触发底层静态图，CPU 单步开销 < 2 微秒
        model_output = self.cuda_graph_runner.replay(cuda_graph_used)
    else:
        # 仅在非 Graph 的预填阶段走常规逐层调用
        model_output = self.model(kv_caches=kv_caches, input_metadata=input_metadata)
```

底层直接对应一次 `cudaGraphLaunch` API 调用（CPU 耗时小于 2 微秒）。这既获得了与 Hugging Face Safetensors 权重的原生互通，又为 DeepSeek-V4.1 特有的 YOCO 跨层投影、Engram 动态注入等前沿结构的研发演进保留了最高生产力。

## 2. 引擎执行主循环与状态机解耦

从请求进入到结果交付，单步执行经历清晰的时序分发：

在 [entrypoints/llm.py](https://github.com/deepseek-ai/DeepInfer/blob/main/deepinfer/entrypoints/llm.py) 中，`LLM.generate()` 逐个将请求推入引擎。若调用方未预先提供 Token IDs，分词在入队前由 `tokenizer.encode()` 一次性完成；输出侧由 `_run_engine()` 收集 `RequestOutput` 后按需执行 `tokenizer.decode()`。分词完全独立于核心步进循环之外。

调度主循环位于 [engine/llm_engine.py](https://github.com/deepseek-ai/DeepInfer/blob/main/deepinfer/engine/llm_engine.py) 的 `step()`：
1. 引擎调用原生 `self.scheduler.schedule(self.sequence_metadata_pool)` 获得本步候选序列及调度决策；
2. 若调度器返回克隆或清零状态的指令，通过 Worker 触发底层显存重置，并利用 `DeferredRelease` 延迟解引用；
3. 执行 `post_schedule()` 推进结构化输出与多模态数据准备；
4. 调用 `_execute_model_async_step()` 驱动 Worker 步进；
5. 处理返回的采样 Token 并更新序列终结状态。

### 三类核心状态的生命周期隔离

审查执行流时，切忌将运行时信息笼统称为“批次状态”。源码在设计上严格区分了三种生命周期完全不同的结构：

<StateDiagram title="三类异构状态在 step 循环中的流转契约" states={[
{ label: 'SchedulerOutputs', detail: 'C++ 调度器生成的决策快照，记录本步选中的序列集、Token 预算及显存操作指令', next: '下发给 Worker', tone: 'amber' },
{ label: 'seq_metadata_list', detail: 'Worker 消费的序列上下文视图，ModelRunner 据此直接装配硬件输入张量', next: '启动设备计算', tone: 'teal' },
{ label: 'WorkerStepState', detail: '封装硬件执行产物、采样结果与 CUDA 事件；在 ZOS 解码下延迟到下一步处理', next: '跨步重叠消费', tone: 'rose' },
]}/>

- **`seq_metadata_list`**：本轮实际分发给 Worker 的序列上下文，ModelRunner 据此准备张量输入；
- **`SchedulerOutputs`**：C++ 调度器生成的单步决策快照，记录被选中的序列集合、Token 预算统计以及显存操作指令；
- **`WorkerStepState`**：Worker 保留的单步执行结果包，封装了序列元数据、调度输出、采样结果、CUDA Event 及静态图尺寸。

在常规执行中，这三者同生共灭；但在下文分析的异步调度模式下，`WorkerStepState` 会跨步存活，形成跨越步进边界的状态流水线。

## 3. Zero-Overhead Scheduling 异步重叠机制

在传统的自回归解码中，单步执行包含 `Schedule → Forward → Sample → Post-process` 四个阶段。由于后处理依赖设备采样结果，CPU 与 GPU 之间存在强同步等待，导致计算设备在 CPU 执行调度与后处理期间处于空闲饥饿状态。

[worker/worker.py](https://github.com/deepseek-ai/DeepInfer/blob/main/deepinfer/worker/worker.py) 的 `execute_model_step()` 实现了零开销异步调度（Zero-Overhead Scheduling, ZOS）：

{ from: 'Engine / Scheduler', to: 'Worker', label: '下发第 N+1 步调度决策' },

{ from: 'Worker', to: 'Worker', label: 'CPU 并发处理第 N 步结果 (prev_step_state)' },
{ from: 'GPU', to: 'Worker', label: '前向计算完成' },

### 跨步状态修正与源码流水线

ZOS 的核心设计并非单纯的异步发射，而是**将解码后处理延迟到下一步模型前向的执行阴影中**：

```python
# deepinfer/worker/worker.py: execute_model_step() 异步流水线核心
# 1. 发射当前 step 前向 (GPU 硬件计算开始)
main_model_output = self.model_runner.execute_main_model(
    seq_metadata_list, self.gpu_cache, metadata_zos=metadata_zos, total_q=total_q
)

# 2. 处理上一 step 保存的输出 (CPU 在前向计算的等待窗口内重叠执行)
if self.is_driver_worker and not is_placeholder and prev_step_state is not None:
    post_process_outputs = self.callbacks.post_process_fn(prev_step_state)

# 3. 发射当前 step 采样
sampler_output = self.model_runner.execute_sample(
    seq_metadata_list, input_metadata, model_output, self.gpu_cache
)

# 4. ZOS 解码将当前状态延迟保留到下一步；Prompt 步骤则就地同步完成
if is_prompt or not envs.DEEPINFER_ZERO_OVERHEAD_SCHEDULING:
    return self.callbacks.post_process_fn(curr_step_state)
self.prev_step_state = curr_step_state
```

这种机制改变了状态可消费的确定性时机：由于在发射第 $N+1$ 步时，第 $N$ 步的采样结果仍在设备端流转，CPU 侧记录的序列长度（`seqlens_q/k`）存在滞后。为此，Worker 在执行前向发射前会调用 `_correct_seqlens_qk()`，依据上一轮的真实采样产物完成元数据修正。当存在设备到宿主（D2H）的数据拉取时，必须精确挂载对应 CUDA Event，确保只有数据就绪后才更新采样状态。

因此，**函数名标注为异步并不等于任意负载下都能达成完美重叠**。在真实性能审计中，必须通过 Profiler 联合观测 CPU 调度耗时、设备前向耗时与 D2H 同步事件的时间线重叠比例。

## 4. CacheEngine：从模型元数据到物理显存字节

[worker/cache_engine.py](https://github.com/deepseek-ai/DeepInfer/blob/main/deepinfer/worker/cache_engine.py) 为 DeepSeek-V4.1 特有的混合注意力体系构建了显存布局管理器 `GPUCacheInterface` 与 `KVCacheManager`。

该缓存体系依据每层的配置差异，将单一显存切分为多种异构视图：
- **`ica_cache` / `ica_state`**：索引注意力（Index Attention）的 Key 缓存与状态；
- **`ca_cache` / `ca_state`**：压缩注意力（Compressed Attention）的 Key-Value 缓存与边界累加状态；
- **`swa_cache`**：滑动窗口注意力（Sliding Window Attention）缓存。

### 显存物理容量与侵入式链表管理

在 C++ 底层，显存块管理由 [csrc/engine/block_manager.hpp](https://github.com/deepseek-ai/DeepInfer/blob/main/csrc/engine/block_manager.hpp) 接管。为了在极高并发下规避频繁堆内存申请释放，系统采用了基于连续数组存储的侵入式双向链表：

```cpp
// csrc/engine/block_manager.hpp
// 侵入式双向链表管理显存块：实现 O(1) 块分配与回收，消除内存碎片与分配抖动
struct Blocks {
    std::vector<BlockNode> _blocks;
    int _head, _tail, _size;

    void _push_back(int i) {
        TORCH_CHECK(i > 0 && i < static_cast<int>(_blocks.size()));
        auto &block = _blocks[i];
        block.prev = _tail;
        if (_tail) { _blocks[_tail].next = i; }
        else { _head = i; }
        _tail = i;
        _size += 1;
    }
};
```

在工程评估中，绝对不能以“层数 × Token 数 × 标称字节”粗暴估算显存占用。源码中的多组底层计算函数展示了极为细致的物理约束：

- `_kv_bytes_per_token()`：计算单 Token 交织 KV 数据及缩放因子的实际字节数，检查维度对齐；
- `_get_qk_topk_bytes()`：计算索引器 FP4 格式的打包字节与 UE8M0 格式的尺度因数开销；
- `_state_bytes()`：按照 `[num_state_token, 2, head_dim]` 计算全精度浮点状态缓冲尺寸；
- **硬件对齐约束**：代码严格规定，DeepGEMM 索引块跨度必须满足 128 字节物理对齐，多处中间偏移量需满足 32 字节对齐。未对齐部分必须计入填充 Padding；
- **层间共享复用**：通过 `layer_kv_map` 或 `layer_index_module_map` 标记为共享的层，直接复用前序层的物理偏移量，不分配重复空间；纯 SWA 层对应的普通 KV 长度直接置 0。

### SWA 缓存为何显著大于窗口尺寸

源码明确定义了两个尺寸函数：
1. `get_inference_swa_block_size(window_size)`：在基础窗口之上，强行叠加 `DEEPINFER_MAX_BACKTRACKING_TOKENS`（最大推测回退历史）；
2. `get_kvstore_swa_block_size(window_size)`：在推理尺寸基础上，进一步增加预填落盘与 YOCO 截断的锚点余量。

系统将存储粒度 `KVSTORE_GRAIN` 硬编码为 128 Tokens，规定持久化写入仅在 128 的整数倍边界处触发。当 Prefill 结束位置未对齐该边界时，必须在显存中保留足量缓冲区以维持上下文完整性。若盲目按照裸窗口分配显存，模型在遭遇推测回退或截断边界时将直接引发越界越权异常。

## 5. SWA Bounded Replay 的截断与重放语义

在 DeepSeek-V4.1 的 YOCO 架构下，Decoder 各层无需对完整前缀进行全局注意力交互，其全局语义通过 Encoder 顶层的隐状态跨层投影获得。因此在解码端，注意力计算退化为局部的滑动窗口（SWA）。

**SWA Bounded Replay 绝不等于“粗暴丢弃窗口外的缓存”。**

若要安全恢复解码状态，必须维系三条严格的边界契约：
1. **重放起点对齐**：重放计算截断在最近的 128 Tokens 边界处，将查询向量限定在局部区间，确保恢复代价为常数级；
2. **状态环形缓冲（State Ring）一致性**：YOCO 消费层 SWA 被分为保留区与丢弃区。丢弃区的重建依赖前向重算，而保留区必须完整覆盖 SWA 窗口加上推测解码的最大回溯跨度；
3. **压缩边界无依赖性**：压缩窗口边界与 128 Tokens 粒度自然对齐，避免跨边界引入历史递归依赖。

如果在系统层仅根据前缀命中率估算收益，却忽略了当 SWA 局部缓存缺失时触发的重放开销，实际的端到端吞吐收益可能大打折扣。

## 6. DSpark 变长推测解码与状态推进

DeepInfer 集成了 DSpark 变长推测解码（Speculative Decoding）优化。ModelRunner 针对草稿预测头配置了专用的 `DFlashCudaGraphRunner`。

### 置信度驱动的动态验证预算

传统的推测解码通常采用固定的验证长度（如固定验证 5 个 Draft Tokens）。由于不同请求、不同上下文位置的接受概率差异巨大，固定长度在低置信度下会白白浪费宝贵的验证算力。

DSpark 在模型前向中引入 Confidence Head 预测每个草稿 Token 的接受概率，在调度阶段利用 TileLang 核函数在 GPU 上执行前缀积与 Top-K 全局排序，动态选取边际收益最高的 Token 组合投入验证（平均验证长度动态伸缩在 3.2 ~ 4.4 之间），在生产环境下实现了 4% ~ 11% 的吞吐收益。

### 状态推进与回退链条

在执行循环中，Engine 的 `_process_model_outputs()` 将实际接受的 Token 列表、草稿预测 Token 与置信度传递给原生 `process_MTPInfo()`，再调用 `Scheduler.process_outputs()` 推进序列状态。

当部分草稿 Token 被验证器拒绝时，系统会触发序列回退：
- 序列有效长度截断至最后被接受的 Token 位置；
- KV Cache 与 State Buffer 依赖先前预留的 `max_backtracking_tokens` 缓冲安全恢复；
- 紧随其后的结构化输出文法状态机也必须同步回滚，确保状态完全自洽。

## 7. 结构化输出：异步文法编译与回滚一致性

在企业级 serving 场景下，强制模型遵循 JSON Schema、Regex 或 EBNF 是高频刚需。DeepInfer 的结构化输出机制由 [structure_output/so_matcher_builder.py](https://github.com/deepseek-ai/DeepInfer/blob/main/deepinfer/structure_output/so_matcher_builder.py) 与 [matcher.py](https://github.com/deepseek-ai/DeepInfer/blob/main/deepinfer/structure_output/matcher.py) 承载。

### 编译解耦与异步轮询

Schema 编译为有限状态自动机（DFA）属于典型的 CPU 重型操作：
1. 引擎在独立线程池中异步调度 `XGrammarCompiler` 编译文法，坚决不阻塞主调度循环；
2. 调度前通过 `pump()` 非阻塞探测编译 Future；一旦就绪立即绑定 Matcher 并将序列投递给 Scheduler；
3. 在每步解码采样前，`matcher.fill_vocab_mask()` 根据当前 DFA 状态填充词表合法 Bitmask，强行压制非法 Token 的 Logits。

### 为什么 Matcher 必须实现 Rollback

在推测解码与结构化输出组合使用的场景下，状态机的一致性变得极为微妙：
- 如果草稿模型连续预测了多个 Token，Matcher 在前向过程中会顺次推进状态；
- 一旦后续验证器判定中间某个 Token 未被接受，序列发生回退；
- 此时若 Matcher 未能同步调用 `rollback()`，文法状态将停留在被拒绝的非法分支上，导致下一步采样生成错误的掩码，甚至误杀合法的语法起点。

因此，源码中 Matcher 的状态回退不是防御性冗余，而是约束解码与推测解码协同工作的数学前提。

## 8. 源码维度的系统审查准则

基于 DeepInfer 的代码依赖与数据流拓扑，在评估或调优该系统时，应当坚持以下工程审查准则：

1. **异步发射不等于零气泡重叠**：必须结合 CUDA Event 观测 D2H 回传、CPU 调度与设备计算的真实时间线分布；
2. **算子视图不等于持久化存储**：代码中的 `CacheEngine` 管理的是显存内的物理切片，与生产环境基于 3FS 集群的分层存储不是同一个系统边界；
3. **有限 SWA 窗口不等于能任意丢弃历史**：推测解码的回退需求、128 Tokens 对齐粒度与压缩状态共同决定了显存保留下界；
4. **Draft Token 数量不等于净收益**：必须将置信度验证开销、拒绝回退成本与硬件吞吐曲线结合评估；
5. **显存容量不能由单维参数推导**：CUDA Graph 静态图捕获开销、双向链表对齐余量、混合精度缩放因子均直接参与最终 Block 数量决策。

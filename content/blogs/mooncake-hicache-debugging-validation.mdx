Mooncake + HiCache 最难调的地方，不是某个 API 调不通，而是系统可能在每一层都给你一个“看起来成功”的信号，却仍然没有形成可复用的 KV cache contract。

这篇只追一个实际问题：**怎么确认一段 remote KV cache 真的被写入、查到、读回 Host，并最终 load back 到 GPU。** 这个问题重要，是因为 `MooncakeStore setup successfully`、`batch_exists` 命中、Transfer Engine completed、Host buffer 填充，分别只能证明一段链路成立；它们都不能单独证明 runtime 已经复用了这段 prefix。

本文不是排一组日志关键词，而是把 remote KV 命中拆成可验证的状态转换：配置启用、backend 初始化、Host buffer 注册、page/object 命中、Storage->Host、Host->GPU、scheduler 使用。每一步都可以单独成功，也都可能成为假阳性。

只看到“Mooncake enabled”不够。完整命中链路要同时成立：

```text
HiCache enabled
  -> Host pool 可用
  -> Storage backend 初始化成功
  -> Host buffer 注册到 Mooncake
  -> page keys 写入 Store
  -> batch_exists 命中连续前缀
  -> batch_get_into 成功读回 Host
  -> load_back 成功回到 GPU
  -> scheduler 使用这段 GPU KV
```

## Article Contract / Source Context

本文基于 SGLang HiCache 和 Mooncake Store backend 的源码阅读，重点观察 SGLang `v0.5.14` 相关路径：

```text
python/sglang/srt/mem_cache/unified_radix_cache.py
python/sglang/srt/mem_cache/hicache_storage.py
python/sglang/srt/mem_cache/storage/mooncake_store/mooncake_store.py
```

排障时对应的调用链可以压成：

```text
Symptom
  -> check configuration
  -> check runtime branch
  -> check page key and object expansion
  -> check Mooncake Store get/put behavior
  -> check Transfer Engine / registered memory
  -> check Host->GPU load_back
  -> check scheduler-visible reuse signal
```

本文覆盖调试顺序、观察点和失败分层；不覆盖完整 benchmark，也不证明某个 workload 下 remote KV 一定降低延迟。Mooncake upstream commit 未在当前博客仓库中固定，因此本文不写具体 commit hash。

本文的判断标准是克制的：某个日志或状态只能证明它所在层的条件成立。只有配置、runtime path、Store metadata、bytes movement、Host->GPU commit 和 scheduler 行为连起来，才能接近“remote KV 真的命中”。

## 先确认参数层

SGLang 侧至少要确认：

```text
--enable-hicache
--hicache-ratio / --hicache-size
--hicache-write-policy
--hicache-mem-layout
--hicache-storage-backend mooncake
--hicache-storage-backend-extra-config
```

Mooncake 侧要确认：

```text
metadata_server
protocol
device_name
master_server_address
global_segment_size
standalone_storage
enable_ssd_offload
```

如果只是打开 HiCache，但没有 storage backend，那只有 L1/L2，没有 Mooncake L3。如果 backend 是 Mooncake，但 Host layout 不满足 backend 要求，zero-copy page meta 也可能失败。

这一层的结论只能证明“配置允许系统进入远端缓存路径”。它不能证明 runtime 真的产生了 page key，也不能证明任何 object 已经进入 Mooncake Store。

## 再确认初始化层

初始化阶段要看几件事：

```text
MooncakeStore setup successfully
register_mem_pool_host
register_buffer(host_pool.kv_buffer)
register_mem_host_pool_v2 for side pools
warmup successfully
```

如果是 shared Transfer Engine，还要确认是否真的复用：

```text
shared TE exists
device_name matches IB device
metadata_server == P2PHANDSHAKE
protocol == rdma
```

条件不满足时，Mooncake Store 会走独立 setup。这不是错误，但排查性能时要知道自己到底用了哪条 TE。

这一步的证据也要谨慎解释：初始化成功说明 backend 可以被创建，Host buffer 可能已经注册，但不说明当前请求一定经过了 `batch_set` 或 `batch_get`。

## 写入验证：看 page 是否进入 Store

写入链路：

```text
write_backup
  -> Host KV page
write_backup_storage
  -> HiCacheStorage.batch_set_v1/v2
MooncakeStore.batch_set_v1/v2
  -> batch_is_exist
  -> batch_put_from / batch_put_from_multi_buffers
```

要确认的不是“有没有调用 set”，而是：

- `node.backuped` 是否为真。
- `node.hash_value` 是否生成了 page keys。
- `backuped_storage` 或相关完成回调是否推进。
- Mooncake backend 是否跳过了已存在 key。
- MHA K/V object 是否都写成功。
- v2 side pool 是否也写成功。

常见误判是只看到 KV page 写成功，但 side pool 没写，最后 hybrid prefix 仍然不能完整复用。

写入验证的边界是：`batch_set` 成功接近于证明 page/object 已经进入 Store 写路径，但不证明后续 request 会命中，也不证明 read path 能把它完整拉回 GPU。

## 查询验证：看连续命中边界

remote cache 命中不是任意 key 存在，而是连续 page prefix 存在。

Mooncake backend 的 `batch_exists` 会把 logical page key 展开成 object keys：

```text
MHA:
  page_k
  page_v

MLA:
  page_k

split heads:
  page_head0_k
  page_head0_v
  page_head1_k
  page_head1_v
```

只要中间某个 object 缺失，连续命中就会截断。

排障时要问：

- logical page key 是否稳定。
- extra_backend_tag 是否导致 key 前缀变化。
- TP size / split head 策略是否改变 key expansion。
- batch_exists 返回的是连续页数，不是独立 bool 列表。

这一层能证明的是 metadata/key 语义对上了一部分。它不能证明 bytes 已经搬回 Host，也不能证明 GPU slots 已经可用。

## 读取验证：看 Host 是否填充

读链路：

```text
prefetch_from_storage
  -> Host indices allocated
  -> HiCacheStorage.batch_get_v1/v2
  -> MooncakeStore.batch_get_into
  -> Host KV pages filled
```

验证点：

- Host pool 是否分配成功。
- prefetch length 是否超过阈值。
- prefetch 是否被 rate limit。
- Mooncake get 返回 object 级成功。
- `_batch_postprocess` 是否把 object 级结果折成 page 级成功。
- 失败后 Host buffer 是否被释放。

如果 batch_get 成功数低，但 Mooncake Store 里 key 明明存在，优先检查 key expansion、buffer pointer、buffer size 和 group/tag 配置。

这一层开始接近数据面，但仍然只是 Storage->Host。Host page 被填充后，attention kernel 仍然不能直接使用它。

## load back 验证：看 GPU 是否真正可用

Storage->Host 之后还要 Host->GPU：

```text
load_back
  -> allocate GPU indices
  -> cache_controller.load
  -> commit_hicache_transfer
  -> node.value 更新
```

验证点：

- load_back token 数是否低于 threshold。
- mem_quota 是否允许本次 load。
- GPU pool 是否有足够空间。
- evict 是否成功释放空间。
- device_indices 是否 commit 回 node。
- ongoing_load_back 是否完成并释放 lock。

如果只看到 storage prefetch 成功，但 GPU 仍然重新 prefill，问题往往在 load_back 或调度时机，而不是 Mooncake Store。

这是最容易漏看的边界：remote object 已经读回 Host，不等于 `node.value` 已经更新成 device slots。只有 load back 和 commit 完成，runtime 才有机会把这段 prefix 当作 GPU cache 使用。

## Transfer Engine 验证：看数据面状态

Mooncake Store 层读写成功还依赖 Transfer Engine。

需要确认：

- local memory 是否 register。
- remote Segment 是否 open。
- protocol 和 endpoint 是否匹配。
- BatchID 是否提交成功。
- `getBatchTransferStatus` 是否 completed。
- 是否发生 timeout/failed/canceled。

但也要记住：Transfer Engine 成功只证明 bytes 搬完，不证明 object 在 Store 语义上可读。

## What to check first

如果现象只是“remote KV 没有明显生效”，不要直接跳到 RDMA、TCP 或 Mooncake Store。先按下面的顺序缩小范围：

```text
1. Configuration:
   HiCache 是否开启，storage backend 是否真的是 mooncake。

2. Runtime branch:
   当前请求是否产生可备份 prefix，write_backup_storage / prefetch_from_storage 是否被触发。

3. Key semantics:
   logical page key 是否稳定，MHA/MLA/split heads 展开后的 object 是否完整。

4. Store metadata:
   batch_exists 是否返回连续前缀，PutEnd/COMPLETE/lease 语义是否满足。

5. Data movement:
   batch_get_into / batch_put_from 是否围绕注册过的 Host buffer 工作，TE 状态是否 completed。

6. Runtime commit:
   Host->GPU load_back 是否完成，GPU slots 是否 commit，scheduler 是否真正使用 reused prefix。
```

这个顺序的价值在于，它把问题从“Mooncake 不工作”拆成配置、runtime、key、metadata、transport 和 cache semantics 六类。每一类都有不同证据，不能只靠一个成功日志跨层推断。

## 常见现象和定位方向

```text
现象: storage backend 初始化成功，但没有 remote hit
优先查: write policy、hit threshold、node.hash_value、batch_set 是否发生

现象: Mooncake 里有 key，但 batch_exists 返回短
优先查: K/V object 是否都存在、split heads、TP suffix、extra_backend_tag

现象: batch_get 成功，但推理仍然重新 prefill
优先查: Host->GPU load_back、load_back_threshold、mem_quota、GPU 空间

现象: batch_get/put 慢
优先查: page size、batch size、memory registration、transport、NIC/NUMA

现象: 偶现旧数据
优先查: PutEnd、lease、local hot cache token、group semantics
```

## 最小验证闭环

做最小实验时，可以按下面顺序看：

```text
1. 启动时确认 MooncakeStore setup 和 register_buffer 成功。
2. 发送一个长 prompt，让 HiCache 产生可备份 prefix。
3. 观察 write_backup_storage 是否触发。
4. 用相同 prefix 再发请求。
5. 观察 batch_exists 是否返回非零连续页数。
6. 观察 batch_get 是否读回 Host。
7. 观察 load_back 是否把 Host KV 回填到 GPU。
8. 对比 prefill token 数、latency 和 cache metrics。
```

如果第 5 步命中但第 7 步没有成功，说明 Mooncake Store 已经工作，问题在 HiCache load back 或 scheduler 边界。

## What this proves — and what it does not

这套验证链能证明的是：一次请求是否按预期经过了 Mooncake-backed HiCache path 的关键边界。它把单层信号拆开，避免把 setup、metadata hit、bytes transfer 和 GPU reuse 混成一个结论。

它不证明：

- 不证明 remote KV 在所有 prompt 分布下都有收益。
- 不证明 Transfer Engine completed 等价于 cache 语义完整。
- 不证明 `batch_exists` 命中后一定会省掉 prefill。
- 不证明本地最小验证能覆盖真实多节点部署里的设备、NUMA、网络和资源竞争。

因此更稳的结论应该是：这些观察点能逐层排除问题，直到你接近 end-to-end reuse；真正的性能收益仍然需要独立的 benchmark 和固定实验条件。

## Takeaway：remote hit 是端到端行为，不是单层日志

验证 remote KV 的终点不是某一行日志，而是运行时行为变了：相同 prefix 的请求能拿到连续命中，Host pages 被填充，load back 提交到 GPU，并在固定实验条件下表现出 prefill 工作减少或端到端延迟改善。

如果只看到 `MooncakeStore setup successfully`，只能说明 backend 初始化成功；如果只看到 Transfer Engine completed，只能说明 bytes 搬完；如果只看到 `batch_exists` 返回命中，只能说明 Store metadata 和 object key 对上了。它们都还不是完整命中。

最可靠的排障方式是沿着 page 级语义走：一个 logical page 展开成哪些 object，这些 object 是否都存在且可读，读回 Host 后是否被折回 page 级成功，最后是否 load back 到 GPU 并被调度器使用。这样定位会慢一点，但不会被某一层的“成功日志”误导。

限制也要说清楚：本文给的是验证顺序和观察点，不替代完整压测；如果要证明 remote KV 在某个 workload 下有收益，还需要固定 prompt 分布、并发、page size、backend protocol、设备拓扑和 tail latency 指标。

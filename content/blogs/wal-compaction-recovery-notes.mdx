存储系统最麻烦的问题，不是正常路径写入成功，而是崩溃后怎么回答一句话：**哪些写入已经算数，哪些只是半成品。**

几个崩溃点放在一起看，会比单独背 WAL、manifest、compaction 更有用：

```text
WAL record 写了一半
WAL 写完但 memtable 还没更新
memtable flush 生成了 SSTable，但 manifest 没记录
manifest 记录了新文件，但旧文件还没删
compaction 输出了一半
delete tombstone 写入了，但低层旧值还在
```

恢复逻辑的本质，就是在一堆文件和日志里重新确认正式历史。

## 写入成功的边界在 WAL 策略里

WAL 的原则是 write-ahead：数据进入内存结构前，先把日志写下来。

简化路径：

```text
append WAL record
  -> maybe fsync / group commit
  -> update memtable
  -> return success
```

这里有一个必须说清楚的边界：系统什么时候对客户端返回成功？

如果返回前 WAL 没有持久化，崩溃后这次写入可能消失。很多系统会用 group commit 在多个写入之间摊 fsync 成本：

```text
write 1
write 2
write 3
  -> one fsync
  -> all return
```

这不是免费优化。它改变的是延迟、吞吐和持久性窗口之间的取舍。

## WAL record 要能识别半条记录

WAL 写了一半进程挂掉，是恢复里非常具体的问题。

一个稳的 WAL 格式通常需要：

- record length。
- type / batch boundary。
- checksum。
- sequence number。
- fragmentation handling。

恢复时读到坏 checksum 或半条 record，不能把后面的随机字节解释成写入。它要能停在最后一条完整有效记录。

```text
valid record seq=101
valid record seq=102
partial record seq=103
  -> ignore / truncate from here
```

所以 WAL 格式不是文件格式洁癖。它直接决定崩溃后能不能找到最后的可信边界。

## flush 完成不等于文件进入历史

memtable flush 会生成 SSTable。但 SSTable 文件存在，不代表它已经属于数据库当前版本。

常见边界是 manifest/version edit：

```text
write table file 000123.sst
fsync table file / directory
append manifest edit: add file 000123 at L0
maybe recycle old WAL
```

如果崩溃发生在 SSTable 写完、manifest edit 之前，恢复时这个文件通常只能当 orphan / pending output 处理，不能直接纳入 live set。

这条规则很关键：**文件存在不是事实，metadata 承认才是事实。**

## manifest 是数据文件的时间线

LSM 里真正描述当前版本的，不是目录里有哪些 `.sst` 文件，而是 manifest replay 后得到的 Version。

compaction 会产生类似 edit：

```text
delete file A from L1
delete file B from L1
add file C to L2
add file D to L2
```

只有这个 edit 成功安装以后，新文件才可见，旧文件才可以进入 obsolete cleanup。

如果 manifest 写成功后崩溃，旧文件可能还在目录里，但恢复时它们不再属于 live files。反过来，如果新文件写出来但 manifest 没写成功，恢复时不能把它们当 live files。

这就是为什么恢复入口通常先读 `CURRENT`，找到 manifest，再 replay manifest edits，而不是直接扫描所有 SSTable 猜状态。

## compaction 的原子性靠“新文件 + manifest edit”

Compaction 不会原地改旧文件。它会读旧文件，写新文件，然后安装 metadata edit。

```text
inputs:
  L1: A, B
  L2: X, Y

outputs:
  L2: C, D

install:
  delete A, B, X, Y
  add C, D
```

崩溃点有三类：

第一，输出文件没写完。恢复时应该清理。

第二，输出文件写完但 manifest 没安装。恢复时仍然不能使用这些新文件。

第三，manifest 已安装但旧文件没删。恢复时 live set 已经指向新版本，旧文件只是垃圾，后续 cleanup 可以删。

这个设计把危险的原地修改变成了可恢复的版本切换。

## tombstone 不是删除完成

删除在 LSM 里通常写 tombstone：

```text
seq=200 key=a tombstone
seq=150 key=a value=v2
seq=100 key=a value=v1
```

读路径看到当前 snapshot 可见的 tombstone，就认为 key 不存在。但低层旧值仍然可能在磁盘上。

tombstone 什么时候能被清掉，取决于：

- 是否已经覆盖所有可能包含旧值的更低层。
- 是否还有 snapshot 需要旧 sequence number。
- 是否有 range tombstone 或 merge operand 之类复杂语义。

如果 snapshot 长时间不释放，compaction 可能不能丢旧版本。于是删除很多数据后，空间仍然不降。

## sequence number 是恢复和可见性的共同语言

sequence number 把写入排成一条时间线。

```text
seq=105 key=a value=v3
seq=101 key=b value=x
seq=98  key=a tombstone
seq=70  key=a value=v1
```

读取时要按 snapshot sequence 判断可见性。恢复时也要知道 WAL replay 从哪里开始、哪些 memtable 已经 flush、哪些 sequence 已进入 SSTable。

没有这条时间线，系统就很难同时处理：

- 新写覆盖旧写。
- snapshot read。
- tombstone 清理。
- WAL replay。
- compaction 丢弃旧版本。

这也是为什么 sequence number 通常会贯穿 WAL、memtable、SSTable 和 manifest 相关逻辑。

## 恢复入口不是“读所有文件”

一个典型恢复流程更像：

```text
read CURRENT
  -> locate manifest
  -> replay manifest edits
  -> build live file set
  -> identify WAL files needing replay
  -> replay valid WAL records
  -> rebuild memtables
  -> cleanup obsolete / orphan files
```

这里每一步都在缩小不确定性：

- manifest 告诉你哪些 SSTable 属于正式版本。
- WAL 告诉你哪些写入还没进入 SSTable。
- checksum / record boundary 告诉你日志读到哪里可信。
- obsolete cleanup 处理崩溃留下的旧文件和半成品。

恢复越依赖明确 metadata，越不需要靠猜。

## Benchmark 不该只看正常运行

存储系统 benchmark 经常只看吞吐、平均延迟、p99。但恢复成本也是可用性的一部分。

我会额外测：

- 写入高峰后重启要 replay 多久。
- WAL 堆积很多时 open database 要多久。
- manifest 很大时 replay 是否变慢。
- compaction backlog 很高时重启是否有额外清理成本。
- 大量 tombstone 后空间何时回收。
- 崩溃注入后是否有 orphan 文件残留。

线上最怕的是：正常跑的时候指标漂亮，一重启恢复几十分钟。

## 我会怎样做故障注入

读或验证一个存储引擎时，我更喜欢按崩溃点打断：

```text
after WAL append, before memtable insert
after memtable insert, before client return
after SSTable file write, before manifest edit
after manifest edit, before obsolete cleanup
during compaction output
after tombstone write, before compaction
```

然后检查：

- 重启后数据是否符合持久性承诺。
- 半写 WAL 是否被截断。
- orphan SSTable 是否被清理。
- live file set 是否只来自 manifest。
- old snapshot 语义是否保持。
- 空间回收是否最终发生。

如果这些点都能解释清楚，WAL、manifest、compaction 和 recovery 才真的连成了一个存储系统。

## 崩溃恢复是在确认历史，不是在修文件

WAL 记录尚未稳定成 SSTable 的写入，manifest 记录哪些 SSTable 属于当前版本，compaction 用新文件和 metadata edit 替换旧历史，recovery 则在重启时重新走一遍这些证据。

所以恢复不是“尽量把文件救回来”，而是确认哪些历史已经被系统正式承认。

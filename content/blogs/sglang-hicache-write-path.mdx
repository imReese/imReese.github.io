HiCache 写路径回答的是：**一段已经在 GPU 上算出来的 prefix KV Cache，什么时候、怎么离开 GPU，并且离开以后还保持可复用。**

这个问题的坑在于，写路径里有两次“成功”：一次是 GPU KV 被备份到 Host，一次是 Host page 被写进 Storage backend。只看其中一次成功，就会误判后续请求能不能 remote hit。

## Source Context

在 SGLang `v0.5.14` 中，主线入口在：

```text
python/sglang/srt/mem_cache/unified_radix_cache.py
  write_backup
  write_backup_storage

python/sglang/srt/mem_cache/hicache_storage.py
  PoolTransfer
  HiCacheStorage.batch_set_v1/v2

python/sglang/srt/mem_cache/storage/mooncake_store/mooncake_store.py
  MooncakeStore.batch_set_v1/v2
```

关键调用链：

```text
write_backup(node)
  -> collect GPU device_indices
  -> build PoolTransfer
  -> cache_controller.write(...)
  -> commit_hicache_transfer(...)
  -> node gains Host backup
  -> write_backup_storage(...)
  -> HiCacheStorage.batch_set_v1/v2
  -> MooncakeStore.batch_set_v1/v2
  -> Store object write result folds back to page result
```

本文只分析 HiCache 写路径和 Mooncake backend 的 page/object 边界，不覆盖完整 eviction policy、GPU kernel、分布式部署 benchmark，也不声称某种 write policy 在所有 workload 下更优。

## 写路径分两段

HiCache 写入不要理解成一次 `set(key, value)`。它至少分成两段：

```text
D->H backup:
  GPU KV pool -> Host KV pool

H->Storage backup:
  Host KV pool -> Storage backend
```

## D->H：write_backup

`write_backup(node)` 的输入是一个 radix node。这个 node 对应一段 prefix，它的 GPU KV indices 保存在 base component 的 `value` 中。

写入 Host 前，代码会先维护一个重要不变量：

```text
非 write_back 场景下，父节点必须先 backup。
```

原因是 prefix cache 是树结构。如果子节点已经写到 Host，而父节点没有写，后续只保留子节点会破坏 prefix 的连续可恢复性。`write_backup` 因此会在必要时递归 backup parent。

核心流程可以压成：

```text
write_backup(node)
  -> 取 node 的 GPU device_indices
  -> 构造 PoolTransfer(name=KV, device_indices=...)
  -> 为 Mamba/SWA/DSA 等组件构造额外 transfers
  -> Host 空间不够时 evict_host
  -> cache_controller.write(...)
  -> 得到 host_indices
  -> commit_hicache_transfer(...)
  -> 标记 node 已经有 Host 备份
```

## PoolTransfer 是跨层描述符

`PoolTransfer` 同时服务 D->H、H->D、H->Storage、Storage->H。它不是 Mooncake 专属结构，而是 HiCache 用来描述“某个 pool 的一批 page 怎么搬”的统一对象。

写 Host 时，KV transfer 主要关心：

```text
name=PoolName.KV
device_indices=<GPU token indices>
```

写 Storage 时，同一个逻辑会变成：

```text
name=PoolName.KV
host_indices=<Host token/page indices>
keys=<storage page keys>
```

这就是为什么 `PoolTransfer` 里同时有 `device_indices`、`host_indices` 和 `keys`。它要跨越多个 tier。

## 写穿和写回的区别

HiCache 中的 write-through 和 write-back 容易混。

write-through 更主动。一个 node 被命中到一定次数，或者策略要求写穿时，HiCache 会提前把它备份到 Host，甚至继续写到 Storage。这样后续驱逐 GPU 时成本更低。

write-back 更像驱逐前的保护。GPU 空间不够，需要驱逐某个 node，但它还没有 Host 备份，此时先 `write_backup(node, write_back=True)`，再把 GPU slot 回收。

区别可以这样看：

```text
write-through:
  cache 仍在 GPU，但先复制一份到 Host/Storage

write-back:
  为了释放 GPU，先保存到 Host，再移除 GPU 引用
```

两者都会让 KV 离开纯 GPU 状态，但触发时机不同。

## H->Storage：write_backup_storage

当 node 已经有 Host 备份，并且启用了 storage backend，`write_backup_storage(node)` 会把 Host page 写到 L3。

核心流程：

```text
write_backup_storage(node)
  -> 检查 enable_storage、cache_controller、node.backuped
  -> 可选生成 prefix_keys
  -> 为额外组件构造 BACKUP_STORAGE transfers
  -> 构造 KV PoolTransfer(host_indices=node.host_value, keys=node.hash_value)
  -> cache_controller.write_storage(...)
  -> 记录 ongoing_backup，持有 Host lock
```

注意这里写入 storage 的 key 是 `node.hash_value`，不是原始 token list。HiCache 会按 page 计算 hash key，让 L3 storage 可以按 page 查询和复用。

## 为什么要持有 Host lock

Storage 写是异步的。`write_backup_storage` 发起后，Host KV page 还不能立刻被回收，否则 backend 可能正在从这块 Host buffer 读数据。

因此代码会在 `ongoing_backup` 里记录 operation id，并通过 host lock 保护 node：

```text
ongoing_backup[operation_id] = (node, host_lock_params)
```

等 storage 写完成后再释放。这个机制防止了一个经典错误：上层认为已经发起写入，于是复用 Host buffer，导致远端存到错误内容。

## v1 和 v2 写入

普通 KV 路径走 v1：

```text
batch_set_v1(keys, host_indices)
```

hybrid cache 走 v2：

```text
batch_set_v2(transfers)
```

v2 的意义是多个 pool 必须一起构成可复用 prefix。比如某些模型除了 KV，还需要 side state。如果 KV 写入成功但 side pool 没写，下一次 prefix 命中也不能完整复用。

因此 v2 按 pool 返回结果：

```text
{
  "kv": [true, true, false],
  "mamba": [true, true],
  "swa": [true]
}
```

最终可用 prefix 长度要取各 pool 的共同命中边界。

## 接到 Mooncake 时发生什么

当 backend 是 Mooncake，`batch_set_v1` 会把 logical page key 展开成 Mooncake object keys。

MHA 通常是：

```text
page_key
  -> page_key_<tp_or_head_suffix>_k
  -> page_key_<tp_or_head_suffix>_v
```

MLA 通常是：

```text
page_key
  -> page_key_<tp_or_rank_suffix>_k
```

然后 Mooncake backend 从 Host pool 拿 pointer 和 size：

```text
mem_pool_host.get_page_buffer_meta(host_indices)
```

最后调用 zero-copy put：

```text
batch_put_from(...)
batch_put_from_multi_buffers(...)
```

## 写路径的失败边界

写路径可能在几个位置失败：

- Host 空间不足，`evict_host` 后仍无法分配。
- D->H transfer 失败，`cache_controller.write` 返回 `None`。
- Storage backend 写失败，page 级结果返回 false。
- hybrid pool 某个 side pool 写失败，导致整体 prefix 可用长度缩短。
- Host lock 或 node split 处理不当，可能造成写入中的 node 状态不一致。

HiCache 通过 lock、ongoing operation 和 page 级结果尽量把失败限制在可回退状态，而不是把 radix tree 直接标成“全都可用”。

## Takeaway：写入成功必须按 page 级语义提交

HiCache 写路径最容易误读的地方，是把“某个 buffer 搬完”当成“这个 prefix 以后可复用”。更稳的读法是按 page 级语义看提交条件：

```text
parent prefix is recoverable
  -> GPU page has Host backup
  -> Host page stays locked during Storage write
  -> every required pool/object reports success
  -> logical page result is true
```

所以 `write_backup` 要关心父节点，`write_backup_storage` 要关心 Host page 生命周期，v2 写路径要关心 side pools 的共同结果。对 Mooncake backend 来说，写入的最终目标不是把一批 object 调用完 `put`，而是让一个 logical page 在后续 read path 中可以被完整地判断为 remote hit。

Mooncake 的 README 和文档会频繁提到 SGLang、vLLM、LMCache、disaggregated prefill-decode、KVCache pool。读这些材料时，一个容易踩的坑是把“系统愿景”和“当前仓库里的代码边界”混在一起。

边界可以先拆成三层：

- Mooncake 仓库里直接提供 Transfer Engine、Mooncake Store、Python binding、测试和集成文档。
- 上层框架负责请求调度、模型执行、prefill/decode worker 组织，以及什么时候决定复用或传输 KV Cache。
- 文档里的 SGLang/vLLM/LMCache 集成说明，是 Mooncake 能力如何接入上层框架的入口，但不等于所有上层 adapter 逻辑都在 Mooncake 仓库里。

本文作为系列附录，只回答一个问题：Mooncake 到底接在上层框架的哪里。

## Python binding 不是另一套 Store

Mooncake 的 Python API 很重要，因为上层 serving 框架通常不会直接写 C++ Store client 或 Transfer Engine API。但 Python 层不是另一个独立实现。

它主要通过 pybind11 把 C++ 能力暴露出去：

```text
Python app / framework
  -> mooncake.store / mooncake.engine
  -> pybind11 wrapper
  -> C++ Store client / Transfer Engine
  -> master + data transfer path
```

Store binding 里的 `MooncakeDistributedStore` 会暴露 setup、init、mount segment、put/get、tensor API、copy/move task 等方法。Transfer Engine binding 则暴露初始化、segment、sync/async transfer 等能力。

所以读 Python API 时，不要停在 wheel 包表面。关键是追它最终落到哪个 C++ 方法：是 Store 的 object API，还是 Transfer Engine 的传输 API。

## Tensor API 只是上层包装，底层仍是 object/slice

Mooncake 支持 tensor 读写，这很容易让人以为底层就是“tensor store”。但从 Store 的角度看，tensor 只是上层对象表达的一种。

底层还是 key、metadata、parts/slices、replica 和 Segment。tensor API 需要处理 dtype、shape、payload span 等信息，但这些最终会被组织成 Store 能处理的 object parts。

这也是为什么 zero-sized tensor 这种细节会出现在 Python binding 里。空 tensor 没有 payload，但 metadata 仍然要能表达 shape 和 dtype，读取时再恢复成 `torch.empty(shape, dtype)`。这个问题不属于 Transfer Engine；它属于 Python/tensor 包装层如何把上层对象语义映射到 Store object。

这个例子能说明 Mooncake 集成层的定位：它不是只做语言绑定，还要把框架里的对象模型翻译成 Store/Transfer Engine 能理解的接口。

## SGLang 有两条 Mooncake 路径

SGLang 里至少有两类 Mooncake 相关路径。

第一类是 PD disaggregation。prefill worker 和 decode worker 分开以后，KV Cache 需要跨节点传递。这条路径更靠近 Mooncake Transfer Engine，因为核心问题是把一段 KV 从一个 worker 搬到另一个 worker。

第二类是 HiCache L3 storage backend。它通过 `HiCacheStorage` 接入 `MooncakeStore`，把 prefix KV page 写入 Mooncake Store，再在后续请求中 prefetch 回 Host pool。

从边界上看，SGLang 仍然负责模型执行和请求调度。Mooncake 提供的是把 KV Cache 从一个节点搬到另一个节点的传输能力，以及在一些路径下和 Store/缓存体系配合的基础设施。

这意味着一个重要判断：不要在 Mooncake 仓库里期待看到完整的 SGLang scheduler。Mooncake 能力需要被 SGLang 的 runtime 和调度逻辑调用，但“什么时候值得等远端 KV Cache，什么时候回退 recompute，prefill/decode 如何分配请求”，这些问题属于上层 serving 系统。

Mooncake 提供的是这类决策可以依赖的数据面能力。

## LMCache / vLLM 更像 Store 后端关系

LMCache 和 vLLM 的语境稍微不同。LMCache 本身就是围绕 KV Cache reuse 做的一层系统，Mooncake Store 可以作为后端基础之一：把 KV Cache 对象放进一个分布式 object cache 里，再通过 Store 和 Transfer Engine 做跨节点访问。

vLLM 相关文档里也会看到 MooncakeStore 与 Redis 等方案的性能对比。这类 benchmark 有参考价值，但要小心它的范围：具体数字依赖模型、硬件、PD ratio、网络和 workload。更重要的不是“Mooncake 在所有情况下都更快”，而是它把 KV Cache 存储和搬运做成了一个专门面向 serving 的系统路径。

从接口边界看：

```text
vLLM / LMCache
  -> cache backend / object store abstraction
  -> Mooncake Store
  -> Transfer Engine
```

这和 SGLang 直接强调 Transfer Engine 的 PD 传输路径不同，但底层问题仍然是 KV Cache 的命名、存储、查询和移动。

## 上层集成的核心是成本模型

Mooncake 把能力提供出来以后，上层框架还要回答一个更难的问题：什么时候该用它？

远端 KV Cache 不是免费资源。它可能节省 prefill 计算，但也会引入网络传输、metadata 查询、等待和缓存命中不确定性。对 serving 系统来说，关键不是“能不能传”，而是：

- 远端 KV Cache 多大。
- 传回来要多久。
- recompute 要多久。
- 当前请求的 tail latency 预算是多少。
- decode worker 等待这段 KV 是否会影响其他请求。
- cache locality 是否能进入调度策略。

这些问题不完全属于 Mooncake 仓库本身，但 Mooncake 的 Store 和 Transfer Engine 是回答这些问题的基础设施。没有稳定的数据面和对象语义，上层 scheduler 很难认真考虑 KV Cache 复用。

## 边界比入口更重要

Mooncake 接在上层框架的位置，不是一个单点 API，而是一组边界。

Python binding 把 C++ Store 和 Transfer Engine 暴露给 Python 世界；tensor/object wrapper 把上层对象翻译成 Store 可处理的 parts/slices；SGLang 更关注 prefill/decode 分离下的 KV 传输；LMCache/vLLM 更容易从 cache backend 和 object store 角度接入。

真正要避免的是把这些边界混成一句“Mooncake 支持某某框架”。支持只是入口。技术上更重要的是：上层框架在什么时机调用 Mooncake，调用的是 Store 语义还是 Transfer Engine 数据面，以及这次 KV Cache 复用在成本模型上是否真的划算。

## 支持框架不是一个单点能力

Mooncake 的价值不在于提供一个“万能 KV cache API”，而是把几件底层能力做清楚：Python 可以调用 C++ Store/TE；Store 能表达 object、replica、lease；Transfer Engine 能在多种 transport 上搬远端内存。上层框架再把这些能力接到自己的 runtime、scheduler 和 cache policy 里。

因此看集成代码时，不要只找入口函数名。更重要的是看这次调用解决的是哪类问题：是 PD worker 间搬 KV，还是 HiCache L3 读写 page，还是 LMCache/vLLM 的 backend 存取。落点不同，应该关注的代码路径、性能瓶颈和正确性边界也不同。

成本模型也必须留在上层。Mooncake 可以让远端 KV 变得可用，但不替 SGLang 或 vLLM 决定当前请求是否值得等待 remote hit。这个判断需要结合 prefill 成本、传输成本、队列状态和 tail latency 预算。

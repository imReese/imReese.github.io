This article examines the execution mechanics, scheduling architecture, and state transitions of [DeepInfer](https://github.com/deepseek-ai/DeepInfer) through its public source code, cross-referenced with DeepSeek's technical report [DeepSeek V4.1 Flash Large-Scale Inference Deployment Practice](https://zhuanlan.zhihu.com/p/2095560295930508953). Source links reference the evolving main branch.

Before diving into code details, the boundary between the open-source repository and production architecture must be made clear. DeepInfer's README states that the public release focuses on the core offline inference engine. Full distributed KV storage systems, cluster-level VE/Prefill/Decode disaggregation, and global multi-replica load balancers are part of internal cloud infrastructure, not the standalone open-source code. This walkthrough focuses strictly on verifiable classes, dataflows, and contracts in the public codebase.

## 1. Architectural Overview and Execution Boundaries

In large-scale serving, the central engineering challenge is **how to drive tens of TFLOPS to PFLOPS of accelerator throughput with microsecond-level host control overhead**. DeepInfer addresses this through clean responsibility partitioning:

#### 1. Tensor Compute is Completely Decoupled from Python
Python code never carries out underlying tensor arithmetic. It serves exclusively as a host-side device proxy. Inside [`models/deepseek.py`](https://github.com/deepseek-ai/DeepInfer/blob/main/deepinfer/model_executor/models/deepseek.py) and [`v4_modules/mlp.py`](https://github.com/deepseek-ai/DeepInfer/blob/main/deepinfer/model_executor/models/v4_modules/mlp.py), all heavy linear algebra operations delegate directly to native kernels:

```python
# deepinfer/model_executor/models/v4_modules/mlp.py
# Dense and expert matrix multiplication executed via DeepGEMM assembly kernels
deep_gemm.m_grouped_fp8_fp4_gemm_nt_contiguous(
    hidden_states, self.weight, out, scales, recipe=(1, 1, get_fp8_casting_granularity())
)
```

- **MoE expert compute and dense GEMM**: handled by [DeepGEMM](https://github.com/deepseek-ai/DeepGEMM) (FP8/FP4 matrix multiplication optimized with hand-tuned SASS assembly);
- **MLA attention computation**: handled by [FlashMLA](https://github.com/deepseek-ai/FlashMLA) (CUDA/C++ kernels specialized for Multi-Head Latent Attention);
- **Inter-GPU communication**: handled by [DeepEP](https://github.com/deepseek-ai/DeepEP) (low-latency communication kernels operating over NVLink and RDMA);
- **Fused sampling and scheduling helpers**: authored in TileLang and JIT-compiled into hardware machine code at runtime.

#### 2. Scheduler in C++: Eliminating Host Bottlenecks
Scheduling and cache allocation are CPU-bound combinatorial algorithms managing discrete state. When decode steps execute in only a few milliseconds, traversing sequence objects, querying dictionaries, and triggering garbage collection (GC) in Python would introduce hundreds of microseconds or milliseconds of latency jitter, starving accelerators.
DeepInfer places the [Scheduler](https://github.com/deepseek-ai/DeepInfer/blob/main/csrc/engine/scheduler.hpp) and [BlockManager](https://github.com/deepseek-ai/DeepInfer/blob/main/csrc/engine/block_manager.hpp) in C++20 with `ObjectPoolPyObject` preallocated memory pools, keeping scheduling decisions within tens of microseconds.

#### 3. ModelRunner in Python: CUDA Graph Eliminates Interpreter Cost
During autoregressive decoding, Python operator launch overhead is eliminated by [CudaGraphRunner](https://github.com/deepseek-ai/DeepInfer/blob/main/deepinfer/worker/cuda_graph_runner.py). Once the static execution graph is captured during warmup, ModelRunner completely bypasses layer-by-layer interpretation during decode:

```python
# deepinfer/worker/model_runner.py: execute_main_model()
with cpu_timer.record("launch_forward"), forbid_cuda_sync():
    if run_cuda_graph:
        # Decode phase: launch recorded static graph directly in <2 microseconds
        model_output = self.cuda_graph_runner.replay(cuda_graph_used)
    else:
        # Standard layer-by-layer invocation used only during non-graph prefill
        model_output = self.model(kv_caches=kv_caches, input_metadata=input_metadata)
```

This issues a single `cudaGraphLaunch` driver invocation in under 2 microseconds. The design maintains compatibility with Hugging Face Safetensors checkpoints while ensuring maximum engineering velocity for exploratory features such as YOCO cross-layer projections and Engram modules.

#### 4. In-Place Zero-Copy Tensor Assembly
To avoid serialization overhead across language boundaries, ModelRunner preallocates static tensor buffers. ```cpp

## 2. Engine Step Loop and State Decoupling

A single execution step progresses through a disciplined sequence of events:

<SequenceDiagram title="DeepInfer step control flow" actors={['LLM.generate', 'LLMEngine.step', 'C++ Scheduler', 'Worker', 'ModelRunner / Device']} steps={[
{ from: 'LLM.generate', to: 'LLMEngine.step', label: 'Token IDs + sampling params' },
{ from: 'LLMEngine.step', to: 'C++ Scheduler', label: 'schedule(sequence_metadata_pool)' },
{ from: 'C++ Scheduler', to: 'LLMEngine.step', label: 'Sequence view + SchedulerOutputs' },
{ from: 'LLMEngine.step', to: 'Worker', label: 'execute_model_step(...)' },
{ from: 'Worker', to: 'ModelRunner / Device', label: 'execute_main_model → execute_sample' },
{ from: 'Worker', to: 'LLMEngine.step', label: 'Step artifacts and sample tokens' },
]}/>

In [entrypoints/llm.py](https://github.com/deepseek-ai/DeepInfer/blob/main/deepinfer/entrypoints/llm.py), `LLM.generate()` enqueues requests. If Token IDs are not pre-encoded, tokenization runs once via `tokenizer.encode()` before entering the engine. On the output path, `_run_engine()` collects `RequestOutput` and calls `tokenizer.decode()` on demand. Tokenization remains outside the inner step loop.

The central execution loop lives in `step()` within [engine/llm_engine.py](https://github.com/deepseek-ai/DeepInfer/blob/main/deepinfer/engine/llm_engine.py):
1. The engine invokes `self.scheduler.schedule(self.sequence_metadata_pool)` to obtain candidate sequences and allocation decisions;
2. If the scheduler requests state cloning or zeroing, Worker triggers memory resets and manages lifetime via `DeferredRelease`;
3. `post_schedule()` advances structured-output matchers and multimodal staging;
4. `_execute_model_async_step()` drives Worker execution across devices;
5. Returned tokens are processed and completed sequences are finalized.

### Lifetime Separation Across Three Core Structures

Runtime data must not be lumped together as generic "batch state". The codebase enforces strict separation across three distinct lifecycles:

<StateDiagram title="State transition contracts across step boundaries" states={[
{ label: 'SchedulerOutputs', detail: 'Immutable decision snapshot from C++ scheduler carrying active sequences, token budgets, and memory ops', next: 'Dispatch to Worker', tone: 'amber' },
{ label: 'seq_metadata_list', detail: 'Sequence context view consumed by Worker to assemble hardware input tensors', next: 'Launch forward', tone: 'teal' },

- **`seq_metadata_list`**: The sequence view supplied to Worker for preparing input tensors;
- **`SchedulerOutputs`**: An immutable snapshot of scheduling decisions carrying active sequence sets, token quotas, and memory operations;
- **`WorkerStepState`**: A preserved execution artifact bundling sequence metadata, scheduler outputs, sampler outputs, CUDA events, and graph dimensions.

In synchronous execution, these structures share a lifecycle; under asynchronous scheduling, `WorkerStepState` survives across step boundaries to form an execution pipeline.

## 3. Zero-Overhead Scheduling and Overlap Mechanics

Conventional autoregressive decoding steps follow `Schedule → Forward → Sample → Post-process`. Because post-processing depends on sampling results, CPU and GPU run in serial lockstep, leaving accelerators idle while host software handles scheduling.

The `execute_model_step()` method in [worker/worker.py](https://github.com/deepseek-ai/DeepInfer/blob/main/deepinfer/worker/worker.py) implements Zero-Overhead Scheduling (ZOS):

<ZosPipelineOverlapExplorer />

### Cross-Step State Correction and Source Pipeline

ZOS hides host overhead by **deferring decode post-processing into the execution shadow of the next forward pass**:

```python
# deepinfer/worker/worker.py: execute_model_step() async pipeline core
# 1. Launch forward pass for step N+1 (accelerator begins execution)
main_model_output = self.model_runner.execute_main_model(
    seq_metadata_list, self.gpu_cache, metadata_zos=metadata_zos, total_q=total_q
)

# 2. Concurrently process previous step output on host during accelerator execution
if self.is_driver_worker and not is_placeholder and prev_step_state is not None:
    post_process_outputs = self.callbacks.post_process_fn(prev_step_state)

# 3. Launch sampling for current step
sampler_output = self.model_runner.execute_sample(
    seq_metadata_list, input_metadata, model_output, self.gpu_cache
)

# 4. Defer current state under ZOS decode; complete synchronously during prefill
if is_prompt or not envs.DEEPINFER_ZERO_OVERHEAD_SCHEDULING:
    return self.callbacks.post_process_fn(curr_step_state)
self.prev_step_state = curr_step_state
```

This shifts the boundary of when data can be safely consumed. Because step $N$ sample tokens are still traversing hardware when launching step $N+1$, CPU sequence lengths (`seqlens_q/k`) lag behind. Worker invokes `_correct_seqlens_qk()` to adjust lengths based on actual sampling results. When device-to-host (D2H) copies occur, CUDA events ensure synchronization before sampling metadata updates.

An async function signature does not guarantee complete overlap. Real-world validation requires inspecting profiler timelines to measure overlap between CPU scheduling, kernel execution, and D2H events.

## 4. CacheEngine: From Metadata to Physical Memory Layout

[worker/cache_engine.py](https://github.com/deepseek-ai/DeepInfer/blob/main/deepinfer/worker/cache_engine.py) provides `GPUCacheInterface` and `KVCacheManager` for DeepSeek-V4.1's hybrid attention architecture.

Physical memory is partitioned into distinct views based on layer configuration:
- **`ica_cache` / `ica_state`**: Key cache and state for Index Attention;
- **`ca_cache` / `ca_state`**: Key-Value cache and compression accumulators for Compressed Attention;
- **`swa_cache`**: Sliding Window Attention cache.

### Physical Block Allocation via Intrusive Doubly-Linked Lists

In the C++ scheduling core, block and state allocations are governed by [csrc/engine/block_manager.hpp](https://github.com/deepseek-ai/DeepInfer/blob/main/csrc/engine/block_manager.hpp).

Handling high-concurrency token churn exposes critical flaws in conventional STL containers like `std::list`: every insertion invokes a dynamic heap allocation (`malloc`), generating allocator lock contention and memory fragmentation within the microsecond scheduler loop. Furthermore, node addresses scattered across heap memory cause frequent CPU cache misses.

DeepInfer borrows an OS-kernel pattern (resembling Linux `list_head` and physical page frame management) by deploying an **intrusive doubly-linked list backed by a pre-allocated contiguous array with integer indices**:

```cpp
// csrc/engine/block_manager.hpp
struct Blocks {
    struct block {
        int ref_count{0}; // Reference count for prefix sharing and speculative branching
        int next{0};      // Intrusive link: array index of next free block
        int prev{0};      // Intrusive link: array index of previous free block
    };

    std::vector<block> _blocks; // Contiguous metadata array pre-allocated at startup
    int _head, _tail, _size;

    // Block 0 serves as NULL sentinel: slot 0 is excluded from active allocation
    Blocks(int _n) : _blocks(_n), _head(1), _tail(_n - 1), _size(_n - 1) {
        for (int i = 1; i < _n; ++i) {
            _blocks[i].prev = i - 1;
            _blocks[i].next = i + 1;
        }
        _blocks[_n - 1].next = 0;
    }

    int allocate() {
        int block_id = _pop_front();
        _blocks[block_id].ref_count += 1;
        return block_id;
    }

    void free(int block_id) {
        auto &block = _blocks[block_id];
        block.ref_count -= 1;
        if (block.ref_count == 0) {
            _push_back(block_id); // Returns to free list in O(1) when ref_count reaches 0
        }
    }
};
```

This architecture provides four vital performance guarantees for LLM serving:
1. **Zero Runtime Heap Allocation**: The entire `_blocks` array is provisioned during startup. Subsequent allocation and recycling operations execute purely as integer assignments with zero `malloc` or `free` syscall overhead;
2. **Compact Footprint and L2 Cache Residency**: Each `block` node occupies only 12 bytes (16 bytes aligned). Managing 20,000 physical blocks (spanning dozens to hundreds of GB of VRAM) demands merely ~320 KB of metadata, allowing the **entire free list to permanently reside in CPU L2 cache (typically 1-2 MB)** without cacheline eviction;
3. **Deterministic $O(1)$ Direct Lookup without Hash Tables**: The `block_id` acts directly as an array index into `_blocks`, bypassing `std::unordered_map` hash calculations. Removal (`_erase`) and insertion (`_push_back`) complete in atomic time;
4. **Native Prefix Sharing and Reference Counting**: Built-in `ref_count` tracking permits multiple concurrent requests to safely reference shared prompt prefixes without duplicate memory assignments.

Estimating memory requirements by multiplying layers by nominal token size is inadequate. Multiple low-level helpers enforce hardware alignment rules:

- `_kv_bytes_per_token()`: Computes bytes for interleaved KV data and scaling factors with dimension alignment checks;
- `_get_qk_topk_bytes()`: Calculates packed FP4 bytes and UE8M0 scale metadata for the indexer;
- `_state_bytes()`: Calculates FP32 state buffer allocation shaped as `[num_state_token, 2, head_dim]`;
- **Hardware alignment constraints**: DeepGEMM index block strides require 128-byte physical alignment; internal offsets enforce 32-byte alignment. Padding must be included;
- **Cross-layer sharing**: Layers sharing parameters via `layer_kv_map` or `layer_index_module_map` reuse previous offsets without allocating redundant memory. Pure SWA layers allocate 0 bytes for standard KV.

### Why SWA Memory Exceeds Window Dimensions

The codebase defines two explicit sizing functions:
1. `get_inference_swa_block_size(window_size)`: Extends the base window by `DEEPINFER_MAX_BACKTRACKING_TOKENS` (speculative decoding rollback buffer);
2. `get_kvstore_swa_block_size(window_size)`: Adds persistence padding and YOCO truncation slack to the inference size.

Storage granularity `KVSTORE_GRAIN` is set to 128 tokens; persistent storage writes only at 128-token boundaries. When prefill ends unaligned, buffers must retain uncommitted tokens. Sizing buffers purely on window length risks memory corruption during rollback or truncation.

## 5. SWA Bounded Replay and State Truncation Semantics

Under DeepSeek-V4.1's YOCO design, decoder layers dispense with full causal self-attention. Global context is projected from top-level encoder hidden states, reducing decoder self-attention to local sliding windows.

<SwaBoundedReplayExplorer />

**Bounded replay is not simply discarding cache outside the window.**

Safe state restoration requires three contracts:
1. **Replay anchor alignment**: Replay computation truncates to the nearest 128-token boundary, restricting query vectors to a bounded range for constant-time recovery;
2. **State ring buffer consistency**: YOCO consumer layers separate SWA memory into retained and dropped sections. Dropped sections reconstruct via forward recomputation, while retained sections must cover both window length and speculative backtracking;
3. **Boundary decoupling**: Compression boundaries align to 128-token multiples, preventing recurrence dependencies across windows.

Evaluating prefix caching benefits without accounting for SWA recomputation overhead overestimates real-world throughput gains.

## 6. DSpark Speculative Decoding and State Rollback

DeepInfer incorporates DSpark variable-length speculative verification. ModelRunner allocates a dedicated `DFlashCudaGraphRunner` for the draft prediction head.

### Confidence-Scheduled Verification Budgets

Fixed draft verification lengths (e.g. verifying exactly 5 tokens per step) waste accelerator cycles when acceptance likelihood varies across tokens.

DSpark predicts draft token acceptance probability via a Confidence Head. During scheduling, TileLang kernels compute cumulative products and sort candidate tokens on the GPU. The scheduler dynamically selects token subsets with the highest expected throughput gain (averaging 3.2 to 4.4 tokens), delivering a 4% to 11% throughput increase in production.

### State Progression and Rollback Chains

`_process_model_outputs()` hands accepted tokens, draft tokens, and confidence scores to native `process_MTPInfo()`, which calls `Scheduler.process_outputs()` to advance sequences.

When draft tokens are rejected by verification, the pipeline rolls back:
- Sequence length truncates to the last accepted token;
- KV Cache and state buffers restore from `max_backtracking_tokens` history;
- Grammar matchers rollback state to prevent downstream divergence.

## 7. Structured Output: Asynchronous Compilation and Matcher Rollback

High-throughput serving requires constraining model output to JSON Schema, Regex, or EBNF grammars. DeepInfer handles this in [structure_output/so_matcher_builder.py](https://github.com/deepseek-ai/DeepInfer/blob/main/deepinfer/structure_output/so_matcher_builder.py) and [matcher.py](https://github.com/deepseek-ai/DeepInfer/blob/main/deepinfer/structure_output/matcher.py).

### Decoupled Grammar Compilation

Compiling schemas into deterministic finite automata (DFAs) is CPU-intensive:
1. `XGrammarCompiler` runs in a background thread pool without blocking scheduling;
2. `pump()` polls futures without blocking; ready matchers bind to sequences and enter the Scheduler;
3. Prior to sampling, `matcher.fill_vocab_mask()` applies a bitmask based on DFA state to eliminate invalid logits.

### State Consistency Under Matcher Rollback

When combining speculative decoding with structured output, state consistency becomes critical:
- If a draft model predicts multiple tokens, the matcher advances through DFA states;
- If verification rejects an intermediate token, the sequence truncates;
- If the matcher fails to invoke `rollback()`, its grammar state points to an invalid branch, generating invalid bitmasks and corrupting output.

Matcher rollback is not defensive cleanup; it is a mathematical prerequisite for combining speculative decoding with grammar-constrained generation.

## 8. Source-Level System Review Guidelines

When auditing or optimizing DeepInfer deployments, apply these source-grounded verification principles:

1. **Async dispatch does not equal zero idle time**: Inspect profiler timelines for D2H sync, CPU schedule duration, and device execution;
2. **Cache views do not represent distributed storage**: `CacheEngine` manages device memory buffers, which operate at a different layer than production 3FS distributed storage clusters;
3. **Finite SWA windows do not allow arbitrary history purging**: Rollback slack, 128-token alignment, and compression accumulators set lower bounds on buffer sizes;
4. **Draft token volume does not directly translate to net speedup**: Confidence verification cost, rejection rates, and rollback overhead determine actual performance;
5. **Memory capacity is not a scalar calculation**: CUDA Graph memory footprints, alignment padding, and mixed-precision scaling factors all dictate maximum allocation blocks.

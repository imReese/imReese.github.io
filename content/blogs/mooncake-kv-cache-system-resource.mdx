这组文章的目标不是介绍 Mooncake 有多快，而是回答一个工程问题：**一段 prefix 的 KV Cache，怎样从单个 worker 的 GPU tensor，变成可以降级、查询、搬运、跨节点复用的系统资源。**

要把这条链路讲清楚，需要同时看三层：

```text
SGLang HiCache
  负责 prefix cache、GPU/Host/Storage tier 状态、调度时机

Mooncake Store
  负责 object、slice、replica、lease、metadata、可读性判断

Mooncake Transfer Engine
  负责 Segment、registered memory、BatchTransfer、transport 数据搬运
```

这三层经常被一句“把 KV Cache 放到 Mooncake”糊在一起。实际读源码时必须拆开，否则很容易把 Store 当普通 KV 服务，或者把 Transfer Engine 当完整缓存系统。

## 先定义三层边界

HiCache 是 SGLang runtime 内部的缓存层级机制。它知道 request、prefix、radix node、token indices、GPU KV pool、Host KV pool，也知道调度器什么时候应该 prefetch 或 load back。它的核心边界在 SGLang 代码里，SGLang `v0.5.14` 主要入口包括：

```text
python/sglang/srt/mem_cache/hicache_storage.py
python/sglang/srt/mem_cache/unified_radix_cache.py
python/sglang/srt/mem_cache/hiradix_cache.py
python/sglang/srt/mem_cache/storage/mooncake_store/mooncake_store.py
```

Mooncake Store 是对象/副本语义层。它不知道 SGLang 的 radix tree，也不决定某个请求是否能跳过 prefill。它看到的是 object key、slice、replica、Segment、状态和 lease。Mooncake 侧主要入口是：

```text
mooncake-store/include/client_service.h
mooncake-store/src/client_service.cpp
mooncake-store/src/master_service.cpp
mooncake-store/include/replica.h
mooncake-store/include/types.h
```

Mooncake Transfer Engine 是数据搬运层。它不理解 KV Cache，也不理解 object 是否可读。它处理的是本地地址、远端 Segment、offset、length、READ/WRITE、BatchID 和 transport。主要入口是：

```text
mooncake-transfer-engine/include/transfer_engine.h
mooncake-transfer-engine/include/transport/transport.h
mooncake-transfer-engine/src/transfer_engine_impl.cpp
mooncake-transfer-engine/src/multi_transport.cpp
```

## 一段 KV Cache 的生命周期

从 SGLang 角度看，一段可复用 prefix 会经历几种状态：

```text
GPU KV pool
  -> Host KV pool
  -> HiCacheStorage backend
  -> Mooncake Store object
  -> Mooncake replica on Segment
  -> Transfer Engine transport path
```

反向读取时顺序也不是直接从 Mooncake 回 GPU：

```text
Mooncake Store object
  -> zero-copy get into Host KV pool
  -> HiCache load_back
  -> GPU KV pool
  -> attention kernel 使用 device KV slots
```

这条路径说明两个事实。

第一，HiCache 的 L3 backend 不直接替代 GPU cache。它只是让已经离开 GPU 的 KV Cache 仍然有机会被找回。真正参与 attention kernel 的仍然是 GPU KV slots。

第二，Mooncake Store 存的不是“一个请求”，而是 SGLang 按 page 组织出来的 cache object。MHA 通常会拆成 K/V 两类 object，MLA 又是另一套 key 和 buffer 组织方式。

## 为什么不能只看 Store 或只看 Transfer Engine

Store 解决的是“这份数据是否存在、在哪里、能不能读”。它需要维护：

- object key 到 metadata 的映射
- object 被拆成哪些 slice
- 每个 replica 的 Segment、offset、length
- replica 是 `PROCESSING`、`COMPLETE` 还是已经移除
- client 拿到的 metadata lease 什么时候失效

Transfer Engine 解决的是“知道远端地址以后，字节怎么过去”。它需要处理：

- local memory 是否已经 register
- remote Segment 是否 open
- 这批 transfer 是 READ 还是 WRITE
- 该走 TCP、RDMA、EFA、NVLink 还是其他 transport
- BatchID 的生命周期和 transfer status

如果只看 Store，会知道对象语义，但不知道大块 KV 数据怎么跨节点搬。如果只看 Transfer Engine，会知道数据怎么搬，但不知道为什么这些 bytes 是可读的。完整理解必须把两边接上。

## HiCache 把缓存问题变成状态机

普通 prefix cache 里，radix node 的 `value` 指向 GPU KV indices。命中就复用，没命中就计算。

HiCache 多了一层状态：

```text
value             GPU KV indices
host_value        Host KV indices
hash_value        L3 storage page keys
backuped          是否已经有 Host 备份
backuped_storage  是否已经写到 L3
lock_ref          GPU 侧引用保护
host_ref_counter  Host 侧引用保护
```

因此 prefix match 不再只是“命中了多少 token”，而是要区分：

```text
哪些 token 已经在 GPU
哪些 token 只在 Host
哪些 token 可能在 Storage
哪些 token 需要重新 prefill
```

这就是 HiCache 与 Mooncake Store 接起来的原因。HiCache 负责把 prefix cache page 化、hash 化、调度化；Mooncake Store 负责让这些 page 在分布式环境中可查询、可传输、可复用。

## 一个实用读法

后续章节可以按这个顺序读：

1. HiCache 总览和写路径，先理解 SGLang 为什么需要 L1/L2/L3。
2. HiCache 读路径，理解 prefetch 和 load back 怎么进入调度。
3. Mooncake Store 对象模型，理解 object、slice、replica、lease。
4. Store Put/Get，理解 metadata 控制面和数据面如何分离。
5. Transfer Engine，理解 Segment、memory registration、BatchTransfer。
6. SGLang 到 Mooncake Store 串联篇，把 page key 和 zero-copy batch API 接起来。
7. 排障验证篇，确认 remote KV 是否真的命中。

读完以后，应该能画出一段 prefix KV Cache 从 GPU 写到远端、再从远端读回 GPU 的完整路径，并知道每个阶段该去哪个源码文件里验证。

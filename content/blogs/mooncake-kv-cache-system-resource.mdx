Mooncake 最吸引我的地方，不是它又支持了一个新的 transport，也不是 README 里那些很大的系统词，而是它把一个原本很局部的东西往系统资源的方向推了一步：KV Cache。

在普通的推理实现里，KV Cache 很容易被理解成某个 worker 进程里的 tensor 状态。一次 request 进来，prefill 算出一批 K/V，decode 继续消费它。这个视角在单机、单进程、短上下文里够用；但到了长上下文、多轮请求、prefill/decode 分离和多节点 serving，KV Cache 就不再只是“模型内部中间结果”了。

它开始像一类资源：

- 它很贵，算出来不想轻易丢。
- 它很大，不能都塞在 GPU 上。
- 它有位置，可能在某个 worker、某段 DRAM、某块 SSD 或远端节点上。
- 它有复用价值，但是否值得搬回来要看传输成本和 recompute 成本。
- 它有正确性边界，不能拿一个还没写完、已经过期或被覆盖的副本来读。

所以 Mooncake 的问题不是简单的“远端拷贝一段内存”。更准确地说，它在问：**KV Cache 能不能被命名、查询、复制、搬运，并被上层 serving 系统当成可调度的资源？**

## 为什么要分成 Store 和 Transfer Engine

我现在理解 Mooncake，最重要的分界线是 Store 和 Transfer Engine。

Store 解决的是对象语义。它关心 key 是什么，一个 object 被切成几个 slice，有几个 replica，每个 replica 在什么状态，master 什么时候允许读，写入失败时怎么撤销，租约边界在哪里。

Transfer Engine 解决的是数据搬运。它不关心 key，不关心这个 object 是 KV Cache、tensor 还是普通 buffer。它关心的是本地地址、远端 Segment、offset、length、READ/WRITE、batch status，以及到底走 TCP、RDMA、EFA、NVLink、HIP 还是其他 backend。

放在一起看，大概是这样：

```text
上层框架 / Python API
  -> Mooncake Store
       key / slice / replica / metadata / lease
  -> TransferSubmitter
       把 replica 读写翻译成传输任务
  -> Transfer Engine
       Segment / registered memory / BatchTransfer
  -> transport backend
       TCP / RDMA / EFA / NVLink / HIP / Sunrise Link / ...
```

这个分层很关键。因为如果没有 Store，Transfer Engine 只是一个跨节点传输库；如果没有 Transfer Engine，Store 只能停留在元数据和对象语义层，真正的大块数据还是搬不动。

Mooncake 的工程价值就在这个交界处：上层看见的是一个可以 Put/Get 的对象系统，底层实际执行的是对远端内存段的批量读写。

## Master 不应该在数据面

读 Store 的时候，一个很容易误解的地方是 master。

master 很重要，但它不是数据面中转站。它主要维护对象元数据、Segment 信息、副本状态和租约。Put 时，client 先问 master：这个 key 应该写到哪些 replica 上。Get 时，client 先问 master：这个 key 现在有哪些完整可读的 replica。

真正的数据搬运发生在 client 侧。

```text
Put:
  client -> master: PutStart
  master -> client: allocated replicas
  client -> TransferSubmitter / Transfer Engine: write data
  client -> master: PutEnd or PutRevoke

Get:
  client -> master: GetReplicaList
  master -> client: completed replicas + lease
  client -> TransferSubmitter / Transfer Engine: read data
```

这个设计有一个很朴素的好处：metadata 控制面和大块数据路径不会挤在一起。master 决定“哪些副本存在、哪些副本可读、哪些写入完成”，client 和 Transfer Engine 负责“数据怎么过去”。

对 KV Cache 这种大对象来说，这个边界比看起来更重要。因为一旦 master 变成数据面，它就会被带宽、复制和大块内存拷贝拖住；而如果没有 master 这样的事实表，client 又很难判断哪些远端状态是安全可读的。

## KV Cache 变成资源以后，多了什么问题

把 KV Cache 当成本地 tensor 时，很多问题不需要显式表达。对象在内存里，生命周期跟 request 走，读写顺序由进程内部保证。

但当 KV Cache 被放进 Store，事情会变复杂：

- 一个 key 可能对应多个 slice。
- 一个 object 可能有多个 replica。
- replica 有 `PROCESSING`、`COMPLETE`、`REMOVED` 这样的状态。
- 写入不是一个瞬间动作，而是 `PutStart`、数据传输、`PutEnd` 的组合。
- 读取不是只看 key 是否存在，还要看有没有 complete replica，以及 lease 是否仍然有效。
- 传输不一定都走同一路径，本地可能 memcpy，远端可能走 Transfer Engine，冷数据可能走 file 或 NoF。

这些东西看起来琐碎，但它们正是“系统资源”和“进程局部变量”的区别。

系统资源必须能被描述、被发现、被并发访问、被失败恢复，也必须能解释自己的状态。KV Cache 一旦跨进程、跨节点，就不能只靠“那块 tensor 还在不在”来判断是否可用。

## Store 和 Transfer Engine 的边界，是理解 Mooncake 的主线

所以我不太把 Mooncake 理解成一个单点功能，比如“KV Cache offload”或者“RDMA transfer”。这些都只是它的一部分。

更合适的理解是：

- Store 把 KV Cache 组织成对象、副本和元数据。
- Transfer Engine 把远端内存访问组织成可提交、可轮询、可选择 transport 的传输任务。
- Python binding 和框架集成把这些能力接回 LLM serving 系统。

这也是为什么读 Mooncake 时，如果一开始只盯 transport，很容易陷进 RDMA/NVLink/Sunrise Link 细节；如果只盯 Store，又会觉得很多 API 只是在搬元数据。真正的主线是：**一个 KV Cache 对象如何被命名、分配、写入、确认、查询、读取，并在必要时跨节点移动。**

一旦这条线清楚了，Mooncake 的各个模块就不再是一堆名词，而是一套把 KV Cache 系统化的分层设计。

Mooncake Transfer Engine 解决的问题很窄：**给定本地 buffer、远端 Segment、offset 和 length，如何把一批 bytes 可靠地搬过去或读回来。**

它不理解 object key，不判断 replica 是否 COMPLETE，也不知道这段数据是不是 KV Cache。这些都是 Store 或上层框架的职责。

核心入口：

```text
mooncake-transfer-engine/include/transfer_engine.h
mooncake-transfer-engine/include/transport/transport.h
mooncake-transfer-engine/src/transfer_engine_impl.cpp
mooncake-transfer-engine/src/multi_transport.cpp
```

## TransferEngine 的公开 API

Transfer Engine 的公开接口可以分成几类：

```text
init / freeEngine
installTransport / uninstallTransport / getTransport
openSegment / closeSegment / removeLocalSegment
registerLocalMemory / unregisterLocalMemory
allocateBatchID / freeBatchID
submitTransfer
getTransferStatus / getBatchTransferStatus
```

这些 API 说明它不是 KV store。它处理的是内存注册、Segment 发现和批量传输任务。

## Segment 是远端可寻址空间

传输任务不能只写 “remote ptr”。跨进程、跨机器时，本地进程不能直接相信远端虚拟地址。Transfer Engine 先通过 `openSegment(segment_name)` 得到 `SegmentHandle`。

Store 侧的 Segment metadata 会告诉 client：

```text
segment id
segment name
base
size
te_endpoint
protocol
```

Transfer Engine 侧拿到 Segment 后，传输任务才能表达：

```text
target_id
target_offset
length
```

也就是说，Store 的 replica 描述会被压成 Transfer Engine 的 Segment + offset + length。

## registerLocalMemory 是数据面的前置条件

很多 transport 不能直接拿任意 malloc 出来的地址做高速传输。RDMA、GPU P2P、NVLink、EFA 等路径通常需要 pin memory、注册 MR、生成 key 或建立映射。

因此 Transfer Engine 暴露：

```text
registerLocalMemory(addr, length, location, remote_accessible, update_metadata)
unregisterLocalMemory(addr)
registerLocalMemoryBatch(...)
```

这一步的意义是：告诉 Transfer Engine 这段本地 buffer 可以参与传输。

SGLang 接 Mooncake Store 时，Mooncake backend 会注册 Host KV pool。之后 `batch_get_into` 和 `batch_put_from` 才能把 Host KV page pointer 直接交给 Store/TE，不需要把数据拷成 Python bytes。

## TransferRequest 是最小传输语义

Transfer Engine 的核心请求可以简化为：

```text
TransferRequest
  opcode: READ | WRITE
  source: local buffer address
  target_id: remote Segment id
  target_offset: offset inside remote Segment
  length: bytes
```

READ 和 WRITE 的区别在于数据方向：

```text
READ:
  remote Segment -> local source buffer

WRITE:
  local source buffer -> remote Segment
```

字段名 `source` 需要按 Transfer Engine 语义理解：它是本地 buffer 地址。具体方向由 opcode 决定。

## BatchID 和批量任务

Transfer Engine 不鼓励每个小对象都单独同步传输。它使用 BatchID 表达一组 transfer request：

```text
BatchID id = allocateBatchID(batch_size)
submitTransfer(id, requests)
getBatchTransferStatus(id, status)
freeBatchID(id)
```

这对 KV Cache 很重要。一个 prefix 可能有大量 page，每个 page 又可能拆成 K/V object。如果每个 object 都独立提交，会被提交开销和轮询开销淹没。

BatchTransfer 的目标是把许多小传输组织成一批，让 transport 层统一调度和查询状态。

## TransferStatus 不是对象状态

Transfer Engine 的状态是数据面状态：

```text
WAITING
PENDING
COMPLETED
TIMEOUT
FAILED
CANCELED
```

这些状态只说明传输任务完成没有，不说明 Store object 是否可读。

例如 Put 路径中，WRITE transfer 成功以后，Store 仍然需要 PutEnd 把 replica 提交为 COMPLETE。反过来，Get 路径中，如果 master 返回 COMPLETE replica，但 READ transfer 失败，上层仍然不能使用数据。

因此要区分：

```text
TransferStatus:
  bytes 是否搬完

ReplicaStatus:
  object replica 是否可读
```

## Transfer Engine 在 Store Put/Get 中的位置

Put 时：

```text
Store replica
  -> TransferSubmitter
  -> TransferRequest(WRITE)
  -> TransferEngine.submitTransfer
  -> transport
```

Get 时：

```text
Store replica
  -> TransferSubmitter
  -> TransferRequest(READ)
  -> TransferEngine.submitTransfer
  -> local slices filled
```

Store 负责 object/replica/lease；Transfer Engine 负责 bytes。这个边界不应该混。

## 为什么这层要独立出来

如果 Store 自己直接实现 RDMA/TCP/NVLink/EFA，每加一种 backend 都会污染 object 语义层。

Transfer Engine 独立出来以后，Store 只需要表达：

```text
把 slice 写到 replica
从 replica 读到 slice
```

底层到底走哪个 transport，由 Transfer Engine 和 MultiTransport 处理。

这让 Mooncake 能同时支持多种部署形态：本地开发可以 TCP，生产可能 RDMA/EFA，同机多卡可能 NVLink，异构硬件还有其他 backend。

## 看 Transfer Engine 时要确认什么

- Transfer Engine 为什么不需要知道 object key？
- Segment + offset + length 如何从 Store replica 推导出来？
- `registerLocalMemory` 防的是什么成本或限制？
- `TransferStatus.COMPLETED` 为什么不等于 Store object 可读？
- BatchID 对 KV Cache page 传输有什么价值？

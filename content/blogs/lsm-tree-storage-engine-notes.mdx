LSM Tree 最容易被一句“写入快”讲扁。

更准确的说法是：LSM Tree 把随机原地更新改成顺序追加和后台整理。前台写入变轻了，但代价没有消失，而是转移到 read amplification、write amplification、space amplification、compaction debt 和 write stall 上。

我现在更愿意沿着一个 key 的生命周期看 LSM，而不是按名词背 memtable、SSTable、compaction。

```text
write key=a
  -> WAL records intent
  -> memtable holds latest version
  -> flush creates L0 SSTable
  -> compaction moves it down levels
  -> later update/delete creates newer versions
  -> old versions are removed only when safe
```

这条线能解释 LSM 为什么快，也能解释它为什么会突然慢。

## 前台写入只做能快速确认的事

一次写入通常会被拆成两步：

```text
append WAL
  -> insert into memtable
```

WAL 是恢复边界。memtable 是查询边界。只要 WAL 策略允许，前台不需要去磁盘上找到旧 value 的位置，也不需要更新某个 B+Tree page。它追加日志，再把新版本放进内存结构。

这就是 LSM 的写入优势。

但这个优势建立在一个前提上：后面有人会收拾旧版本。否则系统只是把垃圾堆到了未来。

## SSTable 的不可变性让后台整理变得可控

memtable 满了以后会变成 immutable memtable，然后 flush 成 SSTable。SSTable 写出后不再原地修改。

不可变文件有几个工程好处：

- 读线程不需要担心文件内容被改。
- 文件可以带 block index、filter block、range metadata。
- compaction 可以写新文件，再通过 manifest/version edit 原子切换。
- 崩溃恢复时可以靠文件编号、校验、manifest 判断哪些文件有效。

代价是更新不会覆盖旧值。

```text
seq=30 key=a value=v3  in L0
seq=20 key=a value=v2  in L1
seq=10 key=a value=v1  in L3
```

读路径必须找当前 snapshot 可见的最新版本。删除也一样，只是写入一个更新的 tombstone，而不是立刻从所有低层文件里抹掉旧值。

## L0 是 LSM 的交通事故现场

L0 和其它层不同。flush 出来的文件直接进入 L0，不同文件的 key range 可能互相重叠。

这对 point lookup 很不友好。低层如果 range 不重叠，系统可以根据 key range 快速定位少数文件；L0 重叠时，一个 key 可能需要查多个 L0 文件。

```text
L0:
  file A: key range [a, z]
  file B: key range [b, y]
  file C: key range [a, m]

lookup key=k
  -> A/B/C may all need checking
```

所以 L0 file count 是很重要的健康信号。它升高时，通常说明 flush 速度大于 compaction 消化速度，后面可能出现：

- point lookup 变慢。
- bloom/filter/index 查询次数增加。
- compaction 被迫更激进。
- write stall 开始出现。

LSM 的很多 tail latency 毛刺，不在写入入口，而在 L0 backlog。

## compaction picker 决定系统在还哪笔债

Compaction 不是简单后台 merge。它要先决定还哪笔债。

一个 compaction picker 通常会考虑：

- L0 文件数量。
- level size 是否超过目标。
- 文件 range 是否和下一层重叠。
- tombstone 是否有机会清掉。
- compaction score。
- 是否有正在运行的 compaction。
- trivial move 是否可行。

被选中的文件会进入 merge iterator：

```text
input files from level N
  + overlapping files from level N+1
  -> merge by key + sequence number
  -> keep newest visible version
  -> drop obsolete versions
  -> output new SSTables
  -> install manifest edit
```

这里最关键的是“visible”。如果还有 snapshot 需要旧 sequence number，compaction 不能把旧版本随便删掉。

这也是为什么快照、长 iterator、事务读会影响 compaction 回收。旧 reader 越久，旧版本和 tombstone 越难清。

## tombstone 是删除事实，不是空间回收

LSM 删除一个 key，通常写 tombstone：

```text
seq=40 key=a tombstone
seq=30 key=a value=v3
seq=20 key=a value=v2
```

读路径看到可见 tombstone，就认为 key 不存在。但磁盘空间未必立刻下降。只有 compaction 确认低层旧值都被覆盖，并且没有 snapshot 需要旧版本时，tombstone 和旧 value 才能一起丢。

大量 delete-heavy workload 的危险就在这里：

- tombstone 本身增加写入。
- point lookup 可能一路查到 tombstone。
- range scan 要跳过大量删除标记。
- 空间回收依赖 compaction 是否及时。

所以“删除了很多数据，磁盘为什么没降”不是 bug 的第一嫌疑，先看 compaction 是否走到了能清 tombstone 的层级。

## 三个放大是同一个账本的不同列

LSM 的代价常被分成三个放大：

```text
write amplification:
  user write bytes -> actual disk write bytes

read amplification:
  one logical read -> multiple structures/files/blocks

space amplification:
  logical live data -> physical bytes on disk
```

它们不是孤立指标。

更 aggressive 的 leveling 可以降低读放大和空间放大，但会提高写放大。更 lazy 的 tiering 可以降低写放大，但读路径和空间占用会更重。

```text
leveling:
  lower read amplification
  lower space amplification
  higher write amplification

tiering:
  lower write amplification
  higher read amplification
  higher temporary space amplification
```

所以 LSM 参数不能离开 workload 讨论。写多读少、读多写少、range scan 多、TTL/tombstone 多，对应的最优点完全不同。

## write stall 是后台债务影响前台的时刻

LSM 的设计看起来把 compaction 放到了后台，但后台债务最终会回到前台。

常见触发包括：

- memtable 太多，flush 追不上。
- L0 文件数超过 soft/hard threshold。
- pending compaction bytes 过高。
- 磁盘空间不足。
- 后台 I/O 被限速或抢占。

这时系统会减慢甚至暂停写入，让 compaction 追债。

```text
foreground writes
  -> generate WAL + memtable
  -> flush creates L0
  -> compaction cannot catch up
  -> L0 grows
  -> write stall
```

所以线上看 LSM，不要只看 QPS 和平均延迟。至少要看 L0 files、pending compaction bytes、stall micros、flush/compaction throughput、block cache hit rate。

## 我会怎么读一个 LSM 实现

读 RocksDB/LevelDB 这类实现时，我会按生命周期找入口：

```text
write path:
  DBImpl::Write / WriteBatch
  WAL writer
  memtable insert

flush path:
  immutable memtable
  table builder
  L0 file install

read path:
  memtable lookup
  version / file picker
  bloom filter
  block cache
  iterator merge

compaction path:
  compaction picker
  merge iterator
  output table builder
  version edit / manifest

recovery path:
  CURRENT
  manifest replay
  WAL replay
  obsolete file cleanup
```

具体函数名会随实现变化，但边界不会变：谁把写入变成可恢复事实，谁把内存变成不可变文件，谁把旧文件替换成新版本，谁在崩溃后确认当前历史。

## LSM 的核心不是写入快，而是债务管理

LSM Tree 的前台写入路径很克制：append WAL，更新 memtable，尽快返回。

真正决定系统能不能长期稳定的，是后台能否持续还债：L0 能不能压住，旧版本能不能清掉，tombstone 能不能回收，compaction 能不能在不打爆前台 tail latency 的情况下推进。

写入快只是第一眼。债务管理才是 LSM 的工程核心。

做存储系统 benchmark 时，平均延迟是最容易骗人、也最容易被拿来讲故事的指标。

一个系统平均延迟很好看，但 p99 有毛刺，线上体验仍然可能很差。尤其是存储系统，后台 compaction、flush、GC、page cache、I/O 调度都会把延迟拉出长尾。

所以我现在看 benchmark，会先问：

```text
测的是什么 workload？
数据集是否大于缓存？
有没有预热？
测的是 steady state 还是刚启动的蜜月期？
看平均值，还是看 p95/p99/p999？
后台任务是否已经进入稳定状态？
```

如果这些问题没有答案，benchmark 数字再漂亮也只能先放一边。

## Workload 先于指标

Benchmark 不是先选工具，而是先定义 workload。

存储系统里最基本的维度包括：

- read / write 比例。
- point lookup / range scan 比例。
- key 分布是 uniform 还是 Zipfian。
- value size。
- 数据集大小。
- 并发数。
- 请求是否有 burst。
- 是否有 delete / update。
- 是否有 snapshot 或 long iterator。

不同 workload 下，同一个系统可能表现完全不同。

比如 LSM 对写入友好，但 range scan、delete-heavy workload、热点读、超大 value 都会触发不同瓶颈。只测一个 `readwrite` 混合比例，然后得出“系统 A 比系统 B 快”，意义很有限。

## 数据集大小决定你测到什么

如果数据集完全落在内存里，你可能测到的是 block cache 或 page cache，而不是磁盘路径。

这不是说内存命中不重要。很多真实系统确实依赖缓存。但 benchmark 必须说明自己测的是：

```text
cache hit workload
cache miss workload
mixed workload
```

我会特别留意两件事：

第一，数据集是否大于内存。

第二，测试前是否 drop cache 或者明确 warm up。

如果没有预热，刚开始的数据可能很差；如果预热过度，结果又可能过于理想。更好的做法是把预热阶段和正式统计阶段分开，并在报告里说明。

## Steady state 很重要

LSM 系统尤其容易出现“刚开始很好看，跑久了变慢”。

刚开始没有太多历史文件，compaction debt 不高，空间也充足。写一段时间后，L0 堆积、compaction 追赶、旧版本和 tombstone 增多，系统才进入真正状态。

所以我会关心：

- 测试前是否先装载足够数据。
- 正式压测持续多久。
- compaction 是否已经稳定。
- 磁盘空间是否在持续上涨。
- 写入速率是否超过后台整理能力。

一个短时间 benchmark 可能只测到了 buffer，而不是系统长期能力。

## 平均延迟不够

我会至少看这些指标：

```text
throughput
avg latency
p50
p95
p99
p999
max
error rate
```

平均值可以说明总体效率，但 tail latency 才能暴露后台任务、锁竞争、I/O 抖动、调度延迟。

比如：

```text
avg: 2 ms
p99: 80 ms
p999: 1.2 s
```

这个系统对很多在线服务来说已经很危险。平均值没问题，但用户会遇到明显卡顿。

存储系统的毛刺常见来源包括：

- WAL fsync。
- memtable flush。
- compaction。
- cache miss。
- block cache eviction。
- 文件系统抖动。
- 云盘 I/O credit。
- CPU 抢占。

所以 benchmark 报告里只给平均值，基本不够。

## 吞吐和延迟要一起看

吞吐提升不一定代表系统更好。

很多系统在低负载下延迟很低，随着并发增加，吞吐上升，但尾延迟也开始恶化。到了某个点以后，吞吐继续涨一点，p99 可能暴涨。

我更喜欢画这样的曲线：

```text
x-axis: offered load / concurrency
y-axis: throughput + p99 latency
```

这样能看到系统的 knee point。也就是从“还能稳定服务”到“开始排队失控”的拐点。

线上容量规划时，这个拐点比峰值吞吐更重要。因为服务不应该长期跑在快崩的边缘。

## 资源隔离要说清楚

Benchmark 环境里的资源隔离经常被忽略。

至少要说明：

- CPU 核数和频率。
- NUMA 拓扑。
- 内存大小。
- 磁盘类型和队列深度。
- 文件系统。
- 是否容器化。
- 是否和别的任务共享机器。
- 云盘类型、IOPS、带宽、burst credit。

云环境里尤其要小心。不同实例类型、不同云盘规格、同一规格不同时间段，都可能有差异。云盘还可能有 credit 或后台限流机制，短测看不出来，长测才暴露。

如果 benchmark 结果要给别人复现，环境描述就是结果的一部分。

## 写放大也应该进报告

对 LSM/存储引擎来说，只看用户吞吐不够。

我会尽量观察：

- 用户写入字节。
- 实际磁盘写入字节。
- compaction read/write 字节。
- WAL 写入字节。
- 空间放大。
- L0 文件数量。
- pending compaction bytes。

如果用户写入 100GB，磁盘实际写了 900GB，那系统吞吐背后有很重的后台成本。这个成本会影响 SSD 寿命、云盘费用、tail latency 和长期稳定性。

写放大不是一个学术指标，它会直接变成钱和故障。

## Benchmark 工具不等于方法

工具很重要，比如 fio、sysbench、YCSB、db_bench、自写压测器。但工具不能替代方法。

我会警惕几种情况：

- 工具默认参数和真实 workload 差很多。
- key/value size 没对齐业务。
- 只测单线程或只测极限并发。
- client 和 server 在同机导致资源互相干扰。
- 压测器自己先成为瓶颈。
- 没有记录错误和超时。

一个好的 benchmark，要能说清楚“为什么这样测”。否则只是跑了一个程序，拿到一串数字。

## 我会怎样写 benchmark 报告

我希望报告至少包含这些部分：

1. 目标：这次想回答什么问题。
2. 环境：机器、磁盘、系统、配置。
3. Workload：读写比例、数据规模、key 分布、value size。
4. 方法：预热、正式运行时长、并发、采样方式。
5. 结果：吞吐、延迟分位、错误率。
6. 资源：CPU、内存、I/O、网络。
7. 后台状态：compaction、GC、队列、空间增长。
8. 结论：适用范围和不适用范围。

最重要的是最后一项。Benchmark 不是证明“我赢了”，而是说明“在这些条件下，这个系统表现如何；换条件后不保证同样结论”。

## Benchmark 要留下证据

benchmark 不是一个数字，而是一组证据。平均延迟是证据之一，但远远不够。真正有用的 benchmark，应该能解释系统在什么负载下稳定，什么时候开始失控，以及为什么失控。

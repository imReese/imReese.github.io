Mooncake Store 的主路径是 Put/Get，但真正容易出问题的是状态管理。大对象缓存系统最怕的不是“没有数据”，而是“读到一份看起来存在但其实不该读的数据”。

这篇只看三个状态边界：

```text
Replica lifecycle
Metadata lease
Local hot cache generation/token
```

## replica 生命周期

replica 不是一创建就可读。它有状态机：

```text
INITIALIZED
  -> PROCESSING
       -> COMPLETE
       -> REMOVED / FAILED
```

写入时，master 先为 object 分配 replica。此时 replica 只是有位置，还没有完成数据写入。client 完成数据面传输后，PutEnd 才把 replica 提交为 `COMPLETE`。

读路径只应该使用 `COMPLETE` replica。这条规则看起来简单，但它是 Store 读正确性的核心。

## PROCESSING 的意义

如果没有 `PROCESSING`，PutStart 后 metadata 里立刻出现新 replica，Get 就可能读到半写入数据。

`PROCESSING` 把写入拆成两步：

```text
控制面:
  我预留了一个位置

数据面:
  我把 bytes 写过去了

提交点:
  我确认这份 replica 可读
```

这个中间态允许 Store 处理部分失败。比如批量写入 100 个 object，其中 3 个远端传输失败，master 不应该把这 3 个 object 也标成 COMPLETE。

## lease 的作用

master 返回 replica 列表时，会给 client 一个 lease。lease 的含义是：这份 metadata view 在一个有限时间内可使用。

lease 不是为了提升性能才加的装饰字段。它限制了 client 复用旧 metadata 的时间。

没有 lease，client 可能在很久以前查到一个 replica，然后在 Segment unmount、replica 删除、master failover 之后继续拿旧地址读。这种 bug 难复现，但在分布式缓存里非常危险。

因此读路径应该理解成：

```text
GetReplicaList
  -> COMPLETE replicas + lease
  -> client 在 lease 内执行数据面读取
  -> lease 过期后重新查询
```

## local hot cache 的边界

local hot cache 是 client 本地的加速层。它可以把热对象放在本地内存里，减少远端读取。

但它不能绕过 master metadata。hot cache 的正确定位是：

```text
metadata correctness:
  master + replica state + lease

local acceleration:
  hot cache
```

如果一个 object 在 hot cache 里，但 master 已经认为它不可读，不能仅凭本地缓存命中就返回。hot cache 应该服务于已确认可读的数据路径。

## put token 防止旧写覆盖新写

hot cache 里常见的风险是异步写入乱序。

想象两个 put 几乎同时发生：

```text
put A 获取 block，准备写 key=x
put B 后来发生，也写 key=x
put B 先完成
put A 后完成
```

如果没有 token/generation 保护，A 可能把旧内容覆盖到 hot cache，导致后续读命中旧数据。

Mooncake 的 hot cache 会使用类似 put token 的机制：写入前先获取 token，真正放入 cache 时检查 token 是否仍然有效。这样过期写入不会覆盖新状态。

## eviction 与可见性

Store 中对象可能被 evict 或移除。对 remote cache 来说，eviction 不是简单 delete memory，还会影响 metadata 可见性。

应该区分：

```text
data bytes:
  某段 Segment 上的内容

metadata:
  object -> replica 的可读事实

local cache:
  client 本地加速副本
```

只有 metadata 承认的 COMPLETE replica 才是全局读路径的一部分。单纯 bytes 还在某块内存里，不代表读者可以使用。

## 和 HiCache 的关系

SGLang HiCache 只需要知道某个 logical page 是否可用。Mooncake Store 要在内部保证这个 page 对应的 object 都满足可读条件。

例如 MHA page 对应 K/V 两个 object：

```text
page_k: COMPLETE + lease valid + transfer success
page_v: COMPLETE + lease valid + transfer success
```

只有两个 object 都成功，HiCache 才能把这个 logical page 当作命中。

这就是为什么 Mooncake backend 要把 object 级结果折回 page 级结果。上层不应该看到半个 page 命中。

## 排障时看什么

如果怀疑 Mooncake Store 读到了旧数据或 miss 异常，先按状态分层查：

- PutStart 是否成功但 PutEnd 没有成功。
- replica 是否仍处于 PROCESSING。
- GetReplicaList 返回的 replica 是否 COMPLETE。
- lease 是否过期。
- local hot cache 是否命中过期内容。
- K/V object 是否只有部分存在。
- group id 是否让一组 object 的管理边界一致。

不要一上来只查 transport。transport 成功只能证明 bytes 搬过了，不能证明这份 bytes 应该被读。

## 排查可见性时看哪里

- `PROCESSING` 和 `COMPLETE` 的差别为什么是可见性边界？
- lease 为什么不能省？
- hot cache 为什么不能绕过 master metadata？
- put token 防止的是哪类乱序？
- HiCache page 命中为什么要求多个 Store object 都成功？

> English version: [Rethinking the SGLang HiCache Boundary: From L2 Offload to a Cache Runtime](/blogs/rethinking-sglang-hicache-runtime-boundary-en/)

这篇文章记录的是一次仍在进行中的设计推演，而不是已经定稿的 SGLang 架构。

起点是我在 SGLang 提出的 [#37372: Out-of-process HiCache data plane with device-memory IPC](https://github.com/sgl-project/sglang/issues/37372)。最初的问题很直接：能否把 HiCache 的 GPU ↔ Host transfer、Host KV pool 和 L3 I/O 从 scheduler 进程中拆出去，交给独立的数据面执行？

但随着 Unified Cache external linker、Rust TreeCore、HiCache `buffer_only` 模式，以及共享副本相关讨论逐渐汇到同一张架构图里，这个问题开始显露出更本质的一层：

**我们真正需要拆开的，是 HiCache L2 本身，还是 SGLang 中逻辑缓存控制与 Cache Runtime 之间的边界？**

本文基于 2026-09-03 附近的 SGLang `main`，并参考以下讨论：

- [#37372](https://github.com/sgl-project/sglang/issues/37372) — HiCache data plane 跨进程拆分
- [#35687](https://github.com/sgl-project/sglang/pull/35687) — Unified Cache external linker
- [#37381](https://github.com/sgl-project/sglang/pull/37381) — external linker 端到端集成
- [#32710](https://github.com/sgl-project/sglang/pull/32710) — Rust TreeCore backend
- [#35648](https://github.com/sgl-project/sglang/issues/35648) — 同 GPU 多副本与共享 KV pool

下面出现的 `CacheRuntime`、`CacheExtentHandle`、`RuntimePlan` 等名字只是设计草案中的概念名，不代表已经被 SGLang 接受或实现。

## 最初的问题看起来只是 L1 ↔ L2 transfer

HiCache 今天把 KV cache 组织成三级资源：

```text
L1  GPU memory
L2  Host memory
L3  External / distributed storage
```

最保守的跨进程方案很自然：scheduler 继续持有 radix tree、prefix matching、lock/ref semantics 和 GPU allocator；独立 daemon 通过 CUDA IPC 映射 GPU KV pool，只负责 D2H/H2D、Host KV residency 和 storage I/O。

这个方案的优点是改动面相对可控：`match_prefix()`、`insert()`、`inc_lock_ref()` 等 scheduler hot path 上的操作都不需要跨 IPC。

但它也隐含了一个假设：新组件主要围绕 L2 构建。随着 Unified Cache 继续演进，这个假设开始显得过窄。

## External linker 让“把 L3 搬出去”不再是核心问题

[#35687](https://github.com/sgl-project/sglang/pull/35687) 为 Unified Cache 增加了 external linker 模式。它不是复刻 HiCache hierarchy，而是让 Unified Radix Cache 可以直接连接 external/global memory，同时继续掌握分配、插入、多组件一致性和 cache-node lifecycle。

因此需要把两条路径分开理解：

```text
Hierarchical cache
L1 -> L2 -> L3

Direct linker
L1 <-> external / global memory
```

external linker 解决的是“Unified Cache 如何直接访问外部缓存资源”；而 #37372 更值得讨论的问题，则变成了“scheduler/cache control 是否应该继续和物理内存执行绑定在同一个 runtime 里”。

所以我不再认为新抽象应该叫 `L2Daemon`，也不应该只围绕 L2 API 建模。L1 ↔ L2 可以是第一阶段最小实现，但不应成为长期架构的固定边界。

## 现有 TreeCore split 已经提供了一条接口边界

重新阅读当前代码时，一个重要线索是：Unified Cache 已经在进行类似的职责拆分。

当前 `cache_action.py` 的开头直接写着：

```text
A TreeCore emits CacheActions through the TreeCoreInterface
to guide Controller behavior.
```

TreeCore 负责树结构、matching、LRU、lock/ref 等逻辑，再产生 `CacheAction`，由 Python/controller 一侧执行 pool operation。Rust TreeCore 的演进也一直强调这个方向：TreeCore 侧负责策略和状态维护，pool side 负责 allocation、free 和 translation。

概念上已经接近：

```text
TreeCore
   |
   | decision / CacheAction
   v
UnifiedRadixCache / Controller
   |
   v
physical pools
```

所以，更自然的方向不是重新设计一套独立的 `HiCacheDaemonProtocol`，而是沿着现有 TreeCore / controller 接口边界，继续把物理内存执行下沉到 runtime 一侧。

## ReqToTokenPool 暴露了真正困难的 ownership 问题

SGLang 的 `memory_pool.py` 对基础 KV 内存关系有一个很准确的描述：

```text
ReqToTokenPool
  request -> token locations

TokenToKVPoolAllocator
  token locations -> KV cache slots

KVCache
  physical KV tensors
```

`ReqToTokenPool` 表面上像 scheduler 侧的 bookkeeping，但实际上横跨了 control 和 execution 两侧。

它内部的 `req_to_token` 是 device tensor：

```python
self.req_to_token = torch.zeros(
    (size + 1, max_context_len),
    dtype=torch.int32,
    device=device,
)
```

`attention backend` 会直接读取这张表，`ForwardBatch` 也携带 `req_pool_indices`。`prefill/extend` 和 `decode` 的 KV allocation 又会直接更新它。例如每一步 decode 拿到新的 KV slot 后，都需要把新的物理位置写回对应 request row。

但同一个 `ReqToTokenPool` 又维护 CPU-side 的生命周期状态：

```text
free_slots
req_generation
alloc / alloc_rows
free / free_rows
```

甚至 `alloc(reqs)` 会直接修改 `req.kv.req_pool_idx`。

也就是说，今天这个对象实际上混合了三个概念：

```text
request 生命周期
+
request-row allocator
+
GPU-resident request -> KV location table
```

这正是跨进程边界最容易出问题的地方。

如果 model execution 和 Cache Runtime 被拆到另一侧，那么物理的 `req_to_token` tensor 更适合留在 model execution 一侧，与 `attention backend` 保持在同一个执行域；但 request 生命周期和 admission policy 是否也应该跟着移动，则不能简单一刀切。

因此，相比“L2 transfer 放在哪个进程”，`ReqToTokenPool` 应该怎么拆，反而更值得先设计清楚。

## Raw physical indices 不适合作为跨 runtime 的长期接口

现有 TreeCore / controller 接口边界还有一个明显限制：`CacheAction` 可以直接携带 `torch.Tensor` 形式的 physical indices。

例如今天可以看到类似：

```text
FreeDeviceKV(indices)
FreeComponentDeviceSlot(indices)
```

这在当前 in-process 架构中很高效，因为双方共享同一套 tensor 和 allocator 语义。

但如果 control 和 runtime 真正跨 process，这种表示会带来一系列问题：

- physical index 的生命周期由谁保证？
- allocator 回收并复用 slot 后，如何避免 stale index 被再次使用？
- 很长的 prefix hit，是否需要把大量 page index 通过 IPC 发送？
- 多组件 cache 中 FULL、SWA、Mamba 等状态的物理位置是否都要暴露给 control side？

因此，一个真正适合跨进程的接口边界，可能需要 logical handle，而不是 raw physical index。

例如：

```text
TreeCore node
    |
    v
CacheExtentHandle(id=42, generation=7)
    |
    v
Cache Runtime
    |
    +-- FULL pages: [71, 72, 91, 103, ...]
    +-- SWA placement: ...
    +-- Host residency: ...
```

这里的 `CacheExtentHandle` 只是占位名字。关键原则是：**control side 引用逻辑缓存对象，runtime side 负责解析它对应的物理位置。**

这样 generation / restart safety 也更自然。裸的 `req_pool_idx = 37` 只表达一个位置；`RequestCacheHandle(slot=37, generation=12)` 才能区分当前这一代 row 37 与已经被回收、重新分配过的旧 row 37。

## Prefix hit 不应该把整张 page table 搬过 IPC

这个原则可能比具体 API 更重要。

今天 `match_prefix()` 最终会得到执行阶段需要的 `device_indices`。如果 control 和 runtime 被拆开，而一次 128K-token prefix hit 导致 control side 生成 128K 个 physical index，再整体通过 IPC 发送给 runtime，那么新的抽象基本失去了意义。

更合理的路径应该是：

```text
request tokens
    |
    v
TreeCore prefix match
    |
    v
logical extents / handles
    |
    | small descriptor
    v
Cache Runtime
    |
    +-- resolve physical pages
    +-- populate ReqToToken table
    +-- prepare execution metadata
```

也就是说，如果未来真的跨进程：

**prefix matching 更适合返回可复用的 logical extent，而不是要求 control side 搬运完整的 physical page table。**

这会成为 TreeCore 内部表示是否需要进一步演进的分水岭。

## Decode path 决定 IPC 必须按 batch，而不是按 memory operation

decode path 最能说明为什么不能把现有方法机械地改成 RPC。

当前每一个 decode step 都需要：

```text
allocate KV slot
-> update ReqToToken row
-> execute forward
```

如果把这三个动作分别做成跨进程 RPC，IPC 就会直接进入 per-token hot path。

因此，一个合理的 runtime boundary 至少应该满足：

```text
Scheduler
   |
   | ExecuteBatchPlan
   v
Cache / GPU Runtime
   |
   +-- reserve / allocate
   +-- update ReqToToken table
   +-- launch forward
   +-- commit runtime state
   |
   v
RuntimeCompletion
```

换句话说，目标应该是：

**一次跨边界传递一个 scheduling/batch decision，而不是每次 allocation/write/free 都跨一次边界。**

## L1 ↔ L2 仍然是最好的第一阶段验证面

把架构做得更通用，并不意味着第一版就要同时解决 L2、L3、共享副本和所有 cache component。

恰恰相反，L1 ↔ L2 仍然可能是最合理的 prototype 范围：

- 单 scheduler
- one GPU
- 单 local runtime
- NVIDIA CUDA / Linux
- 先支持 Full Attention
- 验证 D2H/H2D backup / restore
- TreeCore 保持 control-local
- prefix matching 不跨 IPC
- 暂时不引入 external L3 的 failure mode

这可以先回答最基本的问题：

```text
current in-process cache execution
vs.
control / runtime split
```

真正需要测的是 TTFT、ITL、scheduler CPU time、transfer overlap、control overhead、memory overhead 和故障表现，而不是只证明“CUDA IPC 能映射一块内存”。

## L3、buffer_only 和 direct linker 应该作为能力扩展，而不是重新定义边界

HiCache 现在不只有传统意义上的 Host L2 cache。`buffer_only` 可以把 Host memory 只作为 GPU ↔ storage 的临时 staging，而不是长期 L2 residency。

这进一步说明，如果 API 直接被命名成 L2 service，很快就会被现有语义限制住。

更通用的 Cache Runtime 可以把这些能力拆开描述：

```text
device <-> host transfer
host cache residency
host transient staging
storage read/write execution
external linker execution
```

其中 direct linker 我更倾向继续保持为独立抽象：

```text
UnifiedCacheLinker
  direct L1 <-> external/global memory path

CacheRuntime boundary
  control <-> physical memory/execution ownership
```

如果将来 linker operation 也需要在独立 GPU runtime 里执行，可以再把 linker backend 接到 runtime 的 capability 后面，而不是现在就强行把两套设计合并。

## Shared replicas 是这个边界未来价值最明显的场景之一

[#35648](https://github.com/sgl-project/sglang/issues/35648) 讨论了 same-GPU homogeneous replicas、shared KV pool 和 CUDA MPS。它指出的核心难点同样不是“CUDA IPC 能不能看到 tensor”，而是：

```text
allocation
publication
引用生命周期
eviction
synchronization
generation
故障恢复
```

如果未来多个 scheduler 都连接同一个 runtime：

```text
Scheduler A --\
Scheduler B ----> Cache Runtime -> shared physical KV resources
Scheduler C --/
```

那么 request/cache handles、generation 和 authoritative allocator，会比每个 scheduler 各自保存 raw physical indices 更容易扩展。

不过，这并不意味着第一阶段就应该实现 multi-scheduler TreeCore。相反，我仍然倾向先让 TreeCore 和 prefix matching 留在 control side，把分布式缓存状态机的复杂度延后。

## 现在最需要回答的不是“daemon 用什么 RPC”

UDS、shared-memory ring、eventfd、CUDA event IPC 都可以讨论，但它们不是最先需要锁定的东西。

在讨论通信机制之前，我认为还有几个更基础的问题。

### TreeCore node 最终应该保存什么

继续保存 physical indices，还是逐步改成 runtime-owned logical extent handle？

这是整个设计的分水岭。如果 control side 仍然必须理解每一块 cache 的物理位置，那么我们只是把 allocator 放到了另一个进程，并没有真正分离逻辑控制和物理执行。

### ReqToTokenPool 应该如何拆

它今天同时包含 GPU table、request-row allocation 和 request mutation。更合理的长期形态可能是拆成：

```text
RequestCacheHandle / RequestDirectory
RequestSlotAllocator
DeviceReqToTokenTable
```

但是否值得这样做，以及如何兼容 speculative decoding、beam search、SWA、Mamba、DSA 和不同 hardware backend，都需要逐路径验证。

### CUDA Graph 如何保持稳定地址与低开销

很多 attention / CUDA Graph path 会直接读取 `req_to_token` 和 allocator-backed buffer。process split 不能破坏 graph capture 所依赖的稳定 allocation、pointer 关系和执行顺序。

### 多组件 state 如何成为一个原子的 cache object

Unified Cache 已经不只有 Full KV。SWA、Mamba、DSA sidecar 等 component 可能拥有不同的物理位置、命中策略和生命周期。因此 logical extent 不能简单假设成“一串 KV page id”。

### Failure / restart 必须拒绝 stale state

如果 runtime restart，旧 request handle、old generation、pending transfer completion 都不能污染新的 runtime。反过来，如果 control side crash，runtime 也需要能够回收 request-local lease，同时不能误删仍然安全的 shared cache state。

## 一个更稳妥的演进顺序

我目前更倾向 design-first，而不是直接把现有 HiCache controller 拆成两个进程。

可以把演进过程粗略理解为：

```text
0. 先定义 ownership matrix
   明确 TreeCore / request mapping / allocator / physical pools 谁是 authoritative owner

1. 先在进程内收窄 seam
   减少 TreeCore / control 对 raw physical representation 的依赖

2. 用 L1 <-> L2 做最小 runtime prototype
   单 scheduler / 单 GPU，验证 execution boundary 与性能

3. 再评估 request mapping / allocator 是否真正应该 runtime-owned
   重点验证 forward、CUDA Graph、speculative decoding 和 hybrid cache

4. 把 storage execution 作为 capability 加入
   而不是再定义一套 L3-specific process model

5. 最后再讨论 multi-scheduler / shared replica authority
```

这个顺序不是 roadmap，而是一种降低 correctness risk 的思路。

## 这次讨论真正改变了什么

最初我问的是：

> HiCache L2 能否独立运行在另一个进程中？

现在我觉得更值得问的是：

> SGLang 能否把逻辑缓存控制与物理内存执行拆开，同时又不把 physical cache bookkeeping 或 per-token IPC 重新塞回 scheduler hot path？

如果答案是可以，那么所谓 L2 daemon 只是这套架构的第一个验证场景；L3 execution、`buffer_only` staging、共享副本，甚至未来其他 cache state，都可以沿着同一套所有权模型继续扩展。

如果答案是否，我们也应该尽早知道原因：也许 `ReqToTokenPool`、attention metadata、CUDA Graph，或者 TreeCore 对 physical indices 的依赖，本身就要求这些组件保持紧耦合。

这也是我更愿意先把 boundary 画清楚，再开始实现的原因。

这篇文章会随着 [#37372](https://github.com/sgl-project/sglang/issues/37372) 的设计讨论继续更新。它记录的是推理系统中一个所有权边界如何被逐步推导出来，而不是一份已经冻结的 RFC。

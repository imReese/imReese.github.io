> English version: [Rethinking the SGLang HiCache Boundary: From L2 Offload to a Cache Runtime](/blogs/rethinking-sglang-hicache-runtime-boundary-en/)

这篇文章记录的是一次仍在进行中的设计推演，而不是已经定稿的 SGLang 架构。

起点是我在 SGLang 提出的 [#37372: Out-of-process HiCache data plane with device-memory IPC](https://github.com/sgl-project/sglang/issues/37372)。最初的问题很直接：能否把 HiCache 的 GPU ↔ 主机内存传输、主机 KV 池和 L3 I/O 从调度器进程中拆出去，交给独立的数据面执行？

但随着 Unified Cache external linker、Rust TreeCore、HiCache `buffer_only` 模式，以及共享副本相关讨论逐渐汇到同一张架构图里，这个问题开始显露出更本质的一层：

**我们真正需要拆开的，是 HiCache L2 本身，还是 SGLang 中“逻辑缓存控制”与“物理缓存运行时”之间的边界？**

本文基于 2026-09-03 附近的 SGLang `main`，并参考以下讨论：

- [#37372](https://github.com/sgl-project/sglang/issues/37372) — HiCache 数据面跨进程拆分
- [#35687](https://github.com/sgl-project/sglang/pull/35687) — Unified Cache external linker
- [#37381](https://github.com/sgl-project/sglang/pull/37381) — external linker 端到端集成
- [#32710](https://github.com/sgl-project/sglang/pull/32710) — Rust TreeCore 后端
- [#35648](https://github.com/sgl-project/sglang/issues/35648) — 同 GPU 多副本与共享 KV 池

下面出现的 `CacheRuntime`、`CacheExtentHandle`、`RuntimePlan` 等名字只是设计草案中的概念名，不代表已经被 SGLang 接受或实现。

## 最初的问题看起来只是 L1 ↔ L2 传输

HiCache 今天把 KV 缓存组织成三级资源：

```text
L1  GPU 内存
L2  主机内存
L3  外部或分布式存储
```

最保守的跨进程方案很自然：调度器继续拥有基数树、前缀匹配、锁与引用语义，以及 GPU 分配器；独立守护进程通过 CUDA IPC 映射 GPU KV 池，只负责 D2H/H2D、主机 KV 驻留状态和存储 I/O。

这个方案的优点是改动面相对可控：`match_prefix()`、`insert()`、`inc_lock_ref()` 这些调度器热路径上的操作不需要跨 IPC。

但它也隐含了一个假设：新组件主要围绕 L2 构建。随着 Unified Cache 继续演进，这个假设开始显得过窄。

## External linker 让“把 L3 搬出去”不再是核心问题

[#35687](https://github.com/sgl-project/sglang/pull/35687) 为 Unified Cache 增加了 external linker 模式。它的目标不是复刻 HiCache 的分层结构，而是让 Unified Radix Cache 可以直接连接外部或全局内存，同时继续掌握分配、插入、多组件一致性和缓存节点生命周期。

因此需要把两条路径分开理解：

```text
分层缓存
L1 -> L2 -> L3

直接连接路径
L1 <-> 外部 / 全局内存
```

external linker 解决的是“Unified Cache 如何直接访问外部缓存资源”；而 #37372 更值得讨论的问题，则变成了“调度与缓存控制是否应该继续和物理内存执行绑定在同一个运行时里”。

因此，我不再认为新抽象应该叫 `L2Daemon`，也不应该只围绕 L2 API 建模。L1 ↔ L2 可以是第一阶段最小实现，但不应成为长期架构的固定边界。

## 现有 TreeCore 拆分已经提供了一条接口边界

重新阅读当前代码时，一个重要线索是：Unified Cache 已经在进行类似的职责拆分。

当前 `cache_action.py` 的开头直接写着：

```text
A TreeCore emits CacheActions through the TreeCoreInterface
to guide Controller behavior.
```

TreeCore 负责树结构、匹配、LRU、锁与引用等逻辑，再产生 `CacheAction`，由 Python/controller 一侧执行内存池操作。Rust TreeCore 的演进也一直强调这个方向：树侧负责策略和状态维护，内存池侧负责实际的分配、释放与地址转换。

概念上已经接近：

```text
TreeCore
   |
   | 决策 / 动作
   v
UnifiedRadixCache / Controller
   |
   v
物理内存池
```

所以，更自然的方向不是重新设计一套完全独立的 `HiCacheDaemonProtocol`，而是继续沿着现有的 TreeCore / controller 边界，把物理内存执行进一步下沉。

## ReqToTokenPool 暴露了真正困难的所有权问题

SGLang 的 `memory_pool.py` 对基础 KV 内存关系有一个很准确的描述：

```text
ReqToTokenPool
  请求 -> token 位置

TokenToKVPoolAllocator
  token 位置 -> KV 缓存槽位

KVCache
  真实的 KV 张量
```

`ReqToTokenPool` 表面上像调度器侧的状态记录，但实际上横跨了控制和执行两侧。

它内部的 `req_to_token` 是设备张量：

```python
self.req_to_token = torch.zeros(
    (size + 1, max_context_len),
    dtype=torch.int32,
    device=device,
)
```

注意力后端会直接读取这张表，`ForwardBatch` 也会携带 `req_pool_indices`。预填充、扩展阶段以及解码阶段的 KV 分配又会直接更新这张表。例如，每一步解码拿到新的 KV 槽位后，都会把新的物理位置写回对应的请求行。

但同一个 `ReqToTokenPool` 又维护着 CPU 侧的生命周期状态：

```text
free_slots
req_generation
alloc / alloc_rows
free / free_rows
```

甚至 `alloc(reqs)` 会直接修改 `req.kv.req_pool_idx`。

也就是说，今天这个对象实际上混合了三个概念：

```text
请求生命周期
+
请求行分配器
+
GPU 上的请求到 KV 位置映射表
```

这正是跨进程边界最容易出问题的地方。

如果模型执行和缓存内存运行时被拆到另一侧，那么**物理的 `req_to_token` 张量天然更适合靠近注意力执行运行时**；但请求生命周期、准入策略是否也应该跟着移动，则不能简单地一刀切。

因此，相比“L2 传输放在哪个进程”，`ReqToTokenPool` 的职责应该如何拆分，反而更值得优先设计清楚。

## 裸物理索引会泄漏跨运行时的实现细节

现有 TreeCore / controller 边界还有一个明显限制：`CacheAction` 可以直接携带 `torch.Tensor` 形式的物理索引。

例如今天可以看到类似：

```text
FreeDeviceKV(indices)
FreeComponentDeviceSlot(indices)
```

这在当前进程内架构中很高效，因为双方共享同一套张量对象和分配器语义。

但如果控制侧和运行时侧真正跨进程，这种表示就会带来一系列问题：

- 物理索引的生命周期由谁保证？
- 分配器回收并复用位置后，如何避免旧索引被再次使用？
- 很长的前缀命中，是否需要把大量页索引通过 IPC 传输？
- 在多组件缓存中，FULL、SWA、Mamba 等状态的物理布局是否都要暴露给控制侧？

因此，一个真正适合跨进程的接口边界，可能需要使用逻辑句柄，而不是裸物理索引。

例如可以先把概念表示成：

```text
TreeCore 节点
    |
    v
CacheExtentHandle(id=42, generation=7)
    |
    v
Cache Runtime
    |
    +-- FULL pages: [71, 72, 91, 103, ...]
    +-- SWA placement: ...
    +-- Host residency: ...
```

这里的 `CacheExtentHandle` 只是占位名字。关键原则是：**控制侧引用逻辑缓存对象，运行时侧负责解析它对应的物理位置。**

这样也更容易处理 generation 和重启安全。裸的 `req_pool_idx = 37` 只表达“位置 37”；而 `RequestCacheHandle(slot=37, generation=12)` 才能区分“当前这一代的 37”与已经被回收、重新分配过的旧 37。

## 前缀命中不应该把整张页表搬过 IPC

这个原则可能比具体 API 更重要。

今天 `match_prefix()` 最终会得到可供执行阶段使用的 `device_indices`。如果控制侧和运行时侧被拆开，而一次 128K token 的前缀命中导致控制侧生成 128K 个物理索引，再整体通过 IPC 发送给运行时，那么新的抽象边界基本失去了意义。

更合理的路径应该是：

```text
请求 token
    |
    v
TreeCore 前缀匹配
    |
    v
逻辑区段 / 句柄
    |
    | 小型描述符
    v
缓存运行时
    |
    +-- 解析物理页
    +-- 填充 ReqToToken 表
    +-- 准备执行元数据
```

也就是说，如果未来真的跨进程：

**前缀匹配更适合返回“可复用的逻辑区段”，而不是要求控制侧搬运完整的物理页表。**

这会成为 TreeCore 内部表示是否需要进一步演进的分水岭。

## 解码路径决定 IPC 必须以批次为粒度

解码路径最能说明，为什么不能把现有方法机械地改成 RPC。

当前每一个 decode step 都需要：

```text
分配 KV 槽位
-> 更新 ReqToToken 行
-> 执行 forward
```

如果把这三个动作分别做成跨进程 RPC，IPC 就会直接进入逐 token 的热路径。

因此，一个合理的运行时边界至少应该满足：

```text
调度器
   |
   | ExecuteBatchPlan
   v
缓存 / GPU 运行时
   |
   +-- 预留与分配
   +-- 更新 ReqToToken 表
   +-- 启动模型执行
   +-- 提交运行时状态
   |
   v
RuntimeCompletion
```

换句话说，目标应该是：

**每次跨边界传递一个调度或批次决策，而不是每次分配、写入、释放都跨一次边界。**

## L1 ↔ L2 仍然是最好的第一阶段验证面

把架构设计得更通用，并不意味着第一版就要同时解决 L2、L3、共享副本和所有缓存组件。

恰恰相反，L1 ↔ L2 仍然可能是最合理的原型范围：

- 单调度器
- 单 GPU
- 单本地运行时
- NVIDIA CUDA / Linux
- 先支持 Full Attention
- 验证 D2H/H2D 备份与回载
- TreeCore 保持在控制侧本地
- 不把前缀匹配放到 IPC 后面
- 暂时不引入外部 L3 的故障模式

这可以先回答最基本的问题：

```text
当前进程内的缓存执行
vs.
控制侧 / 运行时侧拆分
```

真正需要测的是 TTFT、ITL、调度器 CPU 时间、传输重叠程度、控制开销、内存开销和故障表现，而不是只证明“CUDA IPC 能映射一块内存”。

## L3、buffer_only 和 direct linker 应该是能力扩展，而不是重新定义边界

HiCache 现在不只有传统意义上的主机 L2 缓存。`buffer_only` 模式可以把主机内存仅作为 GPU ↔ 存储之间的临时中转区，而不是长期保存 L2 驻留数据。

这进一步说明，如果 API 直接被命名成 L2 service，很快就会被现有语义限制住。

更通用的缓存运行时可以把这些能力分别描述出来：

```text
设备 <-> 主机内存传输
主机缓存驻留
主机临时中转
存储读写执行
external linker 执行
```

其中 direct linker 我更倾向继续保持为一条相对独立的抽象：

```text
UnifiedCacheLinker
  负责 L1 <-> 外部 / 全局内存的直接路径

CacheRuntime 边界
  负责控制侧 <-> 物理内存与执行侧的所有权拆分
```

如果将来 linker 操作也需要在独立 GPU 运行时里执行，可以再把 linker 后端接到 `CacheRuntime` 的能力接口之后，而不是今天就强行把两套设计合并。

## 共享副本是这个边界未来价值最明显的场景之一

[#35648](https://github.com/sgl-project/sglang/issues/35648) 讨论了同 GPU 的同构副本、共享 KV 池和 CUDA MPS。它指出的核心难点同样不是“CUDA IPC 能不能看到张量”，而是：

```text
分配
发布
引用生命周期
淘汰
同步
generation
故障恢复
```

如果未来多个调度器都连接同一个运行时：

```text
Scheduler A --\
Scheduler B ----> Cache Runtime -> 共享物理 KV 资源
Scheduler C --/
```

那么请求 / 缓存句柄、generation，以及由单一权威分配器管理物理资源，会比每个调度器各自保存裸物理索引更容易扩展。

不过，这并不意味着第一阶段就应该实现多调度器共享 TreeCore。相反，我仍然倾向先让 TreeCore 和前缀匹配留在控制侧，把分布式缓存状态机的复杂度延后。

## 现在最需要回答的不是“守护进程用什么 RPC”

UDS、共享内存环形队列、eventfd、CUDA event IPC 都可以讨论，但它们不是最先需要锁定的东西。

在讨论通信机制之前，我认为还有几个更基础的问题。

### TreeCore 节点最终应该保存什么

继续保存物理索引，还是逐步改成由运行时拥有的逻辑区段句柄？

这是整个设计的分水岭。如果控制侧仍然必须理解每一块缓存的物理位置，那么我们只是把分配器放到了另一个进程，并没有真正分离逻辑控制和物理执行。

### ReqToTokenPool 应该如何拆

它今天同时包含 GPU 表、请求行分配和对请求对象的修改。更合理的长期形态可能是拆成：

```text
RequestCacheHandle / RequestDirectory
RequestSlotAllocator
DeviceReqToTokenTable
```

但是否值得这样做，以及如何兼容 speculative decoding、beam search、SWA、Mamba、DSA 和不同硬件后端，都需要逐路径验证。

### CUDA Graph 如何保持稳定地址与低开销

很多注意力和 CUDA Graph 路径会直接读取 `req_to_token` 以及由分配器管理的缓冲区。跨进程拆分不能破坏 Graph capture 所依赖的稳定地址、指针关系和执行顺序。

### 多组件状态如何组成一个原子的缓存对象

Unified Cache 已经不只有 Full KV。SWA、Mamba、DSA sidecar 等组件可能拥有不同的物理位置、命中策略和生命周期。因此，逻辑区段不能简单假设成“一串 KV page id”。

### 故障和重启必须拒绝陈旧状态

如果运行时重启，旧请求句柄、旧 generation、尚未完成的传输结果都不能污染新的运行时。反过来，如果控制侧崩溃，运行时也需要能够回收请求私有的租约，同时不能误删仍然安全的共享缓存状态。

## 一个更稳妥的演进顺序

我目前更倾向先把设计边界收敛清楚，而不是直接把现有 HiCache controller 拆成两个进程。

可以把演进过程粗略理解为：

```text
0. 先定义所有权矩阵
   明确 TreeCore、请求映射、分配器和物理内存池分别由谁最终负责

1. 先在进程内收窄接口边界
   减少 TreeCore / 控制侧对裸物理表示的依赖

2. 用 L1 <-> L2 做最小运行时原型
   单调度器 / 单 GPU，验证执行边界与性能

3. 再评估请求映射和分配器是否真正应该由运行时持有
   重点验证 forward、CUDA Graph、speculative decoding 和混合缓存

4. 把存储执行作为可选能力加入
   而不是再定义一套只面向 L3 的进程模型

5. 最后再讨论多调度器 / 共享副本下的权威所有权
```

这个顺序不是路线图，而是一种降低正确性风险的思路。

## 这次讨论真正改变了什么

最初我问的是：

> HiCache L2 能否独立运行在另一个进程中？

现在我觉得更值得问的是：

> SGLang 能否把逻辑缓存控制与物理内存执行拆开，同时又不把物理缓存簿记或逐 token IPC 重新塞回调度器热路径？

如果答案是可以，那么所谓 L2 守护进程只是这套架构的第一个验证场景；L3 执行、`buffer_only` 中转、共享副本，甚至未来其他缓存状态，都可以沿着同一套所有权模型继续扩展。

如果答案是否，我们也应该尽早知道原因：也许 `ReqToTokenPool`、注意力元数据、CUDA Graph，或者 TreeCore 对物理索引的依赖，本身就要求这些组件保持紧耦合。

这也是我更愿意先把边界画清楚，再开始实现的原因。

这篇文章会随着 [#37372](https://github.com/sgl-project/sglang/issues/37372) 的设计讨论继续更新。它记录的是推理系统中一个所有权边界如何被逐步推导出来，而不是一份已经冻结的 RFC。

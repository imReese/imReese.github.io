Mooncake Store 这个名字容易让人误会。看到 Store，很自然会想到一个中心化的 KV 服务：client 把数据发给 server，server 存起来，读的时候再从 server 拿回来。

但 Mooncake Store 的主路径不是这样。它更像一个元数据控制面加一组数据面 client/provider。master 负责维护对象、Segment、副本和租约；真正的数据读写由 client 侧通过 TransferSubmitter 和 Transfer Engine 完成。

这个分工是理解 Store 的第一步：**master 回答“数据应该在哪里、现在能不能读”，client 执行“数据怎么过去”。**

## Store 里的对象不是一个简单 value

Store 对外看起来是 key/value，但底层不是一个 key 对应一块连续 buffer 就结束了。对象数据可以由多个 `Slice` 组成，每个 slice 是一段地址和长度。这个设计很适合 tensor 或 KV Cache 这类对象：上层可能已经把数据组织成多段 buffer，Store 不必强行把它们拷成一块。

写入后，对象会对应若干 `Replica`。Replica 可能是 memory replica，也可能是 NoF、disk/offload 等其他路径。每个 replica 会落在某个 `Segment` 上，而 Segment 描述的是一段可被寻址的存储空间，包括 id、name、base、size、protocol 和 endpoint 之类的信息。

所以 Store 的对象模型大概是：

```text
key
  -> object metadata
  -> slices
  -> replicas
       -> segment + offset + length
       -> status
```

这层抽象的意义是：上层只关心 key，Store 内部必须知道这个 key 对应哪些副本、这些副本写完没有、是否还能读、该从哪里读。

## Put 不是一次写入，而是三段控制流

Store 的 Put 不是 client 直接把数据塞给 master。它更像一次带事务味道的写入：

```text
Client::Put
  -> MasterClient::PutStart
  -> master allocates PROCESSING replicas
  -> client writes data through TransferSubmitter
  -> Transfer Engine / memcpy / file path
  -> MasterClient::PutEnd
```

`PutStart` 的作用是申请写入位置。master 会根据 key、slice length、replica config、Segment 状态等信息分配 replica，并把这些 replica 先放到 `PROCESSING` 状态。

注意这里的数据还没有写完。`PROCESSING` 的含义正是“控制面已经预留了位置，但数据面还没有确认完成”。client 随后对这些 replica 执行写入：本地路径可能是 memcpy，远端路径会通过 Transfer Engine 变成 WRITE request，文件或 NoF replica 又会走别的策略。

只有数据面写入成功后，client 才会调用 `PutEnd`。master 在 `PutEnd` 里把对应 replica 标记成 `COMPLETE`。如果中间失败，则走 `PutRevoke`，撤销 processing replica。

这也是为什么不能把 `PutStart` 理解为“写入成功”。它只是写入的开始。真正可读的边界在 `PutEnd` 之后。

## Get 先问 metadata，再搬数据

Get 的路径反过来，但思路一样：

```text
Client::Get
  -> Query / GetReplicaList
  -> master returns COMPLETE replicas + lease
  -> client chooses a readable replica
  -> TransferRead
  -> data lands in caller slices
```

master 的 `GetReplicaList` 不应该返回还在 `PROCESSING` 的副本。它只把已经 complete 的 replica 返回给 client。client 再从这些 replica 里选一个可读对象，可能还会经过 local hot cache redirect，最后执行真正的数据读取。

这里有两个容易忽略的点。

第一，Get 返回的数据不是 master 发回来的。master 返回的是 replica 和 lease 信息，真正的数据由 client 从对应 Segment 读回来。

第二，lease 是读取正确性的一部分。client 拿到 replica 列表以后，不代表可以无限期使用这份信息。对象状态可能变化，Segment 可能卸载，副本可能被移除。lease 给这次读一个时效边界。

## Master 是事实表，不是搬运工

Store master 的核心价值在于维护事实表。它需要回答：

- 哪些 Segment 已经挂载。
- 哪些 object metadata 存在。
- 哪些 replica 还在写。
- 哪些 replica 已经 complete。
- 哪些 Segment 正在 unmount。
- 哪些 copy/move task 正在控制面推进。

这些状态会影响所有 Put/Get 决策。比如一个 Segment 进入 draining 或 unmounting 状态后，就不能再把新副本随便分配过去。一个 key 的旧 replica 如果正在被覆盖，也不能让读路径误读到不一致状态。

这就是 metadata 服务最麻烦的地方：它不在大块数据路径上，但它决定了数据路径是否安全。

## Client 才是数据面的组织者

client 不只是一个薄 RPC wrapper。它同时持有 `MasterClient`、`TransferSubmitter` 和 `TransferEngine`，所以它既能问 master 要 metadata，也能把 replica 描述翻译成实际传输任务。

这一层的关键角色是 `TransferSubmitter`。它会根据 replica 类型、本地性、endpoint、backend 等信息选择策略：

- 同进程或同 endpoint 的路径可以走 local memcpy。
- 远端 memory replica 走 Transfer Engine。
- disk/offload/NoF 有自己的读写路径。

这让 Store 的 Put/Get 不是一个固定传输方式，而是一个“由 metadata 决定目标、由 submitter 决定执行路径”的过程。

## 小结

Mooncake Store 的核心不是“把 value 存进 master”，而是把 KV Cache 这类大对象拆成可管理的 object、slice、replica 和 Segment 状态。

master 维护元数据和副本事实，client 负责把这些事实转成真实的数据搬运。这个边界让 master 避开大块数据面，也让 client 可以根据本地/远端、内存/文件、不同 transport 做更细的执行选择。

理解这个分工以后，Store 的 Put/Get 就不再是普通 KV API，而是一套围绕对象副本生命周期的控制面和数据面协作。

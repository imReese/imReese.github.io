Mooncake Store 不是“client 把 value 发给 server，server 存起来”的中心化 KV 服务。它更像一个对象元数据控制面，加上一组由 client/provider 执行的数据面。

读源码前先建立对象模型，否则 Put/Get 很容易看散。

主要入口：

```text
mooncake-store/include/client_service.h
mooncake-store/include/types.h
mooncake-store/include/replica.h
mooncake-store/src/client_service.cpp
mooncake-store/src/master_service.cpp
```

## object 不是简单 value

Store 对外是 object key，但内部不会假设 value 必须是一块连续内存。写入时，caller 传入的是 `Slice` 列表：

```text
Slice
  ptr
  size
```

这对 KV Cache 很重要，因为上层数据经常已经按 K/V、layer、head、page 拆开。Store 不应该为了抽象好看强行拷成一块大 buffer。

因此对象模型更接近：

```text
ObjectKey
  -> object metadata
  -> slices
  -> replicas
       -> segment id/name
       -> offset
       -> length
       -> status
```

object key 是上层看到的名字；slice 是本次读写的本地 buffer 描述；replica 是 Store 内部真正能读写的数据副本。

## Segment 是可寻址存储空间

`Segment` 描述的是一段可被寻址的远端或本地存储空间。它包含：

```text
Segment
  id
  name
  base
  size
  te_endpoint
  protocol
```

Store 里的 replica 不直接写“某台机器某个变量”。它会落到某个 Segment 的某段 offset/length 上。Transfer Engine 之后才能把这段描述翻译成 READ/WRITE 请求。

这层间接性很重要。master 维护 Segment 和 replica metadata，client 根据 metadata 选择本地 memcpy、Transfer Engine、NoF 或 offload 路径。

## replica 是可读性的核心

Replica 有状态。关键状态包括：

```text
INITIALIZED
PROCESSING
COMPLETE
REMOVED
FAILED
```

一次 Put 过程中，master 可以先分配 replica，但这不等于数据已经写完。只有进入 `COMPLETE` 的 replica 才能成为正常读路径候选。

因此 Store 的读正确性不是“key 存在”，而是：

```text
key 存在
  + metadata 有可用 replica
  + replica 状态是 COMPLETE
  + lease 仍在有效期内
  + client 能从对应 Segment 成功读出数据
```

这比普通 KV 服务复杂很多，但它允许大对象的数据面绕开 master。

## master 维护事实表

master 的核心职责是维护事实表，不是搬数据。

它至少要回答：

- 哪些 client 和 Segment 已经 mount。
- 每个 object 有哪些 replica。
- 哪些 replica 正在写入。
- 哪些 replica 已经 complete。
- 哪些 Segment 正在 draining 或 unmount。
- tenant quota、allocation strategy、hot cache、lease 是否允许本次操作。

Put 时，master 负责分配 replica 并推进状态。Get 时，master 负责返回可读 replica 和 lease。真正的数据字节不经过 master。

## client 组织数据面

client 不是薄 RPC wrapper。它同时持有：

```text
MasterClient
TransferSubmitter
TransferEngine
LocalHotCache
```

client 先向 master 请求 metadata，再把 metadata 翻译成数据面动作。比如同 endpoint 可以走 memcpy，远端 memory replica 走 Transfer Engine，文件/offload 走对应路径。

这就是 Mooncake Store 的基本分层：

```text
master:
  管 metadata、状态、lease、allocation

client:
  调 master 拿事实
  调 TransferSubmitter 搬数据

Transfer Engine:
  只处理 Segment/offset/length 的字节传输
```

## ReplicateConfig 决定副本策略

`ReplicateConfig` 不是装饰参数。它会影响 Put 时 master 怎样放置 replica。

常见字段包括：

```text
replica_num
nof_replica_num
preferred_segments
preferred_nof_segments
prefer_alloc_in_same_node
with_soft_pin
with_hard_pin
group_ids
```

其中 `group_ids` 对 SGLang/Mooncake 接入很有用。一个 logical KV page 可能展开成 K object、V object 或 side pool object。它们虽然是多个 object key，但属于同一逻辑缓存单元。group id 可以让 Store 在 metadata routing、lease refresh、eviction 上按组理解这些 object。

## 和 HiCache 的映射

SGLang HiCache 接 Mooncake Store 时，不会把“一个请求”作为 object。它会把 prefix KV 按 page 拆开：

```text
HiCache logical page key
  -> Mooncake object key(s)
  -> Store object metadata
  -> replica(s)
  -> Segment + offset + length
```

MHA 通常一个 logical page 会展开成 K/V 两个 object；MLA 通常是一个 object；hybrid pool 还会继续展开 side state object。

所以 Store 看到的是一批 object，不知道它们属于哪个 request，也不知道 SGLang 的 radix tree 结构。这个边界必须守住。

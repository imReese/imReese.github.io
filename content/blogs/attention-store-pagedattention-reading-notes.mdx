读 [PagedAttention](https://arxiv.org/abs/2309.06180) 时，我觉得最重要的不是“像操作系统分页”这个类比，而是它把 KV Cache 从一个缓存名词变成了一个内存管理对象。

LLM serving 里的 KV Cache 有几个麻烦属性：

- 请求长度不同。
- decode 长度不可提前知道。
- 请求随时结束，显存要回收。
- parallel sampling / beam search 会共享 prompt。
- prefix cache 命中时，多个请求可能复用同一段历史。
- scheduler 每一步都在重新组织 batch。

如果仍然用“每个请求一大段连续 KV buffer”的思路，显存很快会浪费在预留和碎片上。

## 先看一个请求怎么长大

一个请求进入 runtime 后，KV Cache 不是一次性完整确定的。

```text
prefill prompt
  -> allocate blocks for prompt K/V
  -> run prefill attention
  -> store K/V blocks

decode token 1
  -> read prompt blocks
  -> append new K/V

decode token 2
  -> read prompt + token 1 blocks
  -> append new K/V
```

这个请求像一条不断增长的序列。它需要保持逻辑 token 顺序，但物理上不一定非要连续。

PagedAttention 的核心就是把这两个问题拆开：

```text
logical token order:
  owned by request / scheduler

physical KV placement:
  owned by block manager
```

## block table 像一层小 MMU

PagedAttention 里，请求的 KV Cache 被切成 logical blocks。每个 logical block 通过 block table 指向一个 physical block。

```text
request A:
  logical block 0 -> physical block 8
  logical block 1 -> physical block 2
  logical block 2 -> physical block 15
```

attention kernel 仍然要按 token 顺序读取历史 K/V。区别在于，它不能再假设 K/V 在一段连续地址里，而要通过 block table 找物理位置。

这层间接性换来两个能力：

1. 请求不需要连续显存。
2. physical block 可以被释放、复用、共享。

代价也很清楚：kernel 要理解 block table，runtime 要维护 block 生命周期，debug 时也多了一层映射。

## block size 是系统参数

block size 太大，尾部浪费明显。请求最后一个 block 可能只用了几个 token，却占住整个 physical block。

block size 太小，block table 更大，管理成本更高，kernel 间接寻址也更频繁。

所以 block size 不是论文里的装饰项。它和这些因素绑在一起：

- 平均 prompt 长度。
- 平均 decode 长度。
- batch size。
- head dimension。
- kernel 对 block layout 的访问效率。
- 共享前缀比例。

这类参数不能脱离 workload 单独说好坏。

## 共享前缀不是复制字符串

parallel sampling 或 beam search 里，多个分支共享同一段 prompt。直觉上，这段 prompt 的 K/V 不应该复制多份。

PagedAttention 可以让多个 sequence 的 logical blocks 指向同一组 physical blocks：

```text
shared prompt blocks:
  P8 -> P2 -> P15

branch A:
  P8 -> P2 -> P15 -> P4

branch B:
  P8 -> P2 -> P15 -> P9
```

这里必须有引用计数。只要还有一个 sequence 引用 `P8`，它就不能回到 free list。

这也是 KV Cache 和普通“字符串前缀相同”不一样的地方。系统共享的是每层、每个 head、每个 token 对应的 K/V block，而不是共享一段文本。

## copy-on-write 是正确性的边界

共享 block 只能读。分支要继续写入时，如果写到一个被多个 sequence 引用的 block，就会污染其它分支。

所以需要 copy-on-write：

```text
P8 ref_count = 2
branch A wants to append into P8

allocate P11
copy P8 -> P11
branch A maps logical block to P11
P8 ref_count--
write new token into P11
```

这个过程如果做错，模型可能不会直接报错，而是悄悄 attend 到别的分支写出的 K/V。输出变奇怪，但栈上看不出普通异常。

调 KV Cache 系统时，这类 bug 比内存泄漏更讨厌，因为它污染的是上下文语义。

## scheduler 不能只问还有多少显存

PagedAttention 让 block 管理更灵活，但 scheduler 仍然要做选择。

它要决定：

- 新请求能不能进来。
- 当前 batch 里哪些请求继续 decode。
- block 不够时是抢占、等待、拒绝还是换出。
- prefix 命中是否值得等。
- 长请求是否挤压短请求 tail latency。

也就是说，block manager 只回答“物理块怎么放”。scheduler 还要回答“这一步应该服务谁”。

这点和 HiCache/Mooncake 的关系很像：有远端 KV 不代表一定要等它，能 prefetch 不代表当前请求应该阻塞。

## PagedAttention 和 HiCache 不是同一层

我会把它们这样分开：

```text
PagedAttention:
  inside one serving runtime
  GPU KV physical block management

HiCache:
  inside SGLang runtime
  GPU / Host / Storage 三层 cache state

Mooncake Store:
  outside runtime
  remote object / replica / transfer path
```

PagedAttention 管的是 GPU 里 KV block 怎么组织。HiCache 继续把 prefix KV 状态扩到 Host 和 Storage。Mooncake Store 再提供远端 object 存取和传输。

它们都和 KV Cache 有关，但状态对象不一样：

- PagedAttention 的对象是 physical KV block。
- HiCache 的对象是 prefix node 的 GPU/Host/Storage 状态。
- Mooncake 的对象是 object、slice、replica 和 Segment。

混在一起讲“KV cache 命中”，很容易把读路径说错。

## 我会重点查的几处实现

读 vLLM、SGLang 或类似 runtime 时，我会直接找这些点：

- block table 在 sequence 上怎么存。
- physical block 的 free list 怎么维护。
- prefill 后 blocks 如何提交。
- decode append 如何申请新 block。
- shared prefix 如何增加 ref count。
- request finish/cancel 如何释放 blocks。
- copy-on-write 在写入前还是写入后做。
- attention kernel 如何从 block table 读 K/V。
- block 不足时 scheduler 采取什么策略。

PagedAttention 的价值，不在于它有一个好记的分页比喻，而在于它把 KV Cache 从连续数组改成了有映射、有引用、有生命周期的内存对象。

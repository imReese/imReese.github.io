ZooKeeper 和 etcd 很容易被误用，因为它们看起来都像 KV。

但它们真正提供的不是“大一点的配置表”，而是一小段带顺序、生命周期和通知能力的控制面事实。

我会用四个问题判断一个系统有没有把协调服务用对：

```text
watch 断了能不能续？
历史 compact 了能不能重建本地状态？
lease 过期后旧进程还能不能写外部资源？
这里存的是控制面事实，还是数据面流量？
```

## 第一条红线：不要把协调服务当数据面

ZooKeeper / etcd 适合存：

- leader identity。
- 服务实例。
- 配置版本。
- 任务领取状态。
- worker session。
- 小规模元数据指针。

不适合存：

- 用户大表。
- 高频请求日志。
- 指标流。
- 大块二进制。
- 消息队列式写入流。

原因不是“它们比较慢”这么粗糙，而是每次写入都会进入一致性复制、落盘、revision 推进和 watch 通知。你把数据面流量塞进去，拖慢的是整个控制面。

协调服务应该小、稳、可解释。它的价值是给其它系统提供事实来源，不是替代业务数据库。

## ZooKeeper 的强项是 session 语义

ZooKeeper 的 znode 树模型很直接：

```text
/
  services/
  locks/
  config/
```

真正有用的是节点类型：

- persistent：显式删除前一直存在。
- ephemeral：session 结束后自动删除。
- sequential：创建时带递增序号。
- ephemeral sequential：临时且有序。

服务注册依赖 ephemeral：进程挂了、session 断了，节点消失。锁和选主依赖 sequential：大家创建有序节点，序号最小者持有权力，其它客户端 watch 前一个节点。

这里的工程边界是 session。协调层不需要知道进程“物理上是否还活着”，它只需要判断这个 session 是否还被承认。

## etcd 的强项是 revision 时间线

etcd 更像 KV，但它的关键不是 key，而是 revision。

```text
rev 101: put /config/a
rev 102: put /services/x
rev 103: delete /services/y
```

revision 让客户端能说清楚自己看到了哪里。watch 断线后，也能从某个 revision 往后继续消费。

这就是 Kubernetes controller 能工作的基础模式：

```text
list current objects at resourceVersion R
watch from R + 1
process ordered events
if watch history is gone, relist
```

如果没有 revision/resourceVersion，controller 断线后只能猜自己漏没漏事件。

## watch 不是 callback

把 watch 当 callback，是使用 etcd/ZooKeeper 时最常见的错误之一。

callback 的心智模型是：

```text
changed -> notify me
```

watch 的真实模型更像：

```text
I have processed history up to revision R.
Please give me events after R.
If you no longer have that history, tell me to rebuild.
```

所以一个可靠 watcher 必须保存进度，并处理断线。

如果代码在 watch 断线后只是重连，不检查 revision 是否还存在，它的本地 cache 就可能悄悄变成旧世界。

## compaction 是事件流的保留窗口

etcd 不会无限保存历史 revision。compaction 会清理旧版本。

这意味着慢 watcher 或长时间断线的 watcher 会错过窗口：

```text
client last seen: 120
etcd compacted <= 180
client watches from 121
  -> compacted error
```

正确动作不是继续 retry，而是 relist。

这点对 Kubernetes controller 很关键。controller 不能假设自己永远在线，也不能假设 watch 永远连续。它必须能用 list 重建本地状态，再从新的 resourceVersion 继续 watch。

## lease 过期不是死亡证明

lease 解决的是沉默客户端的生命周期。

```text
grant lease
put key with lease
keepalive
pause / partition / crash
lease expires
key deleted
```

lease 过期表示协调服务不再承认这个 holder。它不等于进程真的停止了。

旧进程可能只是 GC pause，或者网络短暂断了。恢复后它还会继续跑。如果它手里还有旧 leader 身份，事情就危险了。

所以 lease 通常必须配合 fencing token。

## 选主不带 fencing，只是内部正确

假设：

```text
node-1 holds leader lease 10
node-1 pauses
lease 10 expires
node-2 gets leader lease 11
node-1 resumes
```

协调服务内部已经承认 node-2 是新 leader。但 node-1 进程还活着。如果它继续写外部数据库、对象存储或下游服务，而下游不检查 token，就会出现旧 leader 写入。

更稳的模式是把 epoch / revision / lease id 带到外部写入：

```text
write(value, fencing_token=11)

external system:
  accept only if token >= current_token
```

这样旧 leader 即使恢复，也会因为 token 过期被拒绝。

选主不是终点。选出来的权力必须能被下游验证。

## Kubernetes 用 etcd，是因为它能重建事实

Kubernetes 依赖 etcd，不是因为 etcd 像一个普通数据库，而是因为 API Server 和 controller 能围绕 resourceVersion 建立有序事实。

大致链路是：

```text
kubectl apply
  -> API Server validates object
  -> write object to etcd
  -> controller watches change
  -> controller reconciles actual state
```

controller 的关键动作不是“收到事件就执行”，而是 reconcile：

```text
desired state from etcd
  + observed cluster state
  -> next action
```

watch 可以断，事件可以重复，本地 cache 可以丢。只要 controller 能 relist 并重新 watch，它就能回到事实来源上。

## 我会警惕的使用方式

看到这些设计，我会先打问号：

- 把每个请求状态都写进 etcd。
- watch 断线后没有保存和检查 revision。
- compacted error 只做重试，不做 relist。
- leader 只写一个 key，没有 fencing token。
- lease TTL 设得很短，但进程有长 GC pause。
- 把大 JSON、二进制 blob、指标流塞进协调服务。
- controller 本地 cache 没有重建路径。

这些问题不是 API 用法小错，而是把协调服务的边界理解错了。

## 协调服务应该保持克制

ZooKeeper / etcd 提供的是小规模、有顺序、可观察、带生命周期的控制面事实。

watch 让变化可以被追上，revision 让断线恢复有锚点，lease 让沉默客户端可以被回收，fencing 让旧 leader 不能继续写外部资源。把这些边界用清楚，协调服务会很稳；把它当万能状态中心，它会把整个控制面一起拖下水。

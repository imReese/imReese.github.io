HiCache 要解决的问题不是“多加一个远端 KV 存储”，而是把 SGLang 运行时里的 KV Cache 变成三级资源：

```text
L1: GPU KV pool
L2: Host KV pool
L3: Storage backend, such as Mooncake / 3FS / file / NIXL
```

本文基于 SGLang `v0.5.14`。读源码时建议先看这几个文件：

```text
python/sglang/srt/mem_cache/hicache_storage.py
python/sglang/srt/mem_cache/unified_radix_cache.py
python/sglang/srt/mem_cache/hiradix_cache.py
python/sglang/srt/mem_cache/pool_host.py
python/sglang/srt/mem_cache/storage/backend_factory.py
```

## L1 不是 request table，而是 KV pool

SGLang runtime 里和 KV cache 相关的结构至少有两类。

`ReqToTokenPool` 记录 request 到 token slots 的映射。它回答的是：某个请求的第几个 token 对应哪个 token index。

`TokenToKVPoolAllocator` 和具体 KV pool 记录真实 K/V tensor 的位置。它回答的是：token index 对应的 K/V 在 GPU memory 里的哪一段。

Radix cache 里的 prefix node 通常保存的是 GPU token indices，也就是 node 的 `value`。一次 prefix 命中，本质上是 radix tree 找到一段 token prefix，并返回可以直接喂给 attention backend 的 GPU KV slots。

HiCache 的第一步不是推翻这套机制，而是在它之上增加 Host 和 Storage 状态。

## HiCache 给 radix node 增加位置语义

在普通 prefix cache 中，node 更像“prefix 到 GPU indices 的索引”。在 HiCache 中，node 还要记录这段 prefix 的 KV 是否有 Host 备份、是否已经写入 Storage。

核心字段可以这样理解：

```text
value             这段 prefix 在 GPU KV pool 里的 token indices
host_value        这段 prefix 在 Host KV pool 里的 token indices
hash_value        这段 prefix 对应的 storage page keys
backuped          是否已经完成 D->H 备份
backuped_storage  是否已经完成 H->Storage 备份
lock_ref          GPU 侧引用保护，避免异步 load/evict 时节点被删
host_ref_counter  Host 侧引用保护，避免 storage prefetch/write 时 host slot 被回收
```

因此一次匹配不再只有“命中多少 token”，而是拆成：

```text
device hit:  已经在 GPU，可直接复用
host hit:    GPU 没有，但 Host 有机会 load back
storage hit: Host 没有，但 L3 storage 可能可以 prefetch
miss:        需要重新 prefill
```

这也是 HiCache 难读的原因：它把 prefix tree 从纯索引结构变成了 cache tier 状态机。

## Host pool 是真正的 L2 KV memory

Host pool 不是 Python 字典，也不是普通 bytes cache。它是和 GPU KV pool 类似的一块结构化内存，有自己的 page size、layout、allocator 和 buffer meta。

常见 layout 包括：

```text
layer_first
page_first
page_first_direct
page_head
```

这些 layout 决定 Host KV 在内存里如何排列，也决定 storage backend 能否 zero-copy 地按 page 写入。比如 Mooncake backend 会调用 host pool 的 `get_page_buffer_meta()`，拿到每个 page 对应的 pointer 和 size，再交给 Mooncake Store 的 zero-copy batch API。

所以 Host pool 是 L2，不是临时中转变量。它承担三件事：

- 接收 GPU KV 的 D->H backup。
- 作为 H->D load back 的来源。
- 作为 L3 storage get/set 的 zero-copy buffer。

## HiCacheStorage 是 L3 的统一接口

SGLang 没有在 radix cache 里直接调用 Mooncake API。它通过 `HiCacheStorage` 抽象 L3 backend。

`HiCacheStorage` 在 `v0.5.14` 里有两组接口：

```text
v1:
  batch_exists(keys)
  batch_get_v1(keys, host_indices)
  batch_set_v1(keys, host_indices)

v2:
  batch_exists_v2(keys, pool_transfers)
  batch_get_v2(transfers)
  batch_set_v2(transfers)
```

v1 面向普通 KV pool：一组 page keys 对应一组 Host KV page indices。

v2 面向 hybrid cache：除了 KV 以外，还可能有 Mamba state、SWA state、DeepSeek V4 side pools、draft KV 等额外 pool。v2 用 `PoolTransfer` 描述每个 pool 的 host/device indices、keys、命中策略和依赖关系。

```text
PoolTransfer
  name
  host_indices
  device_indices
  keys
  hit_policy
  nodes_to_load
  indices_from_pool
```

这样 HiCache 不需要知道 Mooncake、NIXL、3FS 每个 backend 的内部实现，只需要围绕 page key 和 Host pool indices 组织读写。

## 写策略决定何时进入 L2/L3

HiCache 的写入不是“生成 KV 后立刻全量写远端”。常见路径有两类。

write-through 路径更主动：命中次数达到阈值，或者策略要求写穿时，node 会先走 D->H backup。之后如果启用 storage，再走 H->Storage。

write-back 路径更像 eviction 保护：GPU 空间不够时，先把还没有 Host 备份的 node 写到 Host，再从 GPU 驱逐。这样被驱逐的 prefix 不一定消失，只是从 L1 降到了 L2。

核心入口在 `unified_radix_cache.py`：

```text
write_backup(node)
  -> cache_controller.write(...)
  -> commit_hicache_transfer(...)
  -> node.backuped = true

write_backup_storage(node)
  -> cache_controller.write_storage(...)
  -> HiCacheStorage.batch_set_v1/v2(...)
```

## 读策略决定何时等 cache

请求进入调度器后，HiCache 会先在本地 tree 里找 prefix。GPU 命中的部分可以直接复用；Host 命中的部分需要 load back；Storage 可能命中的部分需要 prefetch 到 Host。

读路径的关键是：HiCache 不是只要 L3 有数据就阻塞等待。它会考虑：

- prefix 是否 page aligned
- prefetch length 是否超过阈值
- Host pool 是否有可用空间
- load back 是否超过 GPU mem quota
- 当前请求是否值得为 cache 等待
- 额外 pool 是否也命中

核心入口包括：

```text
prefetch_from_storage(...)
  -> allocate Host indices
  -> cache_controller.prefetch(...)
  -> HiCacheStorage.batch_get_v1/v2(...)

load_back(...)
  -> allocate GPU indices
  -> cache_controller.load(...)
  -> commit device indices
```

因此 HiCache 是调度感知的缓存层，不是透明 KV store。

## 和 Mooncake 的连接点

当参数指定：

```text
--hicache-storage-backend mooncake
```

`StorageBackendFactory` 会创建 Mooncake backend。这个 backend 实现 `HiCacheStorage`，并把 SGLang 的 Host KV buffer 注册给 Mooncake Store。之后：

```text
HiCache page key
  -> Mooncake object key

Host KV page pointer
  -> Mooncake zero-copy buffer pointer

batch_set_v1/v2
  -> batch_put_from / batch_put_from_multi_buffers

batch_get_v1/v2
  -> batch_get_into / batch_get_into_multi_buffers
```

Mooncake 只接住 L3 这一段。prefix tree、请求调度、GPU slot 管理仍然在 SGLang。

## 把 HiCache 当成 runtime 状态机

HiCache 难读，是因为它不是一个独立 KV store，而是嵌在 SGLang runtime 里的状态机。radix node 同时保存 GPU、Host、Storage 三层位置：`value` 指向 GPU token indices，`host_value` 指向 Host pool indices，`hash_value` 指向 L3 page key。

这也解释了为什么 L3 backend 的读写对象是 Host pool，而不是 GPU pool。Storage 负责把 page 写入或读出 Host buffer；Host->GPU 的 load back 仍然由 HiCache 和 cache controller 处理。storage hit 只是“远端可能有数据”，不是“attention 已经能复用”。

读代码时可以沿着一个 page 走：GPU 上生成 KV，必要时 backup 到 Host，再 batch_set 到 Storage；下一次请求先查 radix tree，再 batch_exists/prefetch 到 Host，最后 load_back 到 GPU。把这条路径连起来，Mooncake backend 才不会看起来像凭空插进来的黑盒。

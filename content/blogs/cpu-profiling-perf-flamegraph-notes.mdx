CPU profiling 最怕变成看图猜谜。

火焰图上哪个块最宽，就去改哪个函数；改完跑一个本地 benchmark，快了一点，就说优化完成。这条路很容易把时间花在不主导线上延迟的问题上。

我更愿意把 profiling 放进一次完整排查里：

```text
symptom
  -> system counters
  -> on-CPU / off-CPU 判断
  -> profile under matching workload
  -> hypothesis
  -> one change
  -> same workload verification
```

这篇不写 perf 命令大全，只写一次延迟问题里我会怎样把证据串起来。

## 事故入口：p99 抖，但 CPU 看起来不一定满

假设服务出现这样的现象：

```text
avg latency: 4 ms
p99 latency: 180 ms
QPS: stable
error rate: low
CPU usage: 45% - 65%
```

第一反应不应该是打开火焰图。

CPU 使用率不满，不代表没有 CPU 问题；但也可能根本不是 on-CPU 问题。线程可能在等锁、等 I/O、等网络、等 runtime pause、等调度。

我会先看系统层：

```bash
top
pidstat -p <pid> 1
pidstat -w -p <pid> 1
vmstat 1
iostat -xz 1
sar -n DEV 1
```

这里先回答几个问题：

- user/sys CPU 是否接近瓶颈。
- voluntary / involuntary context switch 是否异常。
- run queue 是否堆积。
- disk await / util 是否升高。
- network 是否丢包或打满。
- p99 抖动是否和某个资源曲线对齐。

如果 CPU 不高但上下文切换、I/O await 或 lock wait 很高，普通 CPU 火焰图可能不是第一工具。

## on-CPU 和 off-CPU 先分开

On-CPU profiling 看的是线程正在 CPU 上执行时，时间花在哪里。

Off-CPU profiling 看的是线程没在 CPU 上运行时，卡在哪里。

两者回答的问题不同：

```text
on-CPU:
  CPU cycles are being spent in which call stacks?

off-CPU:
  wall time is being lost waiting for what?
```

如果 CPU 已经打满，on-CPU 火焰图通常很有用。可能看到序列化、压缩、hash、内存分配、日志格式化、拷贝、正则、JSON 等热点。

如果 CPU 不满但延迟高，off-CPU 可能更有价值。可能是 mutex、condition variable、disk I/O、socket read/write、epoll wait、runtime safepoint 或调度等待。

只看 on-CPU，容易优化一个“线程真正在跑时最忙”的函数，却错过“线程大部分时间根本没在跑”的事实。

## perf 采样要贴着 workload

Linux 上常见入口：

```bash
perf record -F 99 -p <pid> -g -- sleep 30
perf report
```

或者生成火焰图：

```bash
perf script > out.perf
stackcollapse-perf.pl out.perf > out.folded
flamegraph.pl out.folded > cpu.svg
```

这里有几个容易犯错的点。

第一，采样窗口要覆盖问题发生时段。没有流量时采样，看到的只是 idle、background thread 或 GC。

第二，workload 要和线上症状接近。请求类型、payload size、并发、数据规模都要对齐。

第三，采样频率不要盲目拉高。频率太高会影响被测进程，太低又看不清。`99Hz` 常作为起点，是为了避开某些周期性对齐。

第四，符号要可读。C/C++/Rust 服务最好保留 frame pointer 或有可用 debug symbols。否则火焰图上全是地址和 `[unknown]`，解释力会大幅下降。

## 火焰图不是时间线

火焰图横向宽度表示采样占比，不表示时间顺序。

```text
wide frame:
  many samples included this frame

tall stack:
  deep call path

top wide frame:
  leaf work where CPU cycles are spent
```

底部框架宽，不一定说明框架慢。它可能只是很多请求都经过那里。真正要看的是顶部宽块，以及它是否符合预期。

比如：

- 压缩函数宽：可能是业务主工作，不一定是浪费。
- JSON parse 宽：如果高频路径反复解析同一字段，可能有优化空间。
- malloc/free 宽：可能是对象生命周期或 buffer 复用问题。
- logging 宽：高频格式化日志可能很不值。
- memcpy 宽：要看是不是跨层重复复制。

火焰图给的是证据，不是自动结论。

## 我会把热点分成“主工作”和“浪费”

看到热点后，我会先问它是不是系统应该做的工作。

主工作：

- 加密。
- 压缩。
- 模型计算。
- 正常序列化。
- 必要校验。

浪费：

- 同一请求重复解析。
- 锁内做重活。
- 每层都复制 buffer。
- 临时对象大量分配。
- debug 日志在热路径格式化。
- 低效 map/list 查找。
- 明明可以 batch 却逐条调用。

优化主工作通常要换算法、换实现或接受 trade-off。优化浪费则更像把不该出现的成本拿掉。

## 一个假设只能配一个主要改动

性能优化很容易越改越多。最后数字变了，但不知道是哪一处生效。

我会把假设写具体：

```text
Hypothesis:
  p99 is affected by repeated JSON parsing in request admission.

Evidence:
  perf shows parse_request_fields accounts for 18% on-CPU samples
  same stack appears in p99-heavy workload

Change:
  parse once at boundary, pass typed fields downstream
```

然后只做这一类改动。不要顺手改 batch size、日志级别、锁粒度和 buffer 池。否则验证阶段没法解释。

## benchmark 要和 profile 场景对得上

profile 是在线上 workload 下采的，benchmark 却是本地单线程 mock，这样的验证很弱。

我会尽量对齐：

- 请求类型。
- payload size。
- 并发度。
- 数据规模。
- 编译参数。
- CPU governor。
- 容器 CPU limit。
- 日志级别。
- 下游 mock 行为。

如果线上 p99 来自高并发下的锁竞争，本地单线程 benchmark 只会证明函数本身快，不会证明 tail latency 修好了。

## 结果记录要能被复盘

一条性能优化记录至少应该留下：

```text
symptom:
  p99 180 ms under workload X

baseline:
  QPS, avg, p95, p99, CPU, memory, context switch

profile:
  command, window, workload, top stacks

hypothesis:
  why this stack is waste or bottleneck

change:
  one main variable

result:
  same workload comparison

risk:
  semantic change, memory trade-off, complexity
```

没有这些，优化就会变成“我记得当时快了”。

## profiling 的最终目标不是更好看的火焰图

CPU profiling 的目标不是把某个宽块变窄，而是解释一次性能症状。

如果症状是 p99 抖，最后就要回到 p99；如果症状是 CPU 打满，最后就要回到 CPU utilization 和吞吐；如果症状是请求卡住，可能最后要证明 off-CPU wait 降了。

火焰图只是中间证据。真正的闭环是：同一个 workload 下，问题指标改善，而且你知道为什么。

CPU 优化最怕的不是慢，而是不知道为什么慢。

很多时候我们会先有直觉：是不是锁太重、是不是内存拷贝太多、是不是 JSON 太慢、是不是线程数不够。但直觉只能用来提出假设，不能用来当结论。

我现在更愿意先做 profiling：

```text
observe
  -> profile
  -> find hotspot
  -> form hypothesis
  -> change one thing
  -> measure again
```

这条闭环比“凭感觉改代码”慢一点，但更容易真的把问题打掉。

## 先区分 CPU 忙和请求慢

请求慢不一定是 CPU 忙。

可能是：

- 等网络。
- 等磁盘。
- 等锁。
- 等下游。
- 被调度器挂起。
- GC 或 runtime pause。
- CPU 真正在算。

所以看 CPU profile 之前，我会先看系统整体：

```bash
top
pidstat
vmstat
iostat
sar
```

如果 CPU 使用率不高，但延迟很高，可能瓶颈不在 CPU。这个时候直接盯火焰图，容易优化一个不主导的问题。

如果 CPU 已经打满，再看 CPU profile 才更有意义。

## perf 的基本入口

Linux 上最常用的是 `perf`。

采样一个进程：

```bash
perf record -F 99 -p <pid> -g -- sleep 30
perf report
```

这里几个参数要注意：

- `-F 99`：采样频率。
- `-p <pid>`：目标进程。
- `-g`：采集调用栈。
- `sleep 30`：采样窗口。

采样频率不是越高越好。太低看不清，太高会增加开销，甚至影响被测程序。`99Hz` 是一个常见起点，因为它能避开某些周期性对齐问题。

如果是多线程服务，我会尽量在真实 workload 下采样。没有请求时采样，看到的可能只是 idle 或后台线程。

## 火焰图看的是“时间花在哪里”

火焰图横向宽度代表采样占比，不代表时间顺序。

这个点很重要。火焰图不是时间线，不要把左边理解成先发生，右边理解成后发生。

我会这样读：

```text
宽的函数
  -> CPU 时间占比高

高的栈
  -> 调用链深

顶部宽块
  -> 具体热点执行点

底部宽块
  -> 入口或上层框架占比大
```

优化时，我更关心宽的顶部块。底部框架函数宽，可能只是因为很多路径都经过它，不一定说明它本身慢。

## 符号很重要

火焰图如果只有一堆地址或 `[unknown]`，价值会大打折扣。

需要注意：

- 编译时是否保留 frame pointer。
- 是否有 debug symbols。
- JIT 语言是否支持 perf map。
- 容器里符号文件是否可见。
- 内核权限是否允许采样调用栈。

C/C++/Rust 服务里，frame pointer 对 profile 质量影响很大。没有可靠调用栈，热点会断在奇怪的位置。

性能优化经常不是从改业务代码开始，而是先让观测工具看清楚系统。

## 热点不等于 bug

看到热点以后，不要立刻改。

一个函数占 CPU 最高，可能只是因为它确实在做主要工作。比如压缩、序列化、hash、加密、矩阵计算，本来就该消耗 CPU。

我会先问：

- 这个热点是否符合预期。
- 它的输入规模是否异常。
- 是否有重复计算。
- 是否可以缓存。
- 是否可以减少拷贝。
- 是否可以换数据结构。
- 是否可以批量化。
- 是否可以下沉到更高效实现。

真正值得优化的热点，通常有“浪费”的味道：重复解析、无意义拷贝、锁内做重活、频繁分配、低效查找、日志过多、格式转换绕来绕去。

## 常见 CPU 问题

我见到或读到的 CPU 热点，很多会落在这些类型里。

第一，序列化和反序列化。

JSON、protobuf、字符串拼接、字段转换，都可能在高 QPS 下变成大头。

第二，内存分配。

频繁 malloc/free、对象逃逸、临时 buffer、容器扩容，都可能带来 CPU 和锁竞争。

第三，拷贝。

一次请求经过多层框架，每层都复制 buffer，最后业务逻辑还没开始，CPU 已经花掉不少。

第四，锁竞争。

锁竞争不一定在 CPU 火焰图里直接表现成业务函数宽，有时要结合 off-CPU profile 或 mutex profile。

第五，日志。

高频路径里格式化日志、拼字符串、同步写日志，会悄悄变成热点。

## On-CPU 和 Off-CPU

普通 CPU flamegraph 多数看的是 on-CPU：线程正在 CPU 上执行时，时间花在哪。

但很多延迟问题来自 off-CPU：线程没在跑，而是在等。

比如：

- 等 mutex。
- 等 condition variable。
- 等磁盘 I/O。
- 等网络。
- 等 epoll。
- 被调度器挂起。

如果服务 CPU 不高但延迟很高，我会考虑 off-CPU profiling。否则只看 on-CPU，很可能看不到真正等待点。

这也是为什么性能分析要先看整体资源，而不是直接打开一张火焰图开始找最大块。

## 优化要一次改一个变量

性能优化很容易越改越多。改完以后变快了，但不知道是哪一处生效；变慢了，也不知道是谁拖后腿。

我更喜欢：

```text
baseline
  -> profile
  -> one change
  -> benchmark
  -> compare
  -> keep or revert
```

每次只改一个主要因素。比如先减少一次拷贝，再改 batch size，再改锁粒度。每一步都留数字。

如果没有 baseline，优化很容易变成故事会。

## Benchmark 要贴近 profiling 场景

profile 和 benchmark 要对得上。

如果 profile 是线上真实流量，benchmark 却是本地单线程 mock 请求，优化结果可能不一致。

我会尽量保证：

- 请求类型接近。
- 并发度接近。
- 数据大小接近。
- 热点路径接近。
- 编译参数一致。
- CPU governor 和容器限制清楚。

CPU 优化特别怕“测了一个不存在的世界”。本地小样本证明某个函数快了，不代表线上 tail latency 会变好。

## 我会怎样写一次优化记录

我希望一条性能优化记录至少包含：

1. 背景：哪个服务、什么 workload、什么症状。
2. Baseline：吞吐、平均延迟、p99、CPU 使用率。
3. Profile：火焰图或 perf 结果指出哪个热点。
4. 假设：为什么这个热点可以优化。
5. 改动：具体减少了什么成本。
6. 结果：同样 workload 下指标变化。
7. 风险：是否改变语义，是否增加内存或复杂度。

这样以后回看时，优化不是“我记得当时快了”，而是一段可解释的工程证据。

## 小结

CPU 优化不是看见热点就手痒，而是一个证据闭环。profile 告诉你时间去哪了，benchmark 告诉你改动有没有用，代码 review 则提醒你不要为了一个小数字把系统复杂度抬得太高。

讲 Paxos 和 Raft，如果只说“多数派投票”，味道就不对。

工程里最危险的场景通常长这样：

```text
node A 是 leader
node A 和多数派断开
node B 在多数派里成为新 leader
node A 还活着，也还以为自己是 leader
```

问题不是谁票多。问题是：**旧 leader 还能不能继续写？旧消息晚到了怎么办？旧日志能不能覆盖新历史？外部存储会不会接受旧 leader 的写入？**

我现在读一致性协议，会先拿这个事故现场去套。

## 多数派交集让旧历史留下证人

5 个节点里，一个多数派至少 3 个节点。任意两个多数派一定相交：

```text
quorum 1: n1 n2 n3
quorum 2: n3 n4 n5
```

`n3` 的意义不是投票公平，而是历史证人。

如果某个值已经在一个多数派里被接受或提交，后续另一个多数派必然有机会遇到至少一个知道旧历史的节点。协议再通过 ballot/term 和日志规则，把这个旧历史带到新一轮里。

没有交集，就可能两个分区各自长出自己的历史。

## term / ballot 是权力版本号

旧 leader 能不能继续写，第一道门是 term 或 ballot。

```text
Paxos: ballot / proposal number
Raft:  term
```

节点一旦见过更高版本，就应该拒绝旧版本写入：

```text
follower has seen term 8
old leader sends term 7 AppendEntries
  -> reject
```

这不是简单的“新编号大于旧编号”。它是在给写权加版本。旧 leader 即使进程还活着，也不能带着旧 term 继续修改复制日志。

## Paxos 的 prepare 阶段是在逼新 leader 听旧历史

Paxos 里 prepare/promise 最容易被看成流程仪式。其实它在解决一个很具体的问题：新 proposer 不能随便覆盖可能已经被选定的旧值。

prepare 做两件事：

1. acceptor 承诺不再接受更低 ballot。
2. acceptor 返回自己接受过的最高 ballot value。

如果返回里已经有旧值，新 proposer 必须继承最高 ballot 的那个值。

```text
prepare ballot=10

acceptor A -> accepted ballot=6 value=x
acceptor B -> none
acceptor C -> accepted ballot=8 value=y

proposer must choose y
```

这条规则防住的是：旧值可能已经在某个多数派里形成决定，新一轮不能把它抹掉。

Paxos 难读，不是因为步骤多，而是因为安全性藏在“你不能自由选择新值”这种约束里。

## Raft 用日志匹配挡住错误后缀

Raft 的工程味更强。leader 复制日志，follower 接受日志，看起来直观很多。但真正要看的不是 happy path，而是 follower 如何拒绝不连续历史。

AppendEntries 会带：

```text
prevLogIndex
prevLogTerm
entries
leaderCommit
```

follower 只有在本地日志能对上 `prevLogIndex/prevLogTerm` 时，才接受后续 entries。

```text
leader:   [1:a] [2:b] [3:c] [4:d]
follower: [1:a] [2:b] [3:x]

append after [3:c]
  -> reject
  -> leader backs off
  -> find common prefix [1:a][2:b]
```

这条规则保证日志不是随便从某个 index 开始覆盖。不同节点要先找到共同前缀，再接上 leader 的后缀。

## old-term commit 是 Raft 里容易漏掉的一刀

Raft leader 不会仅仅因为旧 term 的 entry 复制到多数派，就直接用它推进 commit。它要等当前 term 的 entry 复制到多数派，再把前面的旧 entry 一起带上。

这个规则看着别扭，但它在避免一种危险：新 leader 对旧 term 日志的提交判断不够强，可能让后续 leader election 里的日志安全性变复杂。

更实用的理解是：

```text
current-term entry committed
  -> 当前 leader 的权力被多数派确认
  -> prefix before it becomes committed together
```

如果实现里忽略这个细节，系统可能在罕见选举交错下提交不该提交的旧日志。

## 选主成功不等于外部写安全

一致性协议能守住复制日志，但它不自动保护外部世界。

假设旧 leader 曾经拿到写外部存储的权限。网络分区后，新 leader 在多数派中产生。旧 leader 恢复时，如果外部存储还接受它的写入，就会发生 split-brain side effect。

所以工程系统需要 fencing token：

```text
leader term 8 -> token 8
external storage records max token = 8

old leader term 7 writes with token 7
  -> reject
```

这一步经常不在一致性协议的核心流程图里，但生产系统不能省。leader 的 epoch/term 必须传到它控制的外部资源。

## 我会怎么读实现

看 Raft/Paxos 实现时，我不会从正常复制流程开始，而会找这些入口：

- 节点什么时候持久化当前 term/ballot。
- 收到更高 term 时如何 step down。
- vote request 是否检查候选人的日志新旧。
- AppendEntries 在哪里校验 previous log。
- conflict 后如何回退。
- commit index 何时推进。
- old-term entry 是否被 current-term entry 间接提交。
- snapshot install 后日志前缀语义是否还成立。
- 对外资源有没有 fencing token。

能挡住旧 leader，才是真正理解了多数派、term 和日志匹配的意义。

## 最后记住的是写权，不是投票

Paxos/Raft 要守住的是一条不能被旧世界改写的历史。

多数派交集留下旧历史的证人，term/ballot 让旧 leader 失权，日志匹配防止错误后缀接上来，fencing token 把这个权力版本传到协议外部。

所以一致性协议不是“大家投票选一个值”，而是在一个消息会延迟、节点会恢复、leader 会过期的世界里，持续回答一句话：现在谁还有资格写。

Prefix Cache 命中一半 token，Prefill 就能快两倍——这个直觉只对**每个 token 成本相同**的线性计算成立。

完整因果 Attention（Full Causal Attention）不是这样。越靠后的 Query，能看到的 Key 越多：第一个 Query 只看一个位置，最后一个 Query 要看完整前缀。命中前 50% token，跳过的是 Attention 矩阵左上角较小的三角形，而不是一半面积。

本文只回答一个问题：**从逻辑前缀命中率出发，怎样逐层推导 Attention 剩余计算、完整 Prefill 的理想上界，以及最终需要实测的真实收益？**

## 先统一六个容易混用的术语

- **前缀命中率（Prefix hit ratio）**：索引逻辑匹配到的连续前缀 token 数与完整输入长度之比，本文记为 $\alpha$。它描述匹配结果，不保证状态已经可用。
- **可复用边界（Reusable boundary）**：所有续算必需状态都完整、版本一致并对齐到的最晚 token 边界。不同状态组共同可用时，通常取最短的那个边界。
- **有效复用（Effective reuse）**：运行时真正恢复成功并能够跳过计算的 token 范围。它不大于逻辑前缀匹配，还会受到页、检查点（checkpoint）与状态完整性的限制。
- **回载（Load-back）**：从本地或远端缓存找到对象后，把它读回运行时可消费的位置并完成必要同步的过程。
- **Attention 局部加速比（Attention-only speedup）**：基线 Attention FLOPs 与剩余 Attention FLOPs 的比值；不包含 MLP、投影、通信和缓存恢复。
- **完整 Prefill 加速比（Full-prefill speedup）**：完整 Prefill 基线成本与复用后端到端成本的比值；真实值应包含排队、回载、重放和运行时开销。

因此，**缓存命中不等于运行时已成功恢复**，逻辑前缀匹配也不等于实际可复用前缀。后文的 FLOPs 曲线是理想上界；除非明确写成实测，否则它们都不是 TTFT 或生产吞吐结论。

把完整输入长度记为 $N$，Prefix Cache 命中的长度记为 $P=\alpha N$。只看 Attention 主体时：

$$
\text{剩余 FLOPs}
=
1-\alpha^2,
$$

$$
\text{理想加速比}
=
\frac{1}{1-\alpha^2}.
$$

当 $\alpha=0.5$，仍有 $75\%$ 的 Attention FLOPs 需要执行，理想加速只有：

$$
\frac{1}{1-0.5^2}
=
\frac{1}{0.75}
\approx
1.33\times.
$$

## Prefix Cache 跳过的是旧 Query，不是旧 Key

没有 Prefix Cache 时，长度为 $N$ 的 Prefill 会形成一个下三角 Attention 矩阵。忽略对角线和常数项，其面积是：

$$
F_{\text{full}}
\propto
\int_0^N x\,dx
=
\frac{N^2}{2}.
$$

命中长度为 $P$ 的前缀后，前 $P$ 个 token 的各层输出与 KV 或 latent 状态已经存在，旧 Query 行不必重算。但新增的 Query 仍然要读取旧前缀的 Key/Value：

```text
已缓存的前缀 Query [0, P)
  不再执行

新增的后缀 Query [P, N)
  仍需读取 Key [0, 当前位置]
```

因此跳过的工作量是左上角边长为 $P$ 的旧三角形：

$$
F_{\text{skip}}
\propto
\frac{P^2}{2}.
$$

剩余工作量为：

$$
\begin{aligned}
F_{\text{remain}}
&=F_{\text{full}}-F_{\text{skip}}\\
&\propto\frac{N^2-P^2}{2}\\
&=\frac{N^2(1-\alpha^2)}{2}.
\end{aligned}
$$

除以完整 Prefill 的 $N^2/2$，就得到 $1-\alpha^2$。

这个推导揭示了一个容易忽略的事实：**Prefix 最前面的 token 最便宜，最后面的 token 最贵。** 命中 50% token 跳过的恰好是较便宜的 25% Attention 面积；剩下 50% Query 行包含了较长的历史依赖。

## 同一个命中率，在 MHA、MLA、SWA、KDA 上不是同一条曲线

Prefix Cache 的收益取决于 Attention 如何消费历史。下面的交互曲线统一把完整请求的 Attention 工作量归一化为 1，并比较三种理想模型：

- **MHA / MLA**：完整因果 Attention，剩余比例是 $1-\alpha^2$；
- **SWA**：只看最近窗口 $W$，本文可视化固定为 $W=0.25N$；
- **KDA 递推部分**：递推扫描与 token 数近似线性，但只能从不晚于命中位置的完整 checkpoint 继续。

### MHA、GQA、MQA 与 MLA：缓存表示变了，因果三角形没有消失

MHA、GQA 与 MQA 都保存逐 token 的 K/V，但共享粒度不同：MHA 为每个 Query Head 保存独立 K/V，GQA 让一组 Query Heads 共享 KV Head，MQA 则让所有 Query Heads 共享一组 K/V。这些变化会缩小缓存宽度，却不会改变 `新 Query → 全部历史状态` 的完整因果依赖。

MLA 进一步把历史压成 KV latent 与解耦 RoPE Key，显著改变每 token 的缓存宽度和读写方式。但只要主 Attention 仍对完整历史做因果 Attention，它的 Query-Key 依赖仍是下三角：

$$
R_{\text{MHA/MLA}}(\alpha)
=
1-\alpha^2.
$$

MLA 可以让缓存更小、内存流量更低，也可能改变内核常数；这些收益不能把前缀命中率公式直接改成 $1-\alpha$。

### SWA：上下文超过窗口后，边际成本趋向线性

滑动窗口 Attention（Sliding Window Attention）的第 $t$ 个 Query 最多读取 $W$ 个 Key。累计工作量可近似写成：

$$
A_W(x)
=
\begin{cases}
\frac{x^2}{2}, & x\le W,\\
Wx-\frac{W^2}{2}, & x>W.
\end{cases}
$$

命中比例为 $\alpha$ 时，剩余比例是：

$$
R_{\text{SWA}}(\alpha)
=
\frac{A_W(N)-A_W(\alpha N)}{A_W(N)}.
$$

当前缀和完整请求都远大于窗口，后续每个 token 的 Attention 成本接近固定的 $W$，于是曲线逐渐接近线性模型。这里仍不能只看逻辑命中率：SWA 的尾部状态、局部窗口页与其他 Attention 层必须落在同一个可恢复边界。

### KDA：递推计算可以线性跳过，恢复边界却必须对齐

KDA 一类线性 Attention 不再为每个 Query 回读完整历史，而是递推有限状态。若完整 Prefill 的递推扫描成本近似为 $O(N)$，逻辑匹配长度为 $P_{\text{match}}=\alpha N$，checkpoint 间隔为 $C$，能够直接恢复的位置要先向下对齐：

$$
P_{\text{eff}}
=
\left\lfloor\frac{P_{\text{match}}}{C}\right\rfloor C,
$$

$$
R_{\text{KDA-recurrence}}
=
\frac{N-P_{\text{eff}}}{N}.
$$

交互图默认取 $N=32768$、$C=4096$。例如逻辑命中率为 90% 时，匹配位置约为 29491，但最近 checkpoint 在 28672；递推部分至少还要处理 4096 个 token，所以理想上界是 8×，不是把 $1/(1-0.9)$ 直接算出的 10×。调整 checkpoint 间隔可以看到这条阶梯曲线如何变化。

这里的“存在 checkpoint”仍是强条件。一个可续算的 checkpoint 必须包含该边界完整的递推状态（recurrent state）；如果 ShortConv 或其他续算状态存在，也必须一起完整、版本一致且对齐。只有 token 哈希命中、只有 MLA 页命中，或只有递推矩阵存在，都不能证明请求能从该边界直接恢复。

曲线只计算递推部分的剩余 token，并假设对齐的 checkpoint 可立即使用。它忽略 checkpoint 查询、加载、跨层或跨设备传输、同步，以及恢复状态本身的成本；未对齐的前缀 token 已计入剩余 token，但没有额外建模 checkpoint 重放的实现开销。因此它是**精确对齐 checkpoint 条件下的理想上界**，不是生产环境收益预测。

## 现实中的 Attention 模式

上面的公式描述依赖模式，而不是某个模型版本。下面的家族名称只是帮助把抽象模式映射到常见实现；具体模型仍应以自己的配置和代码为准。

| 模式 | 代表性示例              | 缓存含义               |
| ---- | ----------------------- | ---------------------- |
| GQA  | Llama / Qwen / GLM 系列 | KV 缓存；因果几何不变  |
| MLA  | DeepSeek 系列           | 压缩 KV 状态（latent） |
| SWA  | Mistral 系列            | 滑动窗口历史复用       |
| KDA  | Kimi 系列               | 递推 checkpoint 状态   |

这张表不改变推导：先识别历史依赖是完整因果、滑动窗口还是递推，再选择对应的剩余计算量模型。

## 为什么逻辑命中还要经过可复用边界

Prefix Cache 能跳过计算的前提，不只是索引找到了相同 token。运行时必须恢复该 Attention 模式续算所需的完整状态：它可能是 KV 页、MLA latent、窗口尾部状态，或递推 checkpoint。下面的演进图用于比较这些恢复边界，而不是给模型做分类。

<AttentionStateEvolution />

这里的系统结论只有一个：对象或页的 `match`（匹配）只说明某个键存在；有效复用要求所有必需状态在同一 token 边界完整命中，并成功回载到执行引擎。对混合模型，最终可跳过的长度通常是各状态组共同连续前缀的最小值。

## Attention 加速不是完整 Prefill 加速

前面的 $1/(1-\alpha^2)$ 只描述完整因果 Attention 主体。Prefill 还包含词嵌入、归一化、QKV 投影、输出投影、MLP/MoE、集合通信与运行时调度。

假设基线 Transformer 模块 FLOPs 中 Attention 占比为 $\beta$，其余按 token 近似线性的算子占比为 $1-\beta$。忽略缓存开销时：

$$
R_{\text{attention}}=1-\alpha^2,
\qquad
R_{\text{token-wise}}=1-\alpha,
$$

$$
R_{\text{block}}
=
\beta(1-\alpha^2)
+
(1-\beta)(1-\alpha),
$$

$$
S_{\text{block, ideal}}
=
\frac{1}{R_{\text{block}}}.
$$

下面的交互把 Attention 主体、逐 token 算子与完整模块的理想 FLOPs 加速放在一起。默认 $\alpha=50\%$、$\beta=50\%$；此时模块剩余 62.5%，理想加速为 1.60×。同样在 50% 命中率下，$\beta=30\%,50\%,70\%$ 分别约为 1.74×、1.60×、1.48×：Attention 占比越高，前半段较便宜的因果三角形对整体加速的限制越明显。

<PrefillSpeedupExplorer />

这个完整模块 FLOPs 模型可以作为完整 Prefill 计算的第一层近似，但它仍不是端到端延迟模型。再把缓存查询、主机或存储加载、反序列化、H2D、同步、checkpoint 重放与调度等待归一化为 $h$，才可以粗略写成：

$$
S_{\text{e2e}}
\approx
\frac{1}
{\beta(1-\alpha^2)+(1-\beta)(1-\alpha)+h}.
$$

例如 $\alpha=0.5$、$\beta=0.6$ 且暂时令 $h=0$，剩余模型计算约为：

$$
0.6\times0.75
+
0.4\times0.5
=
0.65,
$$

对应约 $1.54\times$，仍不是 $2\times$。远端缓存的 $h$ 若大于省下来的计算，命中甚至可能比本地重算更慢。

这个模型只是建立量纲，不应替代性能剖析。FlashAttention 的分块、分块 Prefill（chunked prefill）、批次打包、Tensor Parallel 通信和 MoE 路由都会让真实曲线偏离连续面积模型。Attention FLOPs 加速比不等于 TTFT 加速比，理想上界也不等于生产吞吐。

## 把命中率变成可解释的性能指标

只上报一个 `prefix_hit_rate`，很难解释 TTFT。至少应把下面几层分开：

| 指标                | 回答的问题                                          |
| ------------------- | --------------------------------------------------- |
| 逻辑匹配 token 数   | Radix/hash 最长匹配到了多少 token？                 |
| 可恢复匹配 token 数 | 所有必需 Attention 状态共同完整到了哪个边界？       |
| 重放 token 数       | 因页或 checkpoint 粒度不对齐，需要补算多少 token？  |
| 状态查询与回载延迟  | 命中状态从元数据到设备可用花了多久？                |
| 后缀 Prefill 延迟   | 恢复后真正计算新 token 花了多久？                   |
| TTFT                | 排队、调度、传输、Prefill 与首 token 解码合计多久？ |

对完整因果 MHA/MLA，还可以同时上报一个由命中率推导出的 Attention 工作量指标：

$$
\text{避免的 Attention 工作量}
=
\alpha^2,
$$

而不是用 $\alpha$ 代替。这样 50% token 命中会明确显示为避免了 25% 的 Attention 工作量，监控、容量规划和性能回归分析就不会混用两个不同的量。

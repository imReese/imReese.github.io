Kimi Linear 的 prefix cache 不能只按普通 Transformer 的 KV block 来理解。模型里一部分层是 MLA，另一部分层是 KDA；前者需要一串可分页的 KV，后者需要“前缀处理到当前位置以后”的有限状态。工程难点不只是保存状态，而是让它与 token prefix、MLA page、scheduler step、HiCache 层级以及 Mooncake Store object 始终落在同一个逻辑边界。

本文沿两条实现链路展开：

```text
Kimi KDA
  ├─ SGLang: KDA kernel → UnifiedRadixCache → HiCache Host
  │            → MooncakeStore backend → Mooncake Distributed Store
  │
  └─ vLLM: KimiGatedDeltaNetAttention → HybridKVCacheCoordinator
               → MooncakeStoreConnector → Mooncake Distributed Store
```

核心结论是：**Mooncake Store 只负责按 key 保存和搬运 opaque bytes；KDA checkpoint 在哪个 token 边界产生、是否与 MLA prefix 对齐、缺失时是否补算，都由 SGLang 或 vLLM 的控制面决定。**

当前两套引擎采用不同的 checkpoint 创建策略：

```text
SGLang
  一个大 extend 可以让 KDA kernel 返回中间 recurrent states
  → runtime 从中抽取目标边界
  → radix node 持有 KDA/Mamba slot
  → HiCache 将 temporal + conv 写入 Mooncake

vLLM
  KDA prefill 通常只提交当前 scheduler step 的 final state
  → hybrid coordinator 发现 MLA/KDA 命中分歧
  → scheduler 在真正需要的边界提前结束 forward
  → 将该 final state 注册为 prefix checkpoint
```

两边都已具备完整 KDA checkpoint 的存储与传输数据面。真正尚未完全闭合的是 partial-group hit：当 MLA/KV 命中得更长、同边界 KDA state 却不存在时，runtime 是否能发现缺失边界，并只补算一次 KDA checkpoint。

## 2026-07-24 更新：Kimi K3 与细粒度 checkpoint

vLLM 在 2026 年 7 月合入了 hybrid model 的 fine-grained partial prefix-cache 支持，并发布了 [Kimi K3 serving 预览](https://vllm.ai/blog/2026-07-22-kimi-k3-preview)。增量实现主要见 [PR #46384](https://github.com/vllm-project/vllm/pull/46384)。这批变化进一步明确了三个必须分开的概念：

```text
physical state block size
  管理状态页的物理分配与 block table

prefix_match_unit
  决定 rolling hash 与 lookup 的最细 token 边界

actual checkpoint set
  只有 scheduler 真正停下、算子输出完整状态并注册 hash 的边界
```

例如：

```text
physical KDA block = 4096
prefix_match_unit  = 64
```

vLLM 可以在物理 block `[4096, 8192)` 内注册：

```text
H6976 → C(P6976)
```

`C(P6976)` 仍是一份完整的 `(ShortConv window, recurrent state)`。一个 physical state slot 只承载一个精确边界，并不会同时保存 `S4160、S4224、...、S6976`。一个 6976-token 请求可能保留物理边界 `C(P4096)` 和 partial tail `C(P6976)`，但不会因为 match unit 是 64 就自动生成 109 份状态。

当另一条请求命中 `P6976` 并继续 64 token 时：

```text
cached C(P6976) --Copy-on-Write--> request-private working state
                                      |
                                      +-- forward 64 tokens --> C(P7040)
```

共享的 `C(P6976)` 不会被原地更新成 `C(P7040)`。如果产生该 checkpoint 的原请求自己继续，vLLM 会把 `H6976 → C(P6976)` 迁移到 cache-owned copy，让原 working block 留在请求侧继续写。这是 owner-continue 场景下的反向 Copy-on-Write。

许多不同长度的请求理论上可以沿同一 prefix 链逐渐贡献：

```text
H64   → C(P64)
H128  → C(P128)
...
H8192 → C(P8192)
```

但这是多个请求形成的唯一 `(prefix hash, token length)` checkpoint 集合，不是单个请求自动保存所有中间状态。相同 prefix 会去重，实际驻留数量还受 creation policy、retention、state-pool 容量和 LRU eviction 限制。

最新 vLLM 也补上了一个本地控制面细节：当本地 cache group 命中分歧、connector 又没有返回 external tokens 时，scheduler 会回退到普通 hybrid fixed point，恢复各组一致的边界和 `shared_prefix_boundary`。剩余问题主要在远端 metadata：Mooncake Store lookup 返回最终协调后的 hit length 和 per-group load mask，但不会单独返回 MLA-only 更长命中对应的 missing KDA boundary。

K3 预览可以视为 cache-core 设计的确认；Dynamo + vLLM + Mooncake 的分离部署、offload 和大规模生产验证仍需要独立的端到端结果。

## KDA 的递推与充分状态

KDA 为每个 layer、每个 head 维护固定大小的关联记忆矩阵：

$$
\mathbf S_t \in \mathbb R^{d_k \times d_v}.
$$

对当前位置的 key、value 和 query：

$$
\boldsymbol{k}_t,\boldsymbol{q}_t \in \mathbb R^{d_k},
\qquad
\boldsymbol{v}_t \in \mathbb R^{d_v},
$$

KDA 先按 key channel 衰减旧状态，再计算旧记忆对当前 value 的预测误差，最后只写入 delta：

$$
\begin{aligned}
\overline{\mathbf S}_t
  &= \mathbf D_t \mathbf S_{t-1}, \\
\widehat{\boldsymbol{v}}_t
  &= \overline{\mathbf S}_t^\top \boldsymbol{k}_t, \\
\boldsymbol{e}_t
  &= \boldsymbol{v}_t-\widehat{\boldsymbol{v}}_t, \\
\mathbf S_t
  &= \overline{\mathbf S}_t
     +\beta_t\boldsymbol{k}_t\boldsymbol{e}_t^\top, \\
\boldsymbol{o}_t
  &= \mathbf S_t^\top\boldsymbol{q}_t.
\end{aligned}
$$

其中：

$$
\mathbf D_t=\operatorname{Diag}(\boldsymbol\alpha_t),
\qquad
\boldsymbol\alpha_t\in(0,1]^{d_k},
\qquad
\beta_t\in[0,1].
$$

等价地：

$$
\mathbf S_t
=
\left(\mathbf I-\beta_t\boldsymbol{k}_t\boldsymbol{k}_t^\top\right)
\mathbf D_t\mathbf S_{t-1}
+
\beta_t\boldsymbol{k}_t\boldsymbol{v}_t^\top.
$$

与普通 linear attention 的直接外积累加相比，delta rule 会先查看旧状态能否重建当前 value；只有预测错误的部分才被写回。KDA 又把 Gated DeltaNet 每个 head 一个标量遗忘率，细化成每个 key channel 一个遗忘率。

Q/K/V 并不是直接进入 recurrence。实际模型会先做线性投影、因果短卷积和激活，Q/K 还会做 L2Norm：

$$
\begin{aligned}
\boldsymbol{q}_t
&=\operatorname{L2Norm}\!\left(\operatorname{SiLU}(\operatorname{ShortConv}(W_qx)_t)\right),\\
\boldsymbol{k}_t
&=\operatorname{L2Norm}\!\left(\operatorname{SiLU}(\operatorname{ShortConv}(W_kx)_t)\right),\\
\boldsymbol{v}_t
&=\operatorname{SiLU}(\operatorname{ShortConv}(W_vx)_t).
\end{aligned}
$$

因此，一个 prefix `P_t` 的充分 KDA 状态不是只有矩阵 `S_t`，而是：

```text
C(P_t) = {
  每个 KDA layer 的 ShortConv 最近 kernel_size - 1 个 raw Q/K/V 投影,
  每个 KDA layer 的最终 recurrent matrix S_t
}
```

不需要跨请求持久化的量包括完整 prefix 的 q/k/v、逐 token alpha/beta、delta error，以及 prefill chunk 内的 WY/UT workspace。它们要么已折叠进 `S_t`，要么在当前 kernel 结束后失效。

这也解释了 prefix 复用的单向性：`C(P_1k)` 可以向前推进为 `C(P_2k)`，但只有 `C(P_4k)` 时无法倒推出 `C(P_1k)`。递推中的衰减和 delta correction 是有损更新，较早边界的 ShortConv window 也已经被覆盖。

## prefill 为什么能按 chunk 并行

逐 token recurrence 适合 decode，但 prefill 如果每个 token 启动一次 kernel，GPU 利用率会很差。KDA 将一个 kernel chunk 内的多个 transition 压缩成：

$$
\mathbf S_r=\mathbf P_r\mathbf S_0+\mathbf H_r,
\qquad
\mathbf P_r=\mathbf T_r\mathbf T_{r-1}\cdots\mathbf T_1.
$$

其中每个 transition 是 diagonal minus rank-1：

$$
\mathbf T_t
=
\mathbf D_t
-
\beta_t\boldsymbol{k}_t
\left(\boldsymbol{k}_t\odot\boldsymbol\alpha_t\right)^\top.
$$

KDA 利用 WY representation 和 UT transform，将 chunk 内的大部分工作转成矩阵乘法与小型下三角求解。论文与 SGLang Triton 实现常见的 `chunk_size=64` 是算子内部的计算 tile，不是 scheduler 的 chunked-prefill 大小，也不是 prefix checkpoint interval。

```text
KDA kernel chunk
  决定算子内部如何并行

scheduler prefill chunk
  决定一次 forward 处理多少 token

prefix checkpoint policy
  决定哪些 token 边界拥有可寻址的完整状态
```

三者必须分开理解。

## 一个逻辑 checkpoint 如何展开

对一个请求在 `P_t` 边界的模型级 checkpoint：

```text
C(P_t) = {
  S_l(t) | l 是一个 KDA layer
}
```

逻辑上它是一个 prefix hash、一个 token length 和一个状态 block id；物理上却由所有 KDA layer 的状态共同组成。

vLLM 把每层状态打包进 blocks-first raw page：

```text
raw page per KDA layer
  = conv_state bytes
  + recurrent_state bytes
  + optional padding
```

同一个逻辑 block id 在每个 KDA layer 的 page table 中索引出该层的状态。

SGLang 则让一个逻辑 Mamba slot 横跨所有 KDA layer：

```text
temporal buffer
  [num_kda_layers, slots, local_heads, head_dim, head_dim]

conv buffer
  [num_kda_layers, slots, kernel_size - 1, qkv_width]
```

因此：

```text
vLLM
  一个逻辑 checkpoint
  → 每个 KDA layer 各有一页 raw state

SGLang
  一个逻辑 checkpoint
  → 一个跨层 Mamba slot
  → temporal + 一个或多个 conv buffers
```

逻辑原子性不要求物理上只有一个 tensor 或 object。真正的约束是：所有 component 必须属于同一个 prefix hash 和 token boundary，并在 lookup 时被共同验证。

## SGLang：从大 extend 中抽取 checkpoint

SGLang 在需要追踪 prefix state 时，会让 KDA kernel 返回中间 recurrent states：

```python
core_attn_out = kernel_dispatcher.extend(
    ...,
    return_intermediate_states=track_ssm,
)

if track_ssm:
    core_attn_out, h = core_attn_out
    _track_mamba_state_extend(..., h, ssm_states, ...)
```

对应入口包括：

- [`KDAAttnBackend.forward_extend`](https://github.com/sgl-project/sglang/blob/297f9336c8bf81e2fcf06b930d2dd3551f7dec15/python/sglang/srt/layers/attention/linear/kda_backend.py#L390-L487)
- [`HybridLinearAttnBackend`](https://github.com/sgl-project/sglang/blob/297f9336c8bf81e2fcf06b930d2dd3551f7dec15/python/sglang/srt/layers/attention/hybrid_linear_attn_backend.py#L245-L315)

checkpoint 同时包含两部分：

```text
conv checkpoint
  从 mixed_qkv 中选取边界前最近 kernel_size - 1 行

recurrent checkpoint
  若边界等于 extend 末尾，复制 final state
  若边界位于 extend 中间，从 kernel 返回的 h 中抽取
```

所以 SGLang 不要求为了生成 1k checkpoint，就把 4k prefill 拆成四次模型 forward。一个大 extend 可以跨过目标边界，同时从内部 state 中抽出 `C(P_1k)`。

### checkpoint 怎样进入 UnifiedRadixCache

完成 forward 后，radix node 不直接保存整套 tensor，而是保存 pool slot：

```text
UnifiedTreeNode
  token key / page hashes
  Full component
    MLA/KV device indices
  Mamba component
    value       GPU Mamba slot
    host_value  HiCache Host Mamba slot
```

`MambaComponent.prepare_for_caching_req` 使用 `req.mamba_last_track_seqlen` 作为可提交长度，并把 tracking slot 捐给 radix cache。请求命中时：

```text
node.value 存在
  → checkpoint 仍在 GPU，可 CoW 到 request slot

node.host_value 存在
  → GPU state 已逐出，但 Host 副本仍可 load back
```

本地没有 HiCache controller 时，如果 Full/MLA prefix 比 KDA state 更长，`MambaComponent.finalize_match_result` 会产生 `mamba_branching_seqlen`。下一次 extend 可以继续按大预算执行，但 backend 会从中间 `h` 抽取这个分叉 checkpoint。

### HiCache 与 Mooncake 的数据面

对 hybrid model，HiCache 会同时迁移 Full/MLA KV 和 KDA sidecar：

```text
Full/MLA component
  GPU token/KV indices → Host KV indices

KDA component
  GPU Mamba slot → Host Mamba slot
```

写入 Mooncake 时，SGLang 不上传一串历史 `S_t`，只上传 radix node 末尾的一个 checkpoint。Mamba transfer 使用 `TRAILING_PAGES`，因为恢复目标 prefix 只需要末端 recurrent state，而 Full/MLA 仍要求前缀页连续存在。

Mooncake adapter 会将一个逻辑 KDA page 展开成：

```text
{base_key}_{rank}_temporal
{base_key}_{rank}_conv_0
{base_key}_{rank}_conv_1
...
```

`batch_exists_v2` 只有在 temporal 和全部 conv component 都存在时，才将该逻辑 checkpoint 视为命中；任一 component 缺失都必须判 miss。

恢复路径则反向执行：

```text
Mooncake exists
  → 协调 Full/MLA 连续页与 KDA trailing checkpoint
  → batch_get_into Host buffers
  → radix node.host_value
  → load_back / CoW 到请求 GPU slot
  → 从 C(P_t) 继续 suffix
```

### SGLang + HiCache 仍缺少 branching-state fill

数据面已经能完整读写 KDA checkpoint，但 HiCache 模式下的控制面暂时跳过 branching-state fill。具体来说：

```text
Mooncake 已有 MLA(P_1k) + C(P_1k)
  → 可以完整恢复并复用 P_1k

Mooncake 只有 MLA(P_1k)，没有 C(P_1k)
  → hybrid hit 必须缩短
  → 当前 HiCache 路径不会仅凭 MLA-only hit 自动要求
    KDA forward 在 P_1k 创建 checkpoint
```

问题不在 Mooncake 能否搬运 temporal/conv，而在于谁把 missing boundary 传给 scheduler/backend。

## vLLM：step-end state 与 scheduler split

vLLM 的 KDA prefill 路径会调用：

```text
chunk_kda_with_fused_gate(..., output_final_state=True)
  → last_recurrent_state
  → write back to current state slot
```

一次大 prefill 自然只产生该 scheduler step 末尾的 checkpoint。vLLM 的 Kimi 路径不像 SGLang 那样暴露 forward 内多个 chunk 的 `h`，因此缺失边界主要依靠 scheduler 让 forward 恰好停在那里。

Kimi Linear 使用 `mamba_cache_mode=align`。逻辑 block table 仍覆盖完整序列，但绝大多数位置可以是 null placeholder；运行中的请求只需维护少量 rolling state slots。

```text
step n
  previous state --copy--> current working state
  current working state --KDA forward--> C(P_end_n)

step n+1
  C(P_end_n) --copy--> next working state
  更早的 working slot 可被释放
```

当 step-end state 被赋予 prefix hash 后，它同时成为其他请求可命中的 checkpoint。KDA lookup 从目标 prefix 右侧向左寻找最近的 state block，不需要从 0 到该边界的所有历史 state。

### 第一次分叉请求为什么仍需重算

设：

```text
req1 = P_4k
req2 = P_1k + A_1k
req3 = P_1k + B_1k
```

req1 的大 prefill 可能留下：

```text
MLA pages: P_1k、P_2k、P_3k、P_4k
KDA state: 只有 C(P_4k)
```

req2 只共享前 1k，不能用含有后续 token 的 `C(P_4k)`。本地 coordinator 会看到：

```text
MLA hit = 1k
KDA hit = 0
final hybrid hit = 0
missing shared-prefix boundary = 1k
```

scheduler 将 req2 的首次 prefill 截到 1k。forward 结束后生成并注册 `C(P_1k)`，下一 step 再继续 req2 的 suffix。req3 到来时，MLA 与 KDA 就能在 1k 同时命中。

这里重算的是完整模型 forward，而不是只运行 KDA 层。第一次分叉请求付出一次补算成本，收益由后续共享同一 prefix 的请求获得。

### match、creation 与 retention 是三件事

`prefix_match_unit` 只决定 rolling hash 的可寻址粒度：

```text
prefix_match_unit = 64
  → 每 64 token 可以形成一个 hash boundary
```

它不意味着一次长 forward 会自动输出每个 64-token 边界的 KDA state。实际 checkpoint 必须来自：

```text
forward 恰好在该位置结束
算子显式导出中间状态
或从更早 checkpoint replay 到该位置
```

retention policy 只决定已经生成的 checkpoint 哪些继续留在 cache，也不能从 `C(P_4k)` 反向创建 `C(P_1k)`。

```text
creation policy  = scheduler step end / operator snapshot
match granularity = prefix_match_unit
retention policy = reachable-block selection + LRU
```

## MooncakeStoreConnector：可以存什么，缺的又是什么

vLLM 的共享 Store 路径按 cache group 建立 `ChunkedTokenDatabase`：

```text
PoolKey
  = model namespace
  + tp / pcp / dcp / pp rank
  + cache group id
  + chained prefix hash

value
  = 该 cache group physical block 对应的一组 memory segments
```

MLA group 和 KDA group 可以对同一 prefix hash 分别保存：

```text
prefix hash @ group=MLA
  → MLA page object(s)

prefix hash @ group=KDA
  → KDA raw state page(s)
```

如果 Store 中同时存在 `MLA(P_1k)` 和完整 `C(P_1k)`，external coordinator 可以得到完整 1k hit，并将两个 group 装入各自 GPU blocks。

### 远端 partial-group missing boundary

最新 vLLM 已能处理下面的本地情况：

```text
local MLA hit = 1k
local KDA hit = 0
external hit  = 0

→ fallback to hybrid fixed point
→ final local hit = 0
→ shared_prefix_boundary = 1k
→ scheduler 可以停在 1k 补 C(P_1k)
```

剩余缺口在远端 lookup。当前 `MooncakeStoreCoordinator` 对外主要返回：

```text
final reconciled hit length
per-group load mask
```

它不会同时返回：

```text
remote MLA-only longest hit
best remote KDA checkpoint
missing KDA boundary
```

因此：

```text
Store 已有 MLA(P_1k) + C(P_1k)
  → 可以完整命中 1k

Store 只有 MLA(P_1k)
  → final hybrid hit 被协调回更短边界
  → scheduler 不知道远端 MLA 曾命中到 1k
  → 不会仅凭这次 lookup 自动停在 1k 合成 C(P_1k)
```

要补齐这条链，需要 external lookup 保留 per-group hit 或直接返回 `missing_branching_boundary`，随后让 scheduler、partial-tail registration 和 Store save mask 共享同一个边界。

## 本地 HiCache 与 Mooncake 同时命中时怎样算长度

分层缓存场景中，不能把两个系统各自报告的“绝对最长 prefix”直接相加。正确方式是先得到本地统一锚点，再让 Mooncake 只查询 suffix。

设：

```text
L_device = GPU Radix 中所有必要 component 一致支持的 token 数
L_host   = Host HiCache 在同一路径上额外支持的 token 数
```

本地锚点：

$$
L_{\mathrm{local}}=L_{\mathrm{device}}+L_{\mathrm{host}}.
$$

Mooncake 从 `L_local` 之后查询：

```text
Attention/MLA 连续 pages
KDA 目标边界 checkpoint
其他 sidecar
所有 TP/PP/CP rank
```

外部 suffix 长度由所有必要 group 的共同边界决定：

$$
L_{\mathrm{store,delta}}
=
\min_g L_{g,\mathrm{suffix}}.
$$

候选总命中：

$$
L_{\mathrm{candidate}}
=
L_{\mathrm{local}}+L_{\mathrm{store,delta}}.
$$

但实际传输可能因为 timeout、best-effort、Host pool 不足或 rank 间不一致而变短。数据插入 Host Radix 后，权威结果应再次执行全 component match：

$$
L_{\mathrm{final}}
=
\operatorname{Rematch}(\mathrm{Device}+\mathrm{Host}+\mathrm{loaded\ Store\ data}).
$$

在稳定成功路径中，可以近似理解为：

```text
GPU hit + Host hit + Mooncake suffix hit = final prefix hit
```

KDA state slot 数不是 token 数，不能把 `mamba_host_hit_length=1` 当作“多命中一个 token”相加；它是该 token 边界有效性的必要条件。

## Attention page 与 KDA checkpoint 应怎样组织

Attention KV page 和 KDA checkpoint 应视为两种不同对象，而不是每个 KV page 都附带一份完整 KDA state。

```text
Attention KV Page Pool
  page 0
  page 1
  page 2
  ...

KDA Checkpoint Pool
  checkpoint @ L1
  checkpoint @ L2
  ...
```

三个粒度也应分开：

```text
P_KV
  Attention 的物理 page 大小

G_match
  prefix rolling hash / lookup 粒度

I_checkpoint
  KDA checkpoint 的实际保存密度
```

最终可跳过 forward 的长度不是单独由 page size 或 interval 决定，而是最近一个完整边界：

$$
L_{\mathrm{hit}}
=
\max\left\{
L\le L_{\mathrm{common}}:
\mathrm{KV}[0:L)\ \mathrm{complete}
\land
C(P_L)\ \mathrm{complete}
\right\}.
$$

如果 Attention KV 已存在到 6976，但只有 `C(P4096)`，那么仍需从 4096 replay 到请求末尾。常规 runtime 通常会在 lookup 阶段就把 KV hit 截断到 KDA boundary，避免无效加载更长 KV。

工程上可以选择：

```text
Attention page size      16 / 32 / 64
prefix match unit        16 / 32 / 64
periodic KDA checkpoint  512 / 1024 / 2048
```

并在 system prompt、chat turn、tool result、RAG 公共文档和请求 tail 等高价值边界额外保存 checkpoint。具体值要按状态大小、命中分布、replay 成本和状态池容量共同决定。

## Mooncake Store 的 object 与 group 语义

Mooncake Store 不理解 MLA、KDA 或 token span。它看到的是：

```text
object key → one or more memory slices
```

SGLang 可以把一个逻辑 KDA checkpoint 展开成 temporal 与若干 conv objects；vLLM 可以把每层 raw state page 作为 cache group object。Mooncake 只负责对象存在性、放置、传输和生命周期。

不同大小、不同 token span 的 KV 与 KDA objects 可以使用相同 group id，改善 metadata locality、lease refresh 和 best-effort eviction。但 group 不是事务：

```text
不保证全部成员原子可见
不保证全部成员全有全无地淘汰
不知道预期成员总数
```

因此，完整性仍由上层 coordinator 保证。读取时必须检查所有必要 objects；写入时更稳妥的协议是 components first、manifest/commit last；显式失效则先删除 manifest，再异步回收 component objects。

通常不应把从 0 到 L 的所有 KV pages 和 `C(P_L)` 放进一个巨型重叠 group。更合理的是：

```text
KV pages
  独立 content-addressed objects

KDA checkpoint components
  同一 boundary / rank / model namespace 下组成一个 group

Prefix manifest
  关联 prefix length、KV page refs、KDA refs 与 layout metadata
```

同一个 Mooncake 集群也不意味着 SGLang 与 vLLM 可以直接互读：两者的 key namespace、rank 编码、layer 顺序、dtype、shape、byte layout 和 checkpoint policy 都不同。跨引擎复用需要额外定义稳定的公共 ABI。

## 能力边界

```text
能力                         SGLang 本地   SGLang + HiCache/Mooncake
KDA prefix correctness       已支持        完整 checkpoint 数据面已支持
大 forward 抽中间 state     已支持        kernel 基础存在
完整 checkpoint 远端读写    不适用        temporal/conv put/get 已实现
缺失分叉 state 自动补算      已支持        HiCache 模式暂时跳过
Kimi + Mooncake 专项 e2e     不适用        仍需进一步验证

能力                         vLLM 本地     vLLM + MooncakeStoreConnector
KDA raw state page           已支持        数据结构可承载
细粒度 partial checkpoint   已支持        external 路径仍需完整验证
partial hit 后 CoW           已支持        取决于 connector / load path 对齐
完整 checkpoint 远端读写    不适用        接口允许，专项 e2e 仍有限
远端 MLA-only 自动补 KDA     不适用        missing boundary 尚未返回
```

两边都应该覆盖同一组测试：

```text
local branch fill
  req1=4k，req2/req3 分别共享 1k

remote complete hit
  Store 同时存在 MLA(P_1k) 与 C(P_1k)
  replay logits 与无缓存 baseline 一致

remote partial-group hit
  Store 只有 MLA(P_1k)
  req2 只付一次补算并上传 C(P_1k)
  req3 在另一实例完整命中

  temporal/conv 或 raw-page 任一必要部分缺失都必须判 miss
```

## 配置时怎样理解相关旋钮

### SGLang

```text
--mamba-radix-cache-strategy extra_buffer
  使用额外 tracking slot 保存 prefix checkpoint

--page-size
  radix / HiCache page 粒度，也参与可追踪边界对齐

--mamba-track-interval
  状态追踪间隔，不等同于强制 prefill forward 大小

--chunked-prefill-size
  scheduler prefill budget，可以大于 checkpoint 粒度

--enable-hierarchical-cache
--hicache-storage-backend mooncake
  启用 GPU → Host → Mooncake 链路
```

### vLLM

```text
enable_prefix_caching
  启用 hybrid prefix cache

mamba_cache_mode=align
  Kimi Linear 的实际状态物化模式

enable_chunked_prefill
  允许 scheduler 在必要边界结束 step

max_num_batched_tokens
  可以保持较大，不要求机械按 checkpoint interval 切分

prefix_match_unit
  调整可寻址 hash 粒度，不自动创建 state

VLLM_PREFIX_CACHE_RETENTION_INTERVAL
  调整已经创建的 checkpoint 保留密度，不补历史 state
```

验证时不要一开始就把 prefill budget 降到 1k，否则无法区分“按需补点生效”和“所有请求本来就被机械切成 1k”。对于 Mooncake，也不能只检查 object key 是否出现；还应验证 component 完整性、hybrid hit length、missing-boundary 传播、CoW 和 replay logits。

## 最终判断

回到 req1/req2 示例，可以分三层判断：

> req1 的 4k prefill 如果只留下 `C(P_4k)`，req2 第一次共享 1k 时确实必须重新计算这 1k；`C(P_4k)` 无法回滚，MLA pages 也不能替代 KDA state。

> SGLang 本地可以让 req2 的大 extend 跨过 1k，再从 kernel 返回的中间 state 抽出并插入 `C(P_1k)`；vLLM 本地则把 req2 动态截到 1k，利用 step end 补出并注册 `C(P_1k)`。两边都不要求把所有请求的 prefill budget 固定成 1k。

再加上外部缓存限定：

> SGLang + HiCache 已把 temporal/conv checkpoint 接到 Mooncake 的完整读写数据面，但 HiCache 模式仍暂时跳过 branching-state fill。vLLM 最新 main 已支持本地 cache-group divergence 且 connector miss 时的 fixed-point fallback，也支持 physical block 内的 fine-grained partial checkpoint 与 Copy-on-Write；但 MooncakeStoreCoordinator 的远端 lookup 仍不单独返回 MLA-only 更长命中对应的 missing KDA boundary。两条链都能复用一个已经存在且完整的 `C(P_t)`，但远端只有 MLA 命中、缺少 KDA checkpoint 时，仍不会仅凭这次 lookup 自动补算该状态。

优化目标不是机械地每隔 1k 切一次 forward，而是在出现可复用分叉时只补算一次，并把同一个边界持续传递到本地 radix/scheduler、Host staging、Mooncake key/value、lookup 与 retention policy。对 vLLM 而言，还要始终区分 physical state block、prefix match unit 与实际 checkpoint 集合：细粒度可寻址不等于细粒度状态自动生成；checkpoint 一旦发布就应保持不可变，后续扩展通过 CoW 产生新的 working state 或新 checkpoint。

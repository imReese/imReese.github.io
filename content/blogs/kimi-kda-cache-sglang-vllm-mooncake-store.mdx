Kimi Linear 的 prefix cache 不能只按普通 Transformer 的 KV block 来理解。模型里一部分层是 MLA，另一部分层是 KDA：前者需要一串可分页的 KV/latent pages，后者需要“前缀处理到当前位置以后”的有限状态。工程难点不只是保存数据，而是让 token prefix、MLA pages、KDA checkpoint、scheduler step、HiCache 层级和 Mooncake Store objects 始终落在同一个逻辑边界。

本文沿两条实现链路展开：

```text
Kimi KDA
  ├─ SGLang: KDA kernel → UnifiedRadixCache → HiCache Host
  │            → MooncakeStore backend → Mooncake Distributed Store
  │
  └─ vLLM: KimiGatedDeltaNetAttention → HybridKVCacheCoordinator
               → MooncakeStoreConnector → Mooncake Distributed Store
```

核心结论是：**Mooncake Store 负责保存、放置和搬运 opaque bytes；KDA checkpoint 在哪个 token 边界产生、是否与 MLA prefix 对齐、缺失时是否补算，仍由 SGLang 或 vLLM 的控制面决定。**

两套引擎采用不同的 checkpoint 创建方式：

```text
SGLang
  一个大 extend 可以让 KDA kernel 返回 chunk-aligned 中间状态
  → runtime 从中抽取目标边界
  → radix node 持有 KDA/Mamba slot
  → HiCache 将 temporal + conv 写入 Mooncake

vLLM
  KDA prefill 通常只提交当前 scheduler step 的 final state
  → hybrid coordinator 发现 MLA/KDA 命中分歧
  → scheduler 在真正需要的边界提前结束 forward
  → 将该 final state 注册为 prefix checkpoint
```

SGLang 已有显式的 temporal/conv 远端读写链路；vLLM 的 raw-page/cache-group 结构也能够承载完整 KDA checkpoint，通用 Mooncake 传输基础设施已经存在，但 Kimi KDA + MooncakeStoreConnector 的专项调用链证据仍有限。共同尚未完全闭合的是 partial-group hit：当 MLA/KV 命中得更长、同边界 KDA state 却不存在时，runtime 是否能发现缺失边界，并只补算一次 checkpoint。

## 先统一记号：矩阵状态不等于完整 checkpoint

记 tokenizer 产生的前 `t` 个 token ID 组成的 prefix 为：

$$
P_t=(\tau_1,\tau_2,\ldots,\tau_t),
\qquad
\tau_i\in\{0,\ldots,|\mathcal V|-1\}.
$$

这里的 $\tau_i$ 是 token ID。后面 KDA 公式中的 $x_t^{(l)}$ 才表示第 $l$ 层当前位置的归一化 hidden state，二者不能混为一谈。

对第 `l` 个 KDA layer，定义：

$$
\mathbf S_l(t)
\in
\mathbb R^{
n_{h,l}^{\mathrm{local}}
\times d_{k,l}\times d_{v,l}
}
$$

为处理完 `P_t` 后的 recurrent matrices。定义同一边界上的 ShortConv window：

$$
\Gamma_l(t)
\in
\mathbb R^{
(w_l-1)\times d_{\mathrm{qkv},l}^{\mathrm{local}}
}.
$$

这里 $w_l$ 是 causal convolution kernel size；conv window 的物理实现也可能使用转置布局 `[dim, state_len]`。

本文按数学语义将 $\mathbf S_l(t)$ 记作 `[local_heads, d_k, d_v]`。部分 kernel 和 state pool 的物理 layout 使用 `[local_heads, d_v, d_k]`，即最后两个维度转置存放；两种 layout 表示同一个关联状态。

一个 KDA layer 的完整续算状态是：

$$
C_l(t)=\left(\Gamma_l(t),\mathbf S_l(t)\right).
$$

整个模型在 prefix `P_t` 上的 KDA checkpoint 是：

$$
\boxed{
C(P_t)=\left\{C_l(t)\mid l\in\text{KDA layers}\right\}.
}
$$

后文中的 $\mathbf S_l(t)$ 始终只表示 recurrent matrices；$C_l(t)$ 才表示某一层完整的 conv + recurrent state；$C(P_t)$ 则表示所有 KDA layers 在同一 token 边界上的 checkpoint。

MLA pages 不属于 `C(P_t)`。对 Kimi Linear 这样的 hybrid model，一个可直接恢复的 prefix 还必须同时拥有：

```text
MLA / Full Attention cache [0, t)
+
KDA checkpoint C(P_t)
+
其他必要 sidecar 与所有并行 rank 数据
```

## KDA 的递推与充分状态

对单个 head，KDA 维护固定大小的关联记忆矩阵：

$$
\mathbf S_t\in\mathbb R^{d_k\times d_v}.
$$

当前位置的 key、value 和 query 分别是：

$$
\boldsymbol{k}_t,\boldsymbol{q}_t\in\mathbb R^{d_k},
\qquad
\boldsymbol{v}_t\in\mathbb R^{d_v}.
$$

KDA 先按 key channel 衰减旧状态，再计算旧记忆对当前 value 的预测误差，最后只写入 delta：

$$
\begin{aligned}
\overline{\mathbf S}_t
  &=\mathbf D_t\mathbf S_{t-1},\\
\widehat{\boldsymbol{v}}_t
  &=\overline{\mathbf S}_t^\top\boldsymbol{k}_t,\\
\boldsymbol{e}_t
  &=\boldsymbol{v}_t-\widehat{\boldsymbol{v}}_t,\\
\mathbf S_t
  &=\overline{\mathbf S}_t
    +\beta_t\boldsymbol{k}_t\boldsymbol{e}_t^\top,\\
\boldsymbol{o}_t
  &=\mathbf S_t^\top\boldsymbol{q}_t.
\end{aligned}
$$

其中：

$$
\mathbf D_t=\operatorname{Diag}(\boldsymbol\alpha_t),
\qquad
\boldsymbol\alpha_t\in(0,1]^{d_k},
\qquad
\beta_t\in[0,1].
$$

等价地：

$$
\mathbf S_t
=
\left(\mathbf I-\beta_t\boldsymbol{k}_t\boldsymbol{k}_t^\top\right)
\mathbf D_t\mathbf S_{t-1}
+
\beta_t\boldsymbol{k}_t\boldsymbol{v}_t^\top.
$$

与普通 linear attention 的直接外积累加相比，delta rule 会先查看旧状态能否重建当前 value；只有预测错误的部分才被写回。KDA 又把 Gated DeltaNet 每个 head 一个标量遗忘率，细化成每个 key channel 一个遗忘率。

Q/K/V 并不是直接进入 recurrence。对第 $l$ 层的输入 $x_t^{(l)}$，实际模型会先做线性投影、因果短卷积和激活，Q/K 还会做 L2Norm：

$$
\begin{aligned}
\boldsymbol{q}_t
&=\operatorname{L2Norm}\!\left(
  \operatorname{SiLU}(\operatorname{ShortConv}(W_qx^{(l)})_t)
\right),\\
\boldsymbol{k}_t
&=\operatorname{L2Norm}\!\left(
  \operatorname{SiLU}(\operatorname{ShortConv}(W_kx^{(l)})_t)
\right),\\
\boldsymbol{v}_t
&=\operatorname{SiLU}(\operatorname{ShortConv}(W_vx^{(l)})_t).
\end{aligned}
$$

因此只有 recurrent matrix、没有 ShortConv window，并不足以继续计算下一个 token。

不需要跨请求持久化的量包括：

```text
完整 prefix 的 q/k/v
逐 token alpha / beta / delta error
prefill chunk 内的 WY / UT workspace
attention 输出与 output gate 中间量
```

它们要么已经被折叠进 $\mathbf S_l(t)$，要么在当前 kernel 结束后失效。

这也解释了 prefix 复用的单向性：`C(P_1k)` 可以随 suffix 向前推进成 `C(P_2k)`，但只有 `C(P_4k)` 时无法倒推出 `C(P_1k)`。递推中的衰减和 delta correction 是有损更新，较早边界的 ShortConv window 也已经被覆盖。

## prefill 为什么能按 chunk 并行

逐 token recurrence 适合 decode，但 prefill 如果每个 token 启动一次 kernel，GPU 利用率会很差。KDA 将一个 kernel chunk 内的多个 transition 压缩成：

$$
\mathbf S_r=\mathbf P_r\mathbf S_0+\mathbf H_r,
\qquad
\mathbf P_r=\mathbf T_r\mathbf T_{r-1}\cdots\mathbf T_1.
$$

其中每个 transition 是 diagonal minus rank-1：

$$
\mathbf T_t
=
\mathbf D_t
-
\beta_t\boldsymbol{k}_t
\left(\boldsymbol{k}_t\odot\boldsymbol\alpha_t\right)^\top.
$$

KDA 利用 WY representation 和 UT transform，将 chunk 内的大部分工作转成矩阵乘法与小型下三角求解。论文与 SGLang Triton 实现常见的 `chunk_size=64` 是算子内部的计算 tile，不是 scheduler 的 chunked-prefill 大小，也不是 prefix checkpoint interval。

## 一个逻辑 checkpoint 如何展开

逻辑上，一个 checkpoint 由 prefix hash、精确 token length 和 `C(P_t)` 组成；物理上，它由所有 KDA layers 的状态共同构成。

vLLM 在固定快照中把每层状态放进 blocks-first raw page：

```text
raw page per KDA layer
  = conv_state bytes
  + recurrent_state bytes
  + optional padding
```

同一个逻辑 block id 在每个 KDA layer 的 page table 中索引出该层的 `C_l(t)`。

SGLang 则让一个逻辑 Mamba slot 横跨所有 KDA layers：

```text
temporal buffer
  [num_kda_layers, slots, local_heads, d_v, d_k]

conv buffer
  [num_kda_layers, slots, kernel_size - 1, qkv_width]
```

所以：

```text
vLLM
  C(P_t)
  → 每个 KDA layer 各有一页 raw state

SGLang
  C(P_t)
  → 一个跨层 Mamba slot
  → temporal + 一个或多个 conv buffers
```

逻辑原子性不要求物理上只有一个 tensor 或 object。真正的约束是：所有 components 必须属于同一个 prefix hash 和 token boundary，并在 lookup 时共同验证。

## Kimi K3 预览与 vLLM 的细粒度 checkpoint

截至该代码快照，vLLM 的 [PR #46384](https://github.com/vllm-project/vllm/pull/46384) 已合入；同日 vLLM 发布了 [Kimi K3 serving 预览](https://vllm.ai/blog/2026-07-22-kimi-k3-preview)。这批变化进一步明确了三个必须分开的概念：

```text
physical state block size
  管状态页的物理分配与 block table

prefix_match_unit
  管 rolling hash 与本地 lookup 的最细 token 边界

actual checkpoint set
  只有真正物化并注册 hash 的 C(P_t)
```

下面的 `4096 / 64 / 6976` 只是解释机制的示意值，不是 K3 的默认配置：

```text
physical KDA block = 4096
prefix_match_unit  = 64
```

vLLM 的本地 prefix cache 可以在物理 block `[4096, 8192)` 内注册：

```text
Hash(P6976) → C(P6976)
```

一个 physical state slot 只承载一个精确边界，并不会同时保存 `S4160、S4224、...、S6976`。一个 6976-token 请求可能保留物理边界 `C(P4096)` 和 partial tail `C(P6976)`，但不会因为 match unit 是 64 就自动生成 109 份状态。

配置的 match unit 必须整除每个 cache group 的 physical block size；若未显式配置，vLLM 可以从各 group block size 的公约数推导匹配粒度。

当另一条请求命中 `P6976` 并继续 64 token 时：

```text
cached C(P6976) --Copy-on-Write--> request-private working state
                                      |
                                      +-- forward 64 tokens --> C(P7040)
```

共享的 `C(P6976)` 不会被原地更新成 `C(P7040)`。如果产生该 checkpoint 的原请求自己继续，vLLM 会把 `Hash(P6976) → C(P6976)` 迁移到 cache-owned copy，让原 working block 留在请求侧继续写。这是 owner-continue 场景下的反向 Copy-on-Write。

许多不同长度的请求理论上可以沿同一 prefix 链逐渐贡献：

```text
Hash(P64)   → C(P64)
Hash(P128)  → C(P128)
...
Hash(P8192) → C(P8192)
```

但这是多个请求形成的唯一 `(prefix hash, token length)` checkpoint 集合，不是单个请求自动保存所有中间状态。相同 prefix 会去重，实际驻留数量还受 creation、retention、state-pool 容量和 LRU eviction 限制。

## checkpoint 的创建、匹配和保留是三件事

定义实际驻留的 KDA checkpoint 集合：

$$
\mathcal C_{\mathrm{KDA}}
=
\left\{
(\mathsf H_L,L)
\mid
C(P_L)\text{ 已物化、已注册且仍驻留}
\right\},
$$

其中 $\mathsf H_L=\operatorname{Hash}(P_L)$。

三类机制分别负责：

```text
match granularity
  哪些 L 可以形成 rolling hash 并参与 lookup

creation policy
  哪些 L 真正生成了 C(P_L)
  例如 scheduler step end、operator snapshot 或 replay

retention policy
  已生成的 C(P_L) 中，哪些继续留在 state pool
```

`prefix_match_unit=64` 只表示每 64 token 可以形成 hash boundary，不表示一次长 forward 会自动生成所有 64-token 边界的 KDA state。retention 也只能筛选已经生成的 checkpoint，不能从 `C(P_4k)` 反向创造 `C(P_1k)`。

更小的 match unit 也不是完全免费：它不会自动分配更多 recurrent-state pages，但会增加 block hashes、radix/lookup metadata 和候选 partial-tail 边界数量，从而扩大可被实际物化的 checkpoint 集合。

对固定快照中的 MooncakeStoreCoordinator，还存在物理对齐约束：每个 cache-group block size 必须能被 hash block size 整除，scheduler block size 又必须是各 cache-group block size 的整数倍。

### checkpoint state pool 的内存成本

使用当前 TP/PP shard 上的局部维度，单个 KDA layer 的 recurrent-state 字节数可写成：

$$
B_{\mathrm{rec},l}
=
n_{h,l}^{\mathrm{local}}
\,d_{k,l}
\,d_{v,l}
\,b_{\mathrm{rec},l}.
$$

ShortConv window 的字节数近似为：

$$
B_{\mathrm{conv},l}
=
(w_l-1)
\,d_{\mathrm{qkv},l}^{\mathrm{local}}
\,b_{\mathrm{conv},l}.
$$

一份完整模型 checkpoint 的逻辑大小是：

$$
B_{\mathrm{logical}}
=
\sum_{l\in\mathrm{KDA}}
\left(
B_{\mathrm{rec},l}+B_{\mathrm{conv},l}
\right).
$$

若 state pool 中驻留 `N` 个唯一 prefix checkpoints：

$$
M_{\mathrm{logical\ pool}}
\approx
N\,B_{\mathrm{logical}}.
$$

对 vLLM 这类“每层一个 raw state page”的布局，完整物理 checkpoint 的大小应按所有相关层的物理页求和：

$$
B_{\mathrm{physical\ checkpoint}}
=
\sum_{l\in\mathrm{KDA}}
B_{\mathrm{physical\ page},l}
\ge
B_{\mathrm{logical}}.
$$

每层物理页还可能包含 allocator padding、page alignment 和统一 page-byte-size 带来的尾部空间。CoW 的峰值显存与总复制字节数应按完整 physical checkpoint 估算，而不是只按数学状态估算。固定 vLLM 快照中，KDA 的 conv state 使用配置的 cache dtype，而 recurrent state 使用 FP32。

## SGLang：从大 extend 中抽取 checkpoint

SGLang 在需要追踪 prefix state 时，会让 KDA kernel 返回中间 recurrent states：

```python
core_attn_out = kernel_dispatcher.extend(
    ...,
    return_intermediate_states=track_ssm,
)

if track_ssm:
    core_attn_out, h = core_attn_out
    _track_mamba_state_extend(..., h, ssm_states, ...)
```

固定源码入口包括：

- [`KDAAttnBackend.forward_extend`](https://github.com/sgl-project/sglang/blob/4f88206393b620f5a856c8719289cf845a72b4fb/python/sglang/srt/layers/attention/linear/kda_backend.py)
- [`HybridLinearAttnBackend`](https://github.com/sgl-project/sglang/blob/4f88206393b620f5a856c8719289cf845a72b4fb/python/sglang/srt/layers/attention/hybrid_linear_attn_backend.py)
- [`FlashKDA wrapper`](https://github.com/sgl-project/sglang/blob/4f88206393b620f5a856c8719289cf845a72b4fb/python/sglang/srt/layers/attention/linear/kernels/kda_flashkda.py)

checkpoint 同时包含两部分：

```text
conv checkpoint
  从 mixed_qkv 中选取边界前最近 kernel_size - 1 行

recurrent checkpoint
  若边界等于 extend 末尾，复制 final state
  若边界位于 extend 中间，从 kernel 返回的 h 中抽取
```

但“从大 extend 抽中间状态”并不表示可以抽任意 token。固定实现先把目标长度向下对齐到 `mamba_cache_chunk_size`：

$$
L_{\mathrm{track}}
=
L_{\mathrm{prefix}}
+
\left\lfloor
\frac{L_{\mathrm{target}}-L_{\mathrm{prefix}}}
{C_{\mathrm{kernel}}}
\right\rfloor
C_{\mathrm{kernel}}.
$$

- 目标边界与 KDA chunk 对齐时，直接复制 final recurrent state。
- 目标边界位于 extend 中间时，从 `h` 中取最近的 chunk boundary state。
- 源码仍有 `mamba_cache_chunk_size % page_size != 0` 的 TODO，因此 kernel chunk 与 page size 不能任意组合。

如果配置了 FlashKDA，但 runtime 请求 `return_intermediate_states=True`，固定 SGLang wrapper 会回退到 Triton `chunk_kda`。FlashKDA 负责高性能 final-state prefill；中间 checkpoint tracking 依赖能够返回 `h` 的 Triton 路径。

所以 SGLang 不要求为了生成 1k checkpoint，就把 4k prefill 拆成四次模型 forward；但实际抽取的是合法的 chunk/page-aligned 边界，而不是任意 token。

### checkpoint 怎样进入 UnifiedRadixCache

完成 forward 后，radix node 不直接保存整套 tensor，而是保存 pool slot：

```text
UnifiedTreeNode
  token key / page hashes
  Full component
    MLA/KV device indices
  Mamba component
    value       GPU Mamba slot
    host_value  HiCache Host Mamba slot
```

`MambaComponent.prepare_for_caching_req` 使用 `req.mamba_last_track_seqlen` 作为可提交长度，并把 tracking slot 捐给 radix cache。请求命中时：

```text
node.value 存在
  → checkpoint 仍在 GPU，可 CoW 到 request slot

node.host_value 存在
  → GPU state 已逐出，但 Host 副本仍可 load back
```

本地没有 HiCache controller 时，如果 Full/MLA prefix 比 KDA state 更长，`MambaComponent.finalize_match_result` 会产生 `mamba_branching_seqlen`。下一次 extend 可以继续按大预算执行，但 backend 会从中间 `h` 抽取这个分叉 checkpoint。

固定实现见 [`mamba_component.py`](https://github.com/sgl-project/sglang/blob/4f88206393b620f5a856c8719289cf845a72b4fb/python/sglang/srt/mem_cache/unified_cache_components/mamba_component.py)。

### HiCache 与 Mooncake 的数据面

对 hybrid model，HiCache 会同时迁移 Full/MLA KV 和 KDA sidecar：

```text
Full/MLA component
  GPU token/KV indices → Host KV indices

KDA component
  GPU Mamba slot → Host Mamba slot
```

写入 Mooncake 时，SGLang 不上传一串历史 $\mathbf S_l(t)$，只上传 radix node 末尾的一个 `C(P_t)`。Mamba transfer 使用 `TRAILING_PAGES`，因为恢复目标 prefix 只需要末端 KDA checkpoint，而 Full/MLA 仍要求前缀 pages 连续存在。

Mooncake adapter 会将一个逻辑 KDA page 展开成：

```text
{base_key}_{rank}_temporal
{base_key}_{rank}_conv_0
{base_key}_{rank}_conv_1
...
```

`batch_exists_v2` 只有在 temporal 和全部 conv components 都存在时，才将该逻辑 checkpoint 视为命中；任一 component 缺失都必须判 miss。固定实现见 [`mooncake_store.py`](https://github.com/sgl-project/sglang/blob/4f88206393b620f5a856c8719289cf845a72b4fb/python/sglang/srt/mem_cache/storage/mooncake_store/mooncake_store.py)。

恢复路径反向执行：

```text
Mooncake exists
  → 协调 Full/MLA 连续 pages 与 KDA trailing checkpoint
  → batch_get_into Host buffers
  → radix node.host_value
  → load_back / CoW 到请求 GPU slot
  → 从 C(P_t) 继续 suffix
```

### SGLang + HiCache 仍缺少 branching-state fill

数据面已经能完整读写 KDA checkpoint，但固定快照中的 HiCache 模式会暂时跳过 branching-state fill：

```text
Mooncake 已有 MLA(P_1k) + C(P_1k)
  → 可以完整恢复并复用 P_1k

Mooncake 只有 MLA(P_1k)，没有 C(P_1k)
  → hybrid hit 必须缩短
  → 当前 HiCache 路径不会仅凭 MLA-only hit 自动要求
    KDA forward 在 P_1k 创建 checkpoint
```

问题不在 Mooncake 能否搬运 temporal/conv，而在于谁把 missing boundary 传给 scheduler/backend。

## vLLM：step-end state 与 scheduler split

vLLM 的 KDA prefill 路径会调用：

```text
chunk_kda_with_fused_gate(..., output_final_state=True)
  → last_recurrent_state
  → write back to current state slot
```

固定源码入口见 [`kimi_gdn_linear_attn.py`](https://github.com/vllm-project/vllm/blob/1a659a0c370942bae3c8567902e38bddbbae95f3/vllm/model_executor/layers/mamba/gdn/kimi_gdn_linear_attn.py)。

一次大 prefill 自然只产生该 scheduler step 末尾的 checkpoint。vLLM 的 Kimi 路径不像 SGLang 那样暴露 forward 内多个 chunk 的 `h`，因此缺失边界主要依靠 scheduler 让 forward 恰好停在那里。

Kimi Linear 使用 `mamba_cache_mode=align`。逻辑 block table 仍覆盖完整序列，但绝大多数位置可以是 null placeholder；运行中的请求只需维护少量 rolling state slots。

```text
step n
  previous state --copy--> current working state
  current working state --KDA forward--> C(P_end_n)

step n+1
  C(P_end_n) --copy--> next working state
  更早的 working slot 可被释放
```

当 step-end state 被赋予 prefix hash 后，它同时成为其他请求可命中的 checkpoint。KDA lookup 从目标 prefix 右侧向左寻找最近的 state block，不需要从 0 到该边界的所有历史 KDA state blocks。

### 第一次分叉请求为什么仍需重算

设：

```text
req1 = P_4k
req2 = P_1k + A_1k
req3 = P_1k + B_1k
```

req1 的大 prefill 可能留下：

```text
MLA pages: P_1k、P_2k、P_3k、P_4k
KDA state: 只有 C(P_4k)
```

req2 只共享前 1k，不能使用已经混入后续 token 的 `C(P_4k)`。在不挂 connector 的本地路径中，coordinator 会得到：

```text
MLA hit = 1k
KDA hit = 0
final hybrid hit = 0
missing shared-prefix boundary = 1k
```

scheduler 将 req2 的首次 prefill 截到 1k。forward 结束后生成并注册 `C(P_1k)`，下一 step 再继续 req2 的 suffix。req3 到来时，MLA 与 KDA 就能在 1k 同时命中。

这里重算的是完整模型 forward，而不是只运行 KDA layers。第一次分叉请求付出一次补算成本，收益由后续共享同一 prefix 的请求获得。

### connector 路径中的 boundary 丢失

在本文固定的 vLLM 快照中，同样的本地命中分歧在是否挂接 connector 时会走不同路径：

```text
local MLA hit = 1k
local KDA hit = 0

无 connector
  → ordinary hybrid fixed point
  → final local hit = 0
  → shared_prefix_boundary = 1k
  → scheduler 可以停在 1k 补 C(P_1k)

有 connector + Mamba/KDA
  → shared_prefix_boundary = 0
  → num_new_local_computed_tokens = max(per_group_hits) = 1k
  → 本地缺失 checkpoint 的 junction 信息不再向后传播
```

固定逻辑见 [`scheduler.py`](https://github.com/vllm-project/vllm/blob/1a659a0c370942bae3c8567902e38bddbbae95f3/vllm/v1/core/sched/scheduler.py)。

这里的代码真实语义是采用 `max(per_group_hits)`，并不是显式选择 Full Attention group；只是在本文 `MLA hit = 1k, KDA hit = 0` 的例子中，最大值恰好等于 MLA/FA hit。

这条特殊路径原本面向 P/D connector：Full Attention 已有的本地 blocks 可以避免重复传输，而 Mamba state 由对应 worker 另行传递。把同一假设直接用于共享 Store prefix lookup 时，不能自动表达“MLA 已命中到 1k、KDA checkpoint 尚缺失”的补点需求。

## MooncakeStoreConnector：可以存什么，缺的又是什么

vLLM 的共享 Store 路径按 cache group 建立 `ChunkedTokenDatabase`：

```text
PoolKey
  = cache_prefix
  + model basename
  + tp / pcp / dcp / pp rank
  + cache group id
  + chained prefix hash

value
  = 该 cache-group physical block 对应的一组 memory segments
```

固定实现见：

- [`data.py`](https://github.com/vllm-project/vllm/blob/1a659a0c370942bae3c8567902e38bddbbae95f3/vllm/distributed/kv_transfer/kv_connector/v1/mooncake/store/data.py)
- [`worker.py`](https://github.com/vllm-project/vllm/blob/1a659a0c370942bae3c8567902e38bddbbae95f3/vllm/distributed/kv_transfer/kv_connector/v1/mooncake/store/worker.py)
- [`scheduler.py`](https://github.com/vllm-project/vllm/blob/1a659a0c370942bae3c8567902e38bddbbae95f3/vllm/distributed/kv_transfer/kv_connector/v1/mooncake/store/scheduler.py)
- [`coordinator.py`](https://github.com/vllm-project/vllm/blob/1a659a0c370942bae3c8567902e38bddbbae95f3/vllm/distributed/kv_transfer/kv_connector/v1/mooncake/store/coordinator.py)

需要区分 GPU layout 与 Mooncake object layout：

```text
vLLM GPU layout
  每个 KDA layer 各有 raw state page

Mooncake Store value
  一个 group/chunk key
  → 一个或多个底层 storage slices
  → 可由 scatter-gather 地址和 size 组成
```

也就是说，不应简单理解成“每个 KDA layer 必然是一个独立 Mooncake object”。worker 会对底层 storage 去重，计算每个 physical block 在各 storage 中的地址与字节跨度，再把多个 slices 组成同一个 Store value。

MLA group 和 KDA group 可以对同一 prefix hash 分别保存：

```text
prefix hash @ vLLM cache group=MLA
  → MLA page value

same prefix hash @ vLLM cache group=KDA
  → KDA state value
```

如果 Store 中同时存在 `MLA(P_1k)` 和完整 `C(P_1k)`，external coordinator 的数据模型可以表达完整 1k hit，并将两个 cache groups 装入各自 GPU blocks；但固定快照缺少 Kimi KDA + MooncakeStoreConnector 的专项完整调用链证据，因此这里属于“接口形状允许”，而不是已确认闭环。

### 本地 fine-grained checkpoint 不等于远端 fine-grained object

本地 prefix cache 可以在 `prefix_match_unit` 边界注册 partial checkpoint，但固定 MooncakeStoreConnector 的外部查询和写入仍按同一个 resolved scheduler block 对齐。下文将这个 lookup/store 共用的对齐单位记作 $A_{\mathrm{store}}$。

Scheduler 查询前会做：

$$
L_{\mathrm{lookup}}
=
\left\lfloor
\frac{L_{\mathrm{request}}}
{A_{\mathrm{store}}}
\right\rfloor
A_{\mathrm{store}}.
$$

Store worker 写入前同样会做：

$$
L_{\mathrm{store}}
=
\left\lfloor
\frac{L_{\mathrm{computed}}}
{A_{\mathrm{store}}}
\right\rfloor
A_{\mathrm{store}}.
$$

在固定快照中，scheduler 的 `_block_size`、worker 使用的 block size 和 coordinator 的 `lcm_block_size` 来自同一个 resolved scheduler block size；分开写两个公式只是为了区分 lookup 与 store 阶段。

固定实现还要求：

```text
每个 cache-group block size % hash block size == 0
A_store % hash block size == 0
A_store % 每个 cache-group block size == 0
```

### 远端 partial-group missing boundary

固定快照中的 `MooncakeStoreCoordinator` 对外主要返回：

```text
final reconciled hit length
per-group load mask
```

它不会同时返回：

```text
remote MLA-only longest hit
best remote KDA checkpoint
missing KDA boundary
```

因此：

```text
Store 已有 MLA(P_1k) + C(P_1k)
  → 数据模型可以表达完整 1k hit

Store 只有 MLA(P_1k)
  → final hybrid hit 被协调回更短边界
  → scheduler 不知道远端 MLA 曾命中到 1k
  → 不会仅凭这次 lookup 自动停在 1k 合成 C(P_1k)
```

更严谨地说：截至本文固定 commit，external lookup 接口没有显式返回 remote missing KDA boundary；本文也未找到利用该 remote partial-group hit 自动触发 checkpoint synthesis 的完整调用链。

要补齐这条链，需要 local + external lookup 保留 per-group hit，或直接返回 `missing_branching_boundary`，随后让 scheduler、partial-tail registration 和 Store save mask 共享同一个边界。

### 远端 namespace 必须编码模型身份与 cache ABI

固定 vLLM key 中的 `model_name` 只取模型路径的 basename，`cache_prefix` 默认又是空字符串。由此可以推断：如果不同部署共享同一个 Mooncake 集群，同时拥有相同模型 basename 和 token prefix，但权重 revision、量化格式、adapter 或 cache layout 不同，仅靠现有默认 namespace 不足以保证安全隔离。

生产环境中的 cache namespace 至少应编码：

```text
model repository + exact revision / weight digest
tokenizer revision 与 chat-template identity
quantization format
KDA state dtype 与 layout version
adapter / LoRA identity
TP / PP / PCP / DCP topology
engine 与 cache ABI version
```

最简单的做法是为每一套不可互换的部署设置唯一 `cache_prefix`。prefix hash 只证明 token 序列相同，不证明由这些 token 计算出的模型状态可互换。

## SGLang HiCache：本地与 Mooncake 命中长度怎样合并

这一节描述的是 SGLang 的 GPU → Host → Mooncake 分层语义，不应机械套用到 vLLM MooncakeStoreConnector。

首先由 UnifiedRadixCache 求出 GPU 和 Host 上所有必要 components 一致支持的本地锚点。若 `L_host` 表示 Host 在 GPU 命中之后额外覆盖的 token 数，则：

$$
L_{\mathrm{local}}
=
L_{\mathrm{device}}+L_{\mathrm{host}}.
$$

Mooncake 只需要查询 `L_local` 之后的 suffix。由于 KDA checkpoint 是稀疏边界集合，而不是向下闭合的逐 token cache，不能把每个 group 的“最长长度”简单取最小值。

定义远端可恢复边界集合：

$$
\mathcal B_{\mathrm{store}}
=
\left\{
L\in[L_{\mathrm{local}},L_{\mathrm{common}}]
\ \middle|\
\begin{aligned}
&\mathrm{MLA/KV}[L_{\mathrm{local}}:L)\text{ 连续完整},\\
&C(P_L)\text{ 完整},\\
&\text{其他 sidecar 与所有必要 ranks 完整}
\end{aligned}
\right\}.
$$

候选总命中是：

$$
\boxed{
L_{\mathrm{candidate}}
=
\max\left(\{L_{\mathrm{local}}\}\cup\mathcal B_{\mathrm{store}}\right).
}
$$

例如：

```text
MLA/KV 连续存在到 7500
KDA checkpoint 只存在于 4096 和 8192
本地锚点为 0
```

不能取 `min(7500, 8192)=7500`，因为 `C(P7500)` 不存在。真正可恢复的边界只能是 4096。

实际传输还可能因为 timeout、best-effort、Host pool 不足或 rank 间不一致而变短。数据插入 Host Radix 后，权威结果应再次执行全 component match：

$$
L_{\mathrm{final}}
=
\operatorname{Rematch}
\left(
\mathrm{Device}+\mathrm{Host}+\mathrm{LoadedStoreData}
\right).
$$

KDA state slot 数不是 token 数，不能把 `mamba_host_hit_length=1` 当作“多命中一个 token”相加；它只是该 token 边界有效性的必要条件。

### 生成请求通常还要重算最后一个 prompt token

即使完整 prompt 的 cache 都存在，标准自回归生成仍需要最后一个 prompt 位置的输出 logits。若没有另外缓存 last hidden state 或 logits，语义上至少需要：

$$
L_{\mathrm{hit}}
\le
L_{\mathrm{prompt}}-1.
$$

固定 vLLM 的本地 `KVCacheManager` 会把最大 cache hit 设成 `request.num_tokens - 1`。MooncakeStoreScheduler 在全命中时还会将结果向下对齐到 scheduler block boundary。换句话说，语义上至少重算最后一个 token；受 allocator 和 connector 对齐约束影响，实际实现可能重算最后一个 block，而不只是一个 token。

## Attention pages 与 KDA checkpoint 应怎样组织

Attention KV page 和 KDA checkpoint 应视为两种不同资源，而不是每个 KV page 都附带一份完整 KDA state：

```text
Attention KV Page Pool
  page 0
  page 1
  page 2
  ...

KDA Checkpoint Pool
  C(P_L1)
  C(P_L2)
  ...
```

需要分开理解三个独立概念：

```text
P_KV
  Attention/MLA 的物理 page 大小

G_match
  prefix rolling-hash / lookup 粒度

𝒞_KDA
  已实际物化、注册且仍驻留的 checkpoint 集合
```

最终可跳过 forward 的长度是最近一个完整边界：

$$
L_{\mathrm{hit}}
=
\max\left\{
L\le L_{\mathrm{common}}
\ \middle|\
\mathrm{KV}[0:L)\text{ 完整}
\land
C(P_L)\text{ 完整}
\right\}.
$$

如果 Attention KV 已存在到 6976，但只有 `C(P4096)`，那么仍需从 4096 replay 到请求末尾。常规 runtime 通常会在 lookup 阶段就把 KV hit 截到 KDA boundary，避免无效加载更长 KV。

不存在一个跨 SGLang、vLLM 和 Mooncake 通用的“每 N token 自动创建 KDA checkpoint”旋钮。checkpoint 密度应该根据 `B_logical`、完整物理 checkpoint 大小、state-pool 容量、公共前缀分布、平均 replay 成本和实际命中收益来决定；system prompt、chat turn、tool result、RAG 公共文档和请求 tail 等高价值边界可以作为额外候选，但仍需由 engine 真正物化状态。

## Mooncake Store 的 object、Upsert 与 group 语义

固定快照中的 Mooncake Store 是 object-oriented cache。它看到的是：

```text
object key → one or more memory slices
```

`PutStart` / `PutEnd` 保证 reader 不会看到部分写入的 object。对于 content-addressed prefix cache，已经发布的 prefix-hash key 应当被当作 immutable object：新的 prefix 或新状态使用新 key，而不是覆盖旧 checkpoint。

Mooncake 同时提供显式 `Upsert` 生命周期，可以更新已有 key，甚至在布局不变时复用 allocation；因此“不可变”是 prefix-cache 协议应该坚持的不变量，而不是 Store 完全没有更新 API。对已经发布的 prefix-hash key 使用原地 Upsert，会破坏 hash → checkpoint 的稳定映射，不应作为普通缓存更新方式。

固定设计文档见 [`mooncake-store.md`](https://github.com/kvcache-ai/Mooncake/blob/12df58c7de65f88f37f5da99ab95ff3418a9ebef/docs/source/design/mooncake-store.md)。

这里还要区分两个不同的 “group”：

```text
vLLM cache group id
  cache layout / PoolKey namespace
  区分 MLA、KDA、SWA 等 cache groups

Mooncake ReplicateConfig.group_ids
  Mooncake native object lifecycle group
  用于 metadata routing、lease refresh 与 best-effort eviction
```

Mooncake native group 可以包含不同大小、不同 token span 的 objects，但不是事务：

```text
不要求 expected member count
不保证所有成员原子创建或同时可见
不保证所有成员全有全无地淘汰
已有 object 的 group membership 不可变
```

因此，一个完整 hybrid prefix 是否可恢复，仍要由上层 coordinator 逐项验证。

### 固定快照中的两种映射

```text
SGLang
  检测 ReplicateConfig.group_ids 能力
  → 可为一个 logical HiCache page 的 component objects
    使用 sglang-hicache:<logical-key> 作为 Mooncake native group

vLLM
  PoolKey 中的 @group:N 是 cache-group namespace
  → 固定快照创建的 ReplicateConfig 只设置 preferred_segment
  → 没有把 @group:N 当成 Mooncake native group_ids
```

SGLang 可以把一个逻辑 KDA checkpoint 展开为 temporal 与若干 conv objects；vLLM 则按 cache group/chunk key 组织一个或多个底层 storage slices。

同一个 Mooncake 集群也不意味着 SGLang 与 vLLM 可以直接互读。两者的 key namespace、rank 编码、layer 顺序、dtype、shape、byte layout 和 checkpoint policy 都不同。跨引擎复用需要额外定义稳定的公共 ABI。

### 推荐的 Store schema，而不是当前实现描述

若要在 Mooncake 之上实现更强的逻辑原子性，可以由上层增加 manifest 协议：

```text
Attention KV objects
  独立 content-addressed pages

KDA checkpoint objects
  temporal / conv 或 raw-state slices
  按 boundary、rank、model namespace 组织

Prefix manifest
  prefix length
  KV page references
  KDA component references
  dtype / layout / topology metadata
  committed flag
```

写入顺序：

```text
1. 写所有 component objects
2. 验证写入成功
3. 最后写 manifest / commit object
```

失效时反过来先让 manifest 不可见，再异步回收 components。这个 manifest 方案是推荐设计，不代表固定快照中的 SGLang 或 vLLM 已经采用。

```text
  相同 token prefix 与模型 basename
```

## 配置时怎样理解相关旋钮

### SGLang

```text

  使用额外 tracking slot 保存 prefix checkpoint

--page-size
  radix / HiCache page 粒度，也参与可追踪边界对齐

--mamba-track-interval
  状态追踪/保留策略的一部分，不等同于强制 prefill forward 大小

--chunked-prefill-size
  scheduler prefill budget，可以大于 checkpoint 粒度

--enable-hierarchical-cache
--hicache-storage-backend mooncake
  启用 GPU → Host → Mooncake 链路
```

### vLLM

```text
enable_prefix_caching
  启用 hybrid prefix cache

mamba_cache_mode=align
  Kimi Linear 的实际状态物化模式

enable_chunked_prefill
  允许 scheduler 在必要边界结束 step

  可以保持较大，不要求机械按某个 interval 切分

  调整本地可寻址 hash 粒度，不自动创建 state
```

验证实现时，不要一开始就把 prefill budget 降到 1k，否则无法区分“按需补点生效”和“所有请求本来就被机械切成 1k”。对于 Mooncake，也不能只检查 object key 是否出现；还应验证 component 完整性、hybrid hit length、missing-boundary 传播、远端对齐、namespace isolation、CoW、最后一个 token/block 和 replay logits。

## 最终判断

回到 req1/req2 示例，可以分三层判断：

> req1 的 4k prefill 如果只留下 `C(P_4k)`，req2 第一次共享 1k 时确实必须重新计算这 1k；`C(P_4k)` 无法回滚，MLA pages 也不能替代 KDA checkpoint。

> SGLang 本地可以让 req2 的大 extend 跨过 1k，再从 kernel 返回的 chunk-aligned 中间 state 抽出并插入 `C(P_1k)`；需要 intermediate states 时，FlashKDA 会回退到 Triton。vLLM 不挂 connector 的本地路径则把 req2 动态截到 1k，利用 step end 补出并注册 `C(P_1k)`。两边都不要求把所有请求的 prefill budget 固定成 1k。

再加上外部缓存限定：

> SGLang + HiCache 已把 temporal/conv checkpoint 接到 Mooncake 的显式读写链路，但 HiCache 模式仍暂时跳过 branching-state fill。vLLM 在本文固定快照中已支持本地 physical block 内的 fine-grained partial checkpoint 与 Copy-on-Write；然而 connector + Mamba/KDA 的本地路径会清零 `shared_prefix_boundary` 并采用 `max(per_group_hits)`，MooncakeStoreConnector 的远端 store/lookup 还受同一个 resolved scheduler/LCM block 对齐，`MooncakeStoreCoordinator` 也不单独返回 MLA-only 更长命中对应的 missing KDA boundary。

因此，SGLang 可以确认已经存在且完整的 `C(P_t)` 能通过其 HiCache/Mooncake 数据面读写；vLLM 的 raw-page/cache-group 数据模型和通用 Mooncake 传输路径可以表示完整 checkpoint，但在固定快照中，这一结论仍属于“接口形状允许”，不能替代一条已经确认闭环的 Kimi KDA 专项调用链。

优化目标不是机械地每隔 1k 切一次 forward，而是在出现可复用分叉时只补算一次，并把同一个边界持续传递到本地 radix/scheduler、Host staging、Mooncake key/value、lookup、namespace 与 retention policy。还要始终区分 physical state block、prefix match unit、scheduler/LCM block 与实际 checkpoint 集合：细粒度可寻址不等于细粒度状态自动生成，更不等于远端对象也具备相同粒度；checkpoint 一旦发布就应保持不可变，后续扩展通过 CoW 产生新的 working state 或新 checkpoint。

Kimi Linear 的 prefix cache 不能只按普通 Transformer 的 KV block 来理解。模型里一部分层是 MLA，另一部分层是 KDA；前者需要一串可分页的 KV，后者只需要“前缀处理到当前位置以后”的有限状态。难点不仅在于保存这份状态，还在于让它与 token prefix、MLA block、scheduler step、HiCache 层级以及 Mooncake Store object 的命中边界始终一致。

本文以 Kimi KDA 状态为起点，分别追踪 SGLang 和 vLLM 如何将本地 checkpoint 接入 Mooncake Store：

```text
Kimi KDA
  ├─ SGLang: RadixLinearAttention → UnifiedRadixCache → HiCache L2
  │            → MooncakeStore backend → Mooncake Distributed Store
  │
  └─ vLLM: KimiGatedDeltaNetAttention → HybridKVCacheCoordinator
               → MooncakeStoreConnector → Mooncake Distributed Store
```

沿这两条链回答八个问题：

```text
1. KDA cache 里究竟存了什么？
2. 一个请求是只有一个 KDA cache，还是每层各有一份？
3. SGLang 怎样从一次大 prefill 中抽取中间 KDA checkpoint？
4. UnifiedRadixCache 怎样把 checkpoint 关联到 radix node？
5. HiCache 怎样把 MLA 与 KDA 从 GPU 搬到 Host，再写入 Mooncake？
6. vLLM 怎样在共享前缀分叉点按需补 KDA checkpoint？
7. 两套 Mooncake adapter 的 key、value 与 lookup 规则有什么不同？
8. 哪些链路已经打通，哪些仍缺少控制面或端到端测试？
```

核心结论是：**Mooncake Store 负责按 key 保存和搬运不透明的字节数据。KDA checkpoint 在哪个 token 边界创建、它是否和 MLA prefix 对齐、缺失时是否需要补算，全部由 SGLang 或 vLLM 的控制面决定。**

两套引擎当前走的是不同路线：

```text
SGLang
  一个大 extend 可让 KDA kernel 返回中间 h
  → runtime 抽取对齐边界状态
  → radix node 持有 Mamba/KDA slot
  → HiCache 将 temporal + conv 分别写成 Mooncake objects

vLLM
  Kimi KDA forward 通常只物化当前 step 末状态
  → 本地 hybrid coordinator 发现 MLA/KDA 命中长度不一致
  → scheduler 只在真实分叉点截断一次 forward
  → raw KDA page 可交给 MooncakeStoreConnector
```

两条链都已具备 KDA 状态的数据传输能力，但远端共享前缀复用尚未完全打通：SGLang 缺少 HiCache 模式下的分叉状态补算，vLLM 则没有把分叉边界完整传入 `MooncakeStoreConnector`。后文会分别定位这两个控制面缺口。

## KDA 的计算原理：先遗忘，再纠错

KDA 的核心是一张固定大小的关联记忆矩阵 `S`。每个 KDA layer 的每个 head 都用它记录 key 到 value 的映射；新 token 到来时，KDA 不会把 `k vᵀ` 永远累加，而是依次做三件事：

```text
1. 按 key channel 衰减旧状态             fine-grained forgetting
2. 用当前 k 从衰减后的状态预测当前 v      read / reconstruction
3. 只把预测误差写回                       delta correction
```

设论文中的列向量为：

```text
q_t, k_t ∈ R^d_k
v_t      ∈ R^d_v
S_t      ∈ R^(d_k × d_v)

S_t^T k_t  = 用 key k_t 从记忆中预测出的 value
S_t^T q_t  = 当前 token 的 attention 输出
```

### 从普通 linear attention 到 DeltaNet

最朴素的 linear attention 把每个 key/value 外积直接累加：

```text
S_t = S_(t-1) + k_t v_t^T
o_t = S_t^T q_t
```

这等价于不停加强关联，却没有“同一个 key 已经写过时应该覆盖什么”的规则。序列变长后，彼此相似的 key 会在有限矩阵里持续叠加并互相干扰。

DeltaNet 把状态更新改写成一次在线回归。它先看旧状态能否由 `k_t` 重建 `v_t`：

```text
v_hat_t = S_(t-1)^T k_t
e_t     = v_t - v_hat_t
```

然后只写入残差：

```text
S_t = S_(t-1) + beta_t k_t e_t^T

    = (I - beta_t k_t k_t^T) S_(t-1)
      + beta_t k_t v_t^T
```

`beta_t ∈ [0, 1]` 可以理解为这个 token 的写入强度，也就是在线梯度下降的学习率。若旧状态已经能正确预测 `v_t`，`e_t` 接近 0，几乎不用再写；若预测错误，就沿 `k_t` 对应的方向纠正记忆。

### Gated DeltaNet 的标量遗忘为什么还不够

Delta rule 会纠错，但旧关联仍可能长期存在。Gated DeltaNet 因此给每个 head 增加一个标量 `alpha_t`：

```text
S_t = alpha_t (I - beta_t k_t k_t^T) S_(t-1)
      + beta_t k_t v_t^T
```

同一个 head 的整个状态只能用一个遗忘率：要么一起记得久一点，要么一起忘得快一点。KDA 的核心变化，就是把这个 head-wise scalar 换成长度为 `d_k` 的 channel-wise vector。

### KDA 的逐 token 递推

定义：

```text
alpha_t ∈ (0, 1]^(d_k)
D_t     = Diag(alpha_t)
beta_t  ∈ [0, 1]
```

论文公式（Eq. 1）是：

```text
S_t = (I - beta_t k_t k_t^T) D_t S_(t-1)
      + beta_t k_t v_t^T

o_t = S_t^T q_t
```

实际执行时，把它写成下面五步最容易理解：

```text
# 1. 每个 key channel 以自己的速率遗忘
S_decay = D_t S_(t-1)

# 2. 从已经衰减的记忆中读取
v_hat   = S_decay^T k_t

# 3. 计算当前 value 的预测残差
e_t     = v_t - v_hat

# 4. 沿当前 key 方向写回残差
S_t     = S_decay + beta_t k_t e_t^T

# 5. 用 query 读取更新后的状态
o_t     = S_t^T q_t / sqrt(d_k)
```

这里有一个容易忽略的顺序：**KDA 是先做 `D_t S_(t-1)`，再用 `k_t` 计算 delta error**。因为 `D_t` 不再是标量，它不能像 GDN 的 scalar gate 那样随便与 rank-1 变换交换位置。

这也与 SGLang 的 recurrent kernel 一一对应：先执行 `h *= exp(g)`，再做 `v -= h^T k`，随后 `v *= beta`、`h += k v^T`，最后计算 `h^T q`。对应实现见 [`fused_sigmoid_gating_recurrent.py`](https://github.com/sgl-project/sglang/blob/297f9336c8bf81e2fcf06b930d2dd3551f7dec15/python/sglang/kernels/ops/attention/fla/fused_sigmoid_gating_recurrent.py#L145-L200)。源码里的临时变量 `v` 在减去预测值后，已经变成了上式的 `e_t`。

### alpha、beta、Q/K/V 是怎样从 x_t 得到的

论文第 4 节给出的每个 head 的 neural parameterization 可以整理成：

```text
q_raw, k_raw, v_raw = linear projections of x_t

q_t = L2Norm(SiLU(ShortConv(q_raw)))
k_t = L2Norm(SiLU(ShortConv(k_raw)))
v_t =        SiLU(ShortConv(v_raw))

a_t     = low_rank_alpha_projection(x_t)   # [head, d_k]
g_t     = -exp(A_log) * softplus(a_t + dt_bias)
alpha_t = exp(g_t)                          # (0, 1], [head, d_k]

b_t    = beta_projection(x_t)               # [head]
beta_t = sigmoid(b_t)                       # [0, 1], [head]
```

所以 `g_t` 是 **log-decay**，不是另一个需要持久化的 RNN state；`alpha_t = exp(g_t)` 才是公式中的逐通道遗忘率。`A_log` 是每个 head 的缩放参数，`dt_bias` 则细化到 channel。因为 `g_t ≤ 0`，`alpha_t` 不会大于 1。

SGLang 模型层先生成 `mixed_qkv`、raw `forget_gate` 和 raw `beta`。prefill 在模型层对 `beta` 做 sigmoid，再把 raw forget gate 交给 chunk kernel，在 kernel 内融合 `softplus`、`exp` 与 chunk-local cumulative sum；decode kernel 则在单 token 递推里完成 forget-gate activation、beta sigmoid、Q/K L2Norm 和状态更新。入口分别见 [`KimiDeltaAttention.forward`](https://github.com/sgl-project/sglang/blob/297f9336c8bf81e2fcf06b930d2dd3551f7dec15/python/sglang/srt/models/kimi_linear.py#L332-L409)、[`KDAAttnBackend.forward_extend`](https://github.com/sgl-project/sglang/blob/297f9336c8bf81e2fcf06b930d2dd3551f7dec15/python/sglang/srt/layers/attention/linear/kda_backend.py#L384-L487)和 [`kda_gate_chunk_cumsum`](https://github.com/sgl-project/sglang/blob/297f9336c8bf81e2fcf06b930d2dd3551f7dec15/python/sglang/kernels/ops/attention/fla/kda.py#L964-L1029)。

vLLM 做的是同一件事：prefill 调用 `chunk_kda_with_fused_gate(..., output_final_state=True)` 并把 `last_recurrent_state` 写回 slot；decode 先调用 `fused_kda_gate`，再用 `fused_recurrent_kda` 从 slot 中的 `recurrent_state` 继续推进。见 [`KimiGatedDeltaNetAttention._forward`](https://github.com/vllm-project/vllm/blob/387189c42997b27e2c04b5d97ef8190ffa2bf909/vllm/model_executor/layers/mamba/gdn/kimi_gdn_linear_attn.py#L390-L441)。这也是为什么两套引擎虽有不同的 page layout，数学上的 checkpoint 都是同一个 `(conv window, final S)`。

还有一个命名陷阱：模型代码中的 `g_proj_states` 是 attention 输出之后送入 gated RMSNorm 的 **output gate**；传给 KDA recurrence 的是 `forget_gate`，两者不是同一个 `g`。

### 为什么它是特殊的 DPLR transition

把单 token 递推中作用于旧状态的矩阵记作 `T_t`：

```text
T_t = (I - beta_t k_t k_t^T) D_t

    = D_t - beta_t k_t (k_t ⊙ alpha_t)^T
```

第一项是 diagonal，第二项是 rank 1，所以这是 Diagonal-Plus-Low-Rank（符号上实际为 diagonal minus low-rank）transition。一般 DPLR 写成 `D_t - a_t b_t^T`，要独立生成两根向量；KDA 把 low-rank 两侧都约束到同一个 `k_t` 及其 decay-scaled 版本，既保留 classical delta rule 的“按 key 纠错”含义，也让专用 kernel 少做一批中间矩阵乘法。

### prefill 为什么能按 chunk 并行

decode 每次只有一个 token，直接执行上面的五步即可。prefill 若也逐 token launch kernel，GPU 利用率会很差。论文因此把一个 kernel chunk 内的多个 transition 压缩起来。

对于 chunk 中第 `1..r` 个 token，递推可以统一写成：

```text
S_r = P_r S_0 + H_r

P_r = T_r T_(r-1) ... T_1
H_r = 当前 chunk 内所有 k/v 写入项经过后续 transition 后的总和
```

KDA 利用 WY representation，把这一串 diagonal + rank-1 矩阵的乘积转成可批量计算的辅助量 `W` 与 `U`；再用 UT transform 把它们归结为一个小型下三角求解。最终的 chunk state update（论文 Eq. 8）可以概括为：

```text
S_out = Diag(gamma_chunk) S_in
        + K_decay^T (U - W S_in)
```

输出同时拆成两部分：

```text
O_chunk = inter_chunk(S_in)
          + causal_intra_chunk(U, W, Q, K)
```

`inter_chunk` 读取 chunk 入口的旧状态，`causal_intra_chunk` 处理本 chunk 内 token 之间的因果依赖。这样绝大部分工作可落到半精度矩阵乘法；chunk 与 chunk 之间仍只传递最终的 `S`。

论文伪代码默认 `chunk_size = 64`，当前 SGLang Triton KDA prefill 也在 [`chunk_kda_fwd`](https://github.com/sgl-project/sglang/blob/297f9336c8bf81e2fcf06b930d2dd3551f7dec15/python/sglang/kernels/ops/attention/fla/kda.py#L1032-L1075)中固定使用 64。但这个 64 是 **KDA kernel 内部的计算 tile**，不是 scheduler 的 chunked-prefill 大小，更不是 prefix cache checkpoint interval：

| 名称                                | 所在层             | 作用                                         | 是否天然产生可复用 checkpoint              |
| ----------------------------------- | ------------------ | -------------------------------------------- | ------------------------------------------ |
| KDA kernel chunk（如 64）           | 算子               | 用 WY/UT 提高一次 forward 内的并行度         | 否，只产生临时 `W/U/gamma` 和 chunk 末 `S` |
| scheduler prefill chunk（如 1k/4k） | 调度器             | 限制一次 forward 的 token 数、改善调度公平性 | 通常只保证 step 末状态已提交               |
| prefix checkpoint interval          | cache/radix policy | 决定哪些 prefix 边界有可寻址的完整状态       | 是，但必须显式抽取并绑定到该边界           |

因此，不需要为了匹配论文的 64-token chunk，把服务层的 chunked prefill 也设成 64 或 1k。算子可以在一个很大的 scheduler forward 内自行切成许多 64-token tile；能否把其中某个 tile 末状态提升为 prefix checkpoint，是另一层机制。

### 哪些量属于 cache，哪些只是算子临时量

单 token 递推说明 KDA 是 Markov 的：处理下一 token 时，只需要上一边界的 `S`，再加上短卷积所需的有限窗口。于是某个 prefix `P_t` 的充分状态是：

```text
C(P_t) = {
  每个 KDA layer 的 ShortConv 最近 kernel_size - 1 个 raw Q/K/V 投影,
  每个 KDA layer 的最终 recurrent matrix S_t
}
```

以下内容不需要跨请求持久化：

```text
整个 prefix 的 q/k/v
每个 token 的 alpha / beta / delta error
prefill chunk 内的 W / U / gamma / triangular-solve workspace
attention 输出 o_t 与 output gate
```

它们要么已经被折叠进 `S_t`，要么处理完当前 chunk 就失效。反过来，只有 `S_t` 而没有 ShortConv window 也不完整，因为下一个 token 的卷积结果依赖 prefix 末尾的原始 Q/K/V 投影。

这还能直接解释 prefix 复用的单向性：若有 `C(P_1k)`，就能用后续 token 把它前向推进到 `C(P_2k)`；若只有 `C(P_4k)`，不能可靠地“倒推”回 `C(P_1k)`。逐通道衰减和 delta correction 本来就是有损记忆更新，且较早边界的卷积窗口也已被覆盖。

## KDA cache 是卷积前 Q/K/V 历史加递归矩阵

Kimi Linear 的 decoder layer 根据 `config.is_kda_layer(layer_idx)` 在 KDA 与 MLA 之间选择。vLLM 的 KDA 层实例化 `KimiGatedDeltaNetAttention`，入口见 [`KimiDecoderLayer`](https://github.com/vllm-project/vllm/blob/387189c42997b27e2c04b5d97ef8190ffa2bf909/vllm/model_executor/models/kimi_linear.py#L288-L326)；SGLang 对应地实例化 `KimiDeltaAttention`，入口见 [`KimiDecoderLayer`](https://github.com/sgl-project/sglang/blob/297f9336c8bf81e2fcf06b930d2dd3551f7dec15/python/sglang/srt/models/kimi_linear.py#L415-L449)。两边的命名和 kernel 封装不同，但要保存的时间状态相同。

一个 KDA 层的 cache 由两部分组成：

```text
S_l(t) = (conv_state_l(t), recurrent_state_l(t))

conv_state_l(t)
  = Q/K/V 短卷积最近 kernel_size - 1 个输入位置的历史

recurrent_state_l(t)
  = KDA 递推到 token t 之后的矩阵状态
```

当短卷积 kernel size 为 4 时，所谓“最近 3 个时间步”就是最近 3 个 token 位置。但这里存的不是卷积输出，而是**线性投影之后、短卷积之前的 Q/K/V 序列值**。

源码上的证据很直接：`q_proj_states`、`k_proj_states`、`v_proj_states` 被传给 `causal_conv1d_fn`，`conv_state_q/k/v` 同时作为卷积历史输入；卷积返回的 `q/k/v` 才进入 KDA 递推。见 [`KimiGatedDeltaNetAttention._forward`](https://github.com/vllm-project/vllm/blob/387189c42997b27e2c04b5d97ef8190ffa2bf909/vllm/model_executor/layers/mamba/gdn/kimi_gdn_linear_attn.py#L275-L389)。

vLLM 的状态 shape 由 `MambaStateShapeCalculator.kda_state_shape` 给出：

```text
local_heads = num_heads / tensor_parallel_size

conv_state shape
  = (3 * local_heads * head_dim, kernel_size - 1)   # DS layout
  或 (kernel_size - 1, 3 * local_heads * head_dim) # SD layout

recurrent_state shape
  = (local_heads, head_dim, head_dim)
```

更一般的实现允许 Q/K head 配置不同，所以源码写成 `proj_size + 2 * proj_k_size`。Kimi Linear 当前调用没有传独立的 K head 配置，退化成 Q、K、V 三份等宽投影。vLLM 的 shape 计算见 [`kda_state_shape`](https://github.com/vllm-project/vllm/blob/387189c42997b27e2c04b5d97ef8190ffa2bf909/vllm/model_executor/layers/mamba/mamba_utils.py#L237-L260)；SGLang 的 `KimiLinearStateShape.create` 生成等价的 conv 与 temporal shape，见 [`mamba_utils.py`](https://github.com/sgl-project/sglang/blob/297f9336c8bf81e2fcf06b930d2dd3551f7dec15/python/sglang/srt/configs/mamba_utils.py#L239-L291)。

dtype 也不是两部分完全相同：

```text
conv_state      = mamba_cache_dtype 或由 model dtype 推导
recurrent_state = float32
```

vLLM 的 `kda_state_dtype` 明确规定这一点，见 [`mamba_utils.py`](https://github.com/vllm-project/vllm/blob/387189c42997b27e2c04b5d97ef8190ffa2bf909/vllm/model_executor/layers/mamba/mamba_utils.py#L119-L125)；SGLang 默认也令 conv 为 BF16、temporal 为 FP32，并允许分别覆盖，见 [`mamba2_state_dtype`](https://github.com/sgl-project/sglang/blob/297f9336c8bf81e2fcf06b930d2dd3551f7dec15/python/sglang/srt/configs/mamba_utils.py#L41-L107)。因此估算 KDA cache 不能只拿模型 dtype 乘元素数；FP32 递归矩阵通常占用更多字节。

## “一个请求只有一个 KDA cache”要分逻辑与物理两层理解

可以把一个请求在 prefix `P_t` 结束处的模型级 KDA checkpoint 写成：

```text
C(P_t) = {
  S_l(t) | l 是一个 KDA layer
}
```

从 scheduler/radix 的逻辑身份看，它是一个 checkpoint：同一个 token prefix hash、同一个逻辑 KDA block id、同一个可恢复边界。

从物理存储看，它并不是单个 tensor。每个 KDA layer 都有自己的状态页，而同一个 block id 在每层页表中索引出该层的 `conv_state + recurrent_state`。所以更准确的说法是：

> 一个请求在某一可恢复边界上有一个逻辑 KDA checkpoint；这个 checkpoint 由所有 KDA 层的物理状态页共同组成。

两套引擎的物理布局并不相同。

vLLM 把每层状态打包成一个 blocks-first raw page：

```text
raw page per KDA layer
  shape = [num_blocks, 1, 1, page_size_bytes]
  dtype = int8  # 这里只是字节容器

page[block_id]
  = conv_state bytes
  + recurrent_state bytes
  + optional padding
```

模型 runner 在 [`gpu_model_runner.py`](https://github.com/vllm-project/vllm/blob/387189c42997b27e2c04b5d97ef8190ffa2bf909/vllm/v1/worker/gpu_model_runner.py#L7380-L7391) 中创建这个原始页；`MambaBase.bind_kv_cache` 再按每种状态的 shape 和 dtype 切片、reinterpret，得到算子实际使用的 tuple，见 [`abstract.py`](https://github.com/vllm-project/vllm/blob/387189c42997b27e2c04b5d97ef8190ffa2bf909/vllm/model_executor/layers/mamba/abstract.py#L29-L43)。

SGLang 的 `MambaPool` 默认直接维护跨层、跨 slot 的 `conv` 与 `temporal` tensor；启用 page-major envelope layout 时才把它们变成同一 `_raw` byte buffer 的 strided views。见 [`MambaPool`](https://github.com/sgl-project/sglang/blob/297f9336c8bf81e2fcf06b930d2dd3551f7dec15/python/sglang/srt/mem_cache/memory_pool.py#L424-L532)。因此：

```text
vLLM GPU value
  one raw page per KDA layer
  page 内拼接 conv + recurrent

SGLang GPU / Host value
  one logical Mamba slot across all KDA layers
  temporal buffer + one or more conv buffers
  Host/Mooncake adapter 再把这些 component 分开寻址
```

这说明“逻辑 checkpoint 原子性”不要求“物理上只有一个 object”。vLLM 选择完整 raw page；SGLang Mooncake adapter 选择同一 logical page 下的 temporal object 与若干 conv objects。只要 lookup 要求所有 component 同时存在，并以同一个 prefix 边界提交，两种布局都能保持一致。

## SGLang 链路一：一次大 prefill 内抽取 KDA checkpoint

SGLang 的 KDA 层先产生投影后的 `mixed_qkv`。extend 阶段把它拆成 Q/K/V，分别经过短卷积，再把卷积后的 Q/K/V 交给 KDA kernel。与 vLLM 当前 Kimi 路径最大的差异，是 SGLang 在需要 prefix checkpoint 时会令 kernel 返回中间 recurrent states：

```python
core_attn_out = kernel_dispatcher.extend(
    ...,
    return_intermediate_states=track_ssm,
)

if track_ssm:
    core_attn_out, h = core_attn_out
    _track_mamba_state_extend(..., h, ssm_states, ...)
```

完整调用点见 [`KDAAttnBackend.forward_extend`](https://github.com/sgl-project/sglang/blob/297f9336c8bf81e2fcf06b930d2dd3551f7dec15/python/sglang/srt/layers/attention/linear/kda_backend.py#L390-L487)。这里同时处理两部分状态：

```text
conv checkpoint
  从 mixed_qkv 中选出边界前最后 kernel_size - 1 行
  直接写入目标 track slot

recurrent checkpoint
  边界恰好等于本次 extend 末尾：从 final recurrent state 复制
  边界位于大 extend 中间：从 kernel 返回的中间 h 复制
```

`HybridLinearAttnBackend` 先计算卷积窗口在 flattened input 中的索引，再判断 recurrent state 应来自 final state 还是 `h`。见 [`_init_track_conv_indices` 与 `_init_track_ssm_indices`](https://github.com/sgl-project/sglang/blob/297f9336c8bf81e2fcf06b930d2dd3551f7dec15/python/sglang/srt/layers/attention/hybrid_linear_attn_backend.py#L245-L315)；实际的 `h → ssm_states[track_slot]` 复制见 [`_track_mamba_state_extend`](https://github.com/sgl-project/sglang/blob/297f9336c8bf81e2fcf06b930d2dd3551f7dec15/python/sglang/srt/layers/attention/hybrid_linear_attn_backend.py#L675-L694)。

因此，SGLang 不要求为了生成一个 1k checkpoint 就把 4k prefill 拆成四次模型 forward。只要 kernel 路径支持 `return_intermediate_states`，一次大 forward 可以计算 4k，同时从内部 `h` 抽取某个对齐边界的 recurrent state。

### checkpoint 边界由什么决定

SGLang 的 `mamba_cache_chunk_size` 是模型 FLA/Mamba chunk size 与 radix `page_size` 的较大者，并要求两者可以整除。它用于确定 prefill 的可缓存状态边界，见 [`ServerArgs.mamba_cache_chunk_size`](https://github.com/sgl-project/sglang/blob/297f9336c8bf81e2fcf06b930d2dd3551f7dec15/python/sglang/srt/server_args.py#L7583-L7598)。

请求进入 extend 前，scheduler batch 会：

```text
1. 判断本次 extend 是否至少覆盖一个 mamba_cache_chunk_size
2. 计算 prefix 之后最后一个完整 chunk 边界
3. 选择 ping-pong track slot
4. 若 radix 匹配报告了 branching_seqlen，且它位于本次 extend 内，
   改为追踪该分叉边界
5. 把实际边界记录为 req.mamba_last_track_seqlen
```

对应逻辑见 [`_mamba_radix_cache_v2_req_prepare_for_extend`](https://github.com/sgl-project/sglang/blob/297f9336c8bf81e2fcf06b930d2dd3551f7dec15/python/sglang/srt/managers/schedule_batch.py#L2443-L2527)。

这里需要区分两个旋钮：

```text
mamba_cache_chunk_size
  prefill 中 kernel/state 可被抽取的对齐粒度

mamba_track_interval
  decode 期间定期追踪状态的间隔，默认 256
```

它们都影响 checkpoint 密度，但不能简单理解成“每隔 N token 强制一次完整 forward”。

## SGLang 链路二：checkpoint 怎样进入 UnifiedRadixCache

完成 forward 后，SGLang 不会把完整 KDA tensor 直接存入 radix node；radix node 保存的是 Mamba/KDA pool slot index：

```text
UnifiedTreeNode
  key / hash_value        token prefix 与页 hash
  Full component          MLA/KV device indices
  Mamba component
    value                 GPU Mamba slot index
    host_value            HiCache Host Mamba slot index
```

`MambaComponent.prepare_for_caching_req` 以 `req.mamba_last_track_seqlen` 作为可提交的 key length，并把 ping-pong track slot 捐给 radix cache；若启用 INT8 checkpoint pool，则先压缩到独立 checkpoint slot。见 [`prepare_for_caching_req`](https://github.com/sgl-project/sglang/blob/297f9336c8bf81e2fcf06b930d2dd3551f7dec15/python/sglang/srt/mem_cache/unified_cache_components/mamba_component.py#L349-L426)。

随后 `commit_insert_component_data` 把这个 slot index 写到对应 node 的 Mamba component，并维护独立的 Mamba LRU。见 [`commit_insert_component_data`](https://github.com/sgl-project/sglang/blob/297f9336c8bf81e2fcf06b930d2dd3551f7dec15/python/sglang/srt/mem_cache/unified_cache_components/mamba_component.py#L150-L179)。

请求命中时，Mamba component 接受两种状态：

```text
node.value != None
  KDA checkpoint 仍在 GPU，可直接 CoW 到请求活动 slot

node.host_value != None
  GPU 状态已逐出，但 HiCache Host 副本仍在，触发 load_back
```

匹配 validator 与 Host hit 标记见 [`MambaComponent.finalize_match_result`](https://github.com/sgl-project/sglang/blob/297f9336c8bf81e2fcf06b930d2dd3551f7dec15/python/sglang/srt/mem_cache/unified_cache_components/mamba_component.py#L84-L148)。

### SGLang 本地如何发现分叉点

假设 radix tree 已有 req1 的完整 token/MLA path 到 4k，但沿 path 只有 `C(P_4k)`，req2 与它只共享 1k。匹配结果会出现：

```text
value_chunks 覆盖到 P_1k
best Mamba value length = 0
```

没有 HiCache controller 时，`MambaComponent.finalize_match_result` 会把较长 token prefix 向下对齐到 `mamba_cache_chunk_size`，形成 `mamba_branching_seqlen`。下一次大 extend 仍可以一次算完自己的预算，但 backend 会从中间 `h` 抽出这个分叉 checkpoint。

这与 vLLM 的 scheduler split 是两种不同策略：

```text
SGLang local
  forward 可以跨过分叉点
  → 从中间 h 抽取 checkpoint

vLLM local
  Kimi operator 只暴露 step 末状态
  → scheduler 让 forward 恰好停在分叉点
```

## SGLang 链路三：UnifiedRadixCache 到 HiCache Host

对 hybrid 模型，HiCache 会同时迁移 Full/MLA KV 和 KDA 状态：Full/MLA pool 作为主缓存条目，KDA sidecar pool 与它绑定到同一个 radix node。

当 node 需要备份到 Host 时，`UnifiedRadixCache.write_backup` 分别向各 component 请求 transfer descriptor：

```text
Full/MLA component
  GPU token/KV indices → Host KV indices

Mamba/KDA component
  PoolTransfer(
    name = MAMBA,
    device_indices = node.mamba.value,
  )
```

KDA sidecar descriptor 由 [`MambaComponent.build_hicache_transfers`](https://github.com/sgl-project/sglang/blob/297f9336c8bf81e2fcf06b930d2dd3551f7dec15/python/sglang/srt/mem_cache/unified_cache_components/mamba_component.py#L472-L545) 生成。`HybridCacheController` 分配 Host slots，并通过注册的 device/host pool 实现把所有 KDA 层的 temporal 与 conv state 搬到 `MambaPoolHost`。controller 的写入与加载入口见 [`HybridCacheController.write/load`](https://github.com/sgl-project/sglang/blob/297f9336c8bf81e2fcf06b930d2dd3551f7dec15/python/sglang/srt/mem_cache/hybrid_cache/hybrid_cache_controller.py#L364-L500)。

`MambaPoolHost` 的布局很重要：

```text
temporal_buffer
  [num_kda_layers, host_slots, local_heads, head_dim, head_dim]

conv_buffer[0]
  [num_kda_layers, host_slots, kernel_size - 1, qkv_width]
```

所以一个 Host slot 仍然代表“所有 KDA 层在同一 prefix 边界的完整 checkpoint”。`get_page_buffer_meta` 可以为该 slot 枚举 temporal 和每个 conv component 的内存地址与字节数，见 [`MambaPoolHost`](https://github.com/sgl-project/sglang/blob/297f9336c8bf81e2fcf06b930d2dd3551f7dec15/python/sglang/srt/mem_cache/memory_pool_host.py#L66-L243) 与 [`get_page_buffer_meta`](https://github.com/sgl-project/sglang/blob/297f9336c8bf81e2fcf06b930d2dd3551f7dec15/python/sglang/srt/mem_cache/memory_pool_host.py#L553-L610)。

## SGLang 链路四：HiCache Host 到 Mooncake Store

当 node 已有 Host backup，`write_backup_storage` 会再次向 component 请求 `BACKUP_STORAGE` descriptor。Mamba component 不上传一串历史状态，只上传 node 末尾的一个 checkpoint：

```text
PoolTransfer(
  name = MAMBA,
  host_indices = node.mamba.host_value,
  keys = [node.hash_value[-1]],
  hit_policy = TRAILING_PAGES,
)
```

这段代码在 [`MambaComponent.build_hicache_transfers`](https://github.com/sgl-project/sglang/blob/297f9336c8bf81e2fcf06b930d2dd3551f7dec15/python/sglang/srt/mem_cache/unified_cache_components/mamba_component.py#L534-L560)。`TRAILING_PAGES` 的含义正适合递归状态：full/MLA 需要从头连续命中，而 KDA 只要求目标 prefix 末尾的 checkpoint object 存在。

Mooncake backend 注册 `MambaPoolHost` 后，将一个 logical page 展开成多个物理 object key：

```text
base_key = radix node 最后一个 page hash

{base_key}_{rank}_temporal
{base_key}_{rank}_conv_0
{base_key}_{rank}_conv_1 ...  # 若模型有多个 conv state
```

key 展开逻辑见 [`MooncakeStore._get_hybrid_page_component_keys`](https://github.com/sgl-project/sglang/blob/297f9336c8bf81e2fcf06b930d2dd3551f7dec15/python/sglang/srt/mem_cache/storage/mooncake_store/mooncake_store.py#L709-L774)。adapter 从 Host pool 取得每个 object 的 pointer/size，再调用 Mooncake 的零拷贝批量 API：

```text
backup  → batch_put_from(keys, pointers, sizes)
prefetch → batch_get_into(keys, pointers, sizes)
lookup  → batch_is_exist(keys)
```

SGLang 侧实现见 [`_batch_io_v2`](https://github.com/sgl-project/sglang/blob/297f9336c8bf81e2fcf06b930d2dd3551f7dec15/python/sglang/srt/mem_cache/storage/mooncake_store/mooncake_store.py#L831-L893)；Mooncake Python binding 将这些指针直接传给 Store client，见 [`store_py.cpp`](https://github.com/kvcache-ai/Mooncake/blob/3ae17993c15a7339229cd5cde386b0eda6397438/mooncake-integration/store/store_py.cpp#L2685-L2818)。

### Mooncake lookup 为什么不会拿到“半个 KDA checkpoint”

`batch_exists_v2` 对同一个 logical page 检查全部 temporal/conv component：只有这一页的所有 object 都存在，`page_exists` 才为 true。对于 Mamba/KDA 的 `TRAILING_PAGES` policy，它从候选 prefix 尾部向前寻找最近一个完整 checkpoint，再与 Full/MLA 的连续命中长度取最小值。实现见 [`MooncakeStore.batch_exists_v2`](https://github.com/sgl-project/sglang/blob/297f9336c8bf81e2fcf06b930d2dd3551f7dec15/python/sglang/srt/mem_cache/storage/mooncake_store/mooncake_store.py#L776-L829)。

因此，SGLang 以完整 checkpoint 为单位判断 KDA 命中：

```text
temporal exists AND every conv exists
  → KDA page hit

任一 component 缺失
  → 该 KDA page miss
```

## SGLang 链路五：另一实例怎样恢复 KDA checkpoint

远端实例请求相同 prefix 时，链路反向执行：

```text
1. UnifiedRadixCache 生成候选 prefix page hashes
2. HiCacheController 向 Mooncake batch_exists_v2
3. Full/MLA 连续页与 Mamba trailing checkpoint 协调出最终 hit
4. 为命中范围分配 Host KV pages 与一个 Host Mamba slot
5. Mooncake batch_get_into 直接写入这些 Host buffers
6. 把 Host indices 提交到 radix node.host_value
7. 请求运行前 load_back / CoW 到自己的 GPU Mamba slot
8. KDA 从 C(P_t) 继续递推 suffix
```

Mamba prefetch descriptor 只先分配一个 Host slot，实际 key 在 storage hit 长度确定后同步到“最后一个命中 page hash”；controller 对 trailing keys 的重定位见 [`_sync_trailing_keys`](https://github.com/sgl-project/sglang/blob/297f9336c8bf81e2fcf06b930d2dd3551f7dec15/python/sglang/srt/mem_cache/hybrid_cache/hybrid_cache_controller.py#L707-L725)。数据回来后，`commit_hicache_transfer(PREFETCH)` 把 Host slot 写入目标 radix node；后续 `LOAD_BACK` 再复制到 GPU request slot，见 [`MambaComponent.commit_hicache_transfer`](https://github.com/sgl-project/sglang/blob/297f9336c8bf81e2fcf06b930d2dd3551f7dec15/python/sglang/srt/mem_cache/unified_cache_components/mamba_component.py#L565-L628)。

## SGLang + HiCache 当前仍缺什么：branching-state fill

上面的数据面链路已经显式支持 Mamba/KDA：Host pool 有 temporal/conv buffers，Mooncake 有 component keys、完整性 lookup、batch put/get，radix node 也有 `host_value`。

但“Store 中不存在某个共享分叉 checkpoint 时，是否自动补出它”是另一件事。`MambaComponent.finalize_match_result` 的源码明确写着：

```text
if cache_controller is None and full prefix longer than Mamba hit:
  calculate mamba_branching_seqlen
else:
  branching_seqlen = None
```

也就是说，本地 UnifiedRadixCache 会做 branching-state fill；一旦 HiCache controller 存在，这个策略暂时跳过，等待 HiCache-aware branching policy。见 [`mamba_component.py`](https://github.com/sgl-project/sglang/blob/297f9336c8bf81e2fcf06b930d2dd3551f7dec15/python/sglang/srt/mem_cache/unified_cache_components/mamba_component.py#L97-L148)。

因此对 `req1=C(P_4k)`、`req2` 只共享 `P_1k` 的例子：

```text
Mooncake 已有 MLA(P_1k) + KDA C(P_1k)
  → SGLang HiCache 可以完整恢复并复用 P_1k

Mooncake 只有 MLA(P_1k)，没有 C(P_1k)
  → KDA component miss，最终 hit 必须缩短
  → 当前 HiCache 路径不会利用 MLA-only 的更长命中自动要求
    KDA forward 在 P_1k 生成 branching checkpoint
```

问题不在 Mooncake 的数据传输，而在于 HiCache 控制面尚未触发缺失 checkpoint 的创建。

## vLLM prefill 默认只把 step 末状态写回 state slot

KDA prefill 的算子路径是：

```text
hidden_states
  -> q_proj / k_proj / v_proj
  -> causal_conv1d_fn(..., conv_states, cache_indices)
  -> convolved q / k / v
  -> chunk_kda_with_fused_gate(..., initial_state, output_final_state=True)
  -> last_recurrent_state
  -> recurrent_state[state_index] = last_recurrent_state
```

短卷积函数会使用并更新当前 state index 下的 conv history；KDA chunk kernel 只请求 `output_final_state=True`，随后把 `last_recurrent_state` 写回同一个 state index。核心代码见 [`kimi_gdn_linear_attn.py`](https://github.com/vllm-project/vllm/blob/387189c42997b27e2c04b5d97ef8190ffa2bf909/vllm/model_executor/layers/mamba/gdn/kimi_gdn_linear_attn.py#L303-L417)。

这意味着，在当前 Kimi vLLM 集成里，一次长度 4k 的 prefill forward 自然产生的是该序列末尾的 `C(P_4k)`。它没有像 SGLang 的某些 KDA kernel 路径那样，把 forward 内部多个 chunk 的 `h` 暴露给 runtime，让 runtime 一次性挑选 `C(P_1k)`、`C(P_2k)`、`C(P_3k)`。

Decode 则使用 `causal_conv1d_update` 原地推进卷积历史，再通过 `fused_recurrent_kda` 推进递归状态。见同一文件的 [decode 分支](https://github.com/vllm-project/vllm/blob/387189c42997b27e2c04b5d97ef8190ffa2bf909/vllm/model_executor/layers/mamba/gdn/kimi_gdn_linear_attn.py#L342-L445)。

由此得到两个不可绕过的性质：

```text
C(P_4k) 可以向前推进到 C(P_4k+n)
C(P_4k) 不能反推回 C(P_1k)
```

后来的请求如果只共享 1k prefix，而系统没有 `C(P_1k)`，保存着 `C(P_4k)` 对它没有帮助。

## Kimi Linear 在 vLLM 中使用 align 模式

vLLM 暴露三种 `mamba_cache_mode`：

```text
none
  不做 Mamba/KDA prefix cache

all
  在所有 i * block_size 位置缓存状态，前提是模型实现支持

align
  只在 scheduler step 末尾且位置满足缓存对齐时物化状态
```

定义见 [`CacheConfig.mamba_cache_mode`](https://github.com/vllm-project/vllm/blob/387189c42997b27e2c04b5d97ef8190ffa2bf909/vllm/config/cache.py#L127-L147)。

`KimiLinearForCausalLM` 实现了 `HasInnerState` 和 `IsHybrid`，但没有实现 `SupportsMambaPrefixCaching` 协议，见 [`kimi_linear.py`](https://github.com/vllm-project/vllm/blob/387189c42997b27e2c04b5d97ef8190ffa2bf909/vllm/model_executor/models/kimi_linear.py#L557-L633)。配置校验因此会把 Kimi Linear 选到 `align`；即使用户强行指定 `all`，也会回退到 `align`。这段选择逻辑在 [`MambaModelConfig.verify_and_update_config`](https://github.com/vllm-project/vllm/blob/387189c42997b27e2c04b5d97ef8190ffa2bf909/vllm/model_executor/models/config.py#L545-L594)。

`align` 的意义不是“每个 block 都有状态”，而是“block table 仍按完整序列位置建立，但绝大多数位置可以是 null placeholder，只有 scheduler step 结束的位置拥有真实 state page”。

内存估算也体现了这一点：

```text
all:
  每请求最多约 ceil(max_model_len / block_size) 个状态页

align:
  每请求运行时只需要 2 + num_speculative_blocks 个状态页
  但逻辑 block table row 仍覆盖整个序列长度
```

见 [`MambaSpec.max_memory_usage_bytes`](https://github.com/vllm-project/vllm/blob/387189c42997b27e2c04b5d97ef8190ffa2bf909/vllm/v1/kv_cache_interface.py#L689-L730)。

## align 模式如何让一个状态页跨 scheduler step 前进

`MambaManager` 在 align 模式下维护 `last_state_block_idx`。每个 step 为当前运行状态准备一个新的尾部 state block；worker 在 forward 前，把上一步状态从旧 block 复制到这个新 block，然后本次 KDA 算子原地推进新 block。再过一个 step，更早的 state block 才会被释放并替换成 null placeholder。

可以把它理解成双缓冲式滚动：

```text
step n 开始
  previous state block --copy--> current tail state block
  current tail --KDA forward--> C(P_end_n)

step n+1 开始
  C(P_end_n) --copy--> next tail state block
  更早的 state block 变成 null / 可释放
```

manager 的分配与释放逻辑见 [`MambaManager.remove_skipped_blocks`](https://github.com/vllm-project/vllm/blob/387189c42997b27e2c04b5d97ef8190ffa2bf909/vllm/v1/core/single_type_kv_cache_manager.py#L1384-L1413) 和 [`allocate_new_blocks`](https://github.com/vllm-project/vllm/blob/387189c42997b27e2c04b5d97ef8190ffa2bf909/vllm/v1/core/single_type_kv_cache_manager.py#L1500-L1604)。worker 侧的复制入口是 [`preprocess_mamba`](https://github.com/vllm-project/vllm/blob/387189c42997b27e2c04b5d97ef8190ffa2bf909/vllm/v1/worker/mamba_utils.py#L992-L1055)。

当某个 step 末状态被赋予 prefix hash 后，它就不再只是请求的运行状态，也成为其他请求可命中的 checkpoint。`MambaManager.find_longest_cache_hit` 从目标 prefix 的最右边向左搜索；一旦找到一个 KDA state block，就在前面补 null placeholders 并返回该边界。它不需要像 full attention 那样拿到从 0 到边界的所有 state block，因为一个终点状态已经压缩了全部历史。见 [`find_longest_cache_hit`](https://github.com/vllm-project/vllm/blob/387189c42997b27e2c04b5d97ef8190ffa2bf909/vllm/v1/core/single_type_kv_cache_manager.py#L1248-L1324)。

## req1 只有 C(P_4k) 时，req2 第一次仍要重算 1k

现在回到具体例子：

```text
req1 prompt = P_4k
req2 prompt = P_1k + S_1k
req1 与 req2 只共享前 1k
```

假设 req1 的 4k prefill 在一个大 forward 中完成：

```text
MLA cache: P_1k、P_2k、P_3k、P_4k 对应的分页 KV 都在
KDA cache: 只有 scheduler step 末尾的 C(P_4k)
```

req2 不能使用 `C(P_4k)`，因此它第一次到来时，至少必须从头处理共享的 1k，才能生成 `C(P_1k)`。vLLM 会按需截断这次分叉请求，无需预先把所有请求固定切成 1k。

本地 hybrid coordinator 会分别看各 cache group 的命中：

```text
Full/MLA group hit = 1k
KDA/Mamba group hit = 0

hybrid 可恢复命中 = 0
最长单组命中       = 1k
缺失的公共前缀     = 1k - 0 = 1k
```

协调器用单调递减的 fixed-point 算法求所有 group 都能接受的命中长度，并额外返回 `num_uncached_common_prefix_tokens`，见 [`HybridKVCacheCoordinator.find_longest_cache_hit`](https://github.com/vllm-project/vllm/blob/387189c42997b27e2c04b5d97ef8190ffa2bf909/vllm/v1/core/kv_cache_coordinator.py#L676-L808)。`KVCacheManager.get_computed_blocks` 再把它转成：

```text
shared_prefix_boundary
  = reconciled_hit + uncached_common_prefix
  = 0 + 1k
```

见 [`kv_cache_manager.py`](https://github.com/vllm-project/vllm/blob/387189c42997b27e2c04b5d97ef8190ffa2bf909/vllm/v1/core/kv_cache_manager.py#L222-L288)。

随后 scheduler 把 req2 这次本来可能更长的 prefill 截到 1k。forward 结束时 KDA 算子自然写出 `C(P_1k)`；cache manager 给它绑定 P_1k 的 hash，并把这个分叉点 pin 住。下一次 scheduler step 才继续 req2 的后 1k。

这里最容易误解的一点是：req2 的第一次 1k 不是只算 KDA 层。当前 hybrid model forward 仍会经过整网，所以此前 MLA 已经有 P_1k，也要随这 1k 一起重算。系统做的是“一次性补齐后续可复用的分叉 checkpoint”，不是只补一类层的旁路计算。

## 不需要把全局 chunked prefill 设成 1k

`align` 模式确实要求启用 chunked prefill，但“允许把 prefill 分 step”与“固定每 1k 做一次 forward”不是同一件事。

`Scheduler._mamba_block_aligned_split` 会在当前计划区间中寻找必须提前停下的位置：

```text
1. 从细粒度 partial hit 恢复后遇到的下一个 block boundary
2. prompt 最后一个可缓存的 block boundary
3. prefix_match_unit 比物理 block 更细时的 partial-tail boundary
4. 当前请求发现的 shared_prefix_boundary
```

只有这些位置严格落在本次大 chunk 内部时，scheduler 才截断到最早一个。源码见 [`_mamba_block_aligned_split`](https://github.com/vllm-project/vllm/blob/387189c42997b27e2c04b5d97ef8190ffa2bf909/vllm/v1/core/sched/scheduler.py#L351-L419)。

因此可以保留较大的 `max_num_batched_tokens` 或 long-prefill budget：

```text
没有已知分叉点
  -> 允许一个 4k、8k 或更大的 forward

发现缺失的 P_1k 分叉点
  -> 只让这次请求先停在 1k
  -> 下一 step 再继续后缀

分叉 checkpoint 已经存在
  -> 后来的请求直接从 1k 恢复，不再重复补点
```

在这种策略下，额外的 forward 次数由实际出现的共享分叉点决定，而不是按每个长 prompt 的长度固定增长。

## prefix_match_unit 只改变匹配粒度，不会生成状态

`--prefix-match-unit` 很容易被误当成 checkpoint interval。它实际控制 rolling hash 每隔多少 token 产生一个可匹配边界，可以比物理 cache block 更细；它明确**不控制状态多久保存一次**。定义见 [`CacheConfig.prefix_match_unit`](https://github.com/vllm-project/vllm/blob/387189c42997b27e2c04b5d97ef8190ffa2bf909/vllm/config/cache.py#L56-L67)。

把它设成 1k 只能表示：

```text
“P_1k 可以成为一个 hash lookup boundary”
```

不能表示：

```text
“一次 P_4k forward 会自动额外产生 C(P_1k)、C(P_2k)、C(P_3k)”
```

要实际生成一个 KDA state，仍然需要以下至少一种机制：

```text
forward 恰好在该位置结束
算子显式导出 forward 内部中间状态
或从更早 checkpoint 重放到该位置
```

当前 vLLM Kimi 路径选择第一种，并由 scheduler 在必要时制造 step end。

## retention interval 决定“保留谁”，不是“创建谁”

当前 vLLM 还有一个环境变量：

```text
VLLM_PREFIX_CACHE_RETENTION_INTERVAL
```

它作用于 sliding-window 与 Mamba/linear-attention checkpoint 的稀疏保留。合法值必须是非负数，并且是 scheduler block size 的整数倍，校验见 [`kv_cache_coordinator.py`](https://github.com/vllm-project/vllm/blob/387189c42997b27e2c04b5d97ef8190ffa2bf909/vllm/v1/core/kv_cache_coordinator.py#L30-L57)。

`MambaManager.reachable_block_mask` 的语义是：

```text
未设置 None
  -> 不加稀疏 mask，保留所有已经物化且有 hash 的状态

设置为 0
  -> 只保留 proven reachable boundaries
     包括 replay boundary 和检测到的共享前缀分叉点

设置为正数 N
  -> 每个 N-token segment 保留一个尾状态
  -> 同时始终保留 replay boundary 与共享前缀分叉点
```

实现见 [`reachable_block_mask`](https://github.com/vllm-project/vllm/blob/387189c42997b27e2c04b5d97ef8190ffa2bf909/vllm/v1/core/single_type_kv_cache_manager.py#L1326-L1382)，跨请求分叉 pin 的单测见 [`test_mamba_shared_prefix_reuse_under_zero_retention`](https://github.com/vllm-project/vllm/blob/387189c42997b27e2c04b5d97ef8190ffa2bf909/tests/v1/core/test_prefix_caching.py#L4167-L4220)。

要特别注意“已经物化”四个字。假设一次 4k forward 只写出 `C(P_4k)`：

```text
retention interval = 1k
```

不会凭空生成 `C(P_1k)`、`C(P_2k)`、`C(P_3k)`。它只能在已有多个 checkpoint 时决定哪些 hash/state 继续留在 cache。换句话说：

```text
creation policy  = scheduler step end / operator snapshot
retention policy = reachable_block_mask
match granularity = prefix_match_unit
```

这三者必须分开配置和排障。

## 本地 vLLM 的完整调用链

把前面的部分串起来，一次本地 KDA prefix cache 的主链是：

```text
KimiLinearForCausalLM
  -> KimiDecoderLayer selects KDA or MLA
  -> KimiGatedDeltaNetAttention.get_kv_cache_spec
  -> MambaSpec(shapes, dtypes, page_size, block_size, mode=align)

GPU allocation
  -> one raw byte page per layer per physical state block
  -> MambaBase.bind_kv_cache
  -> (conv_state_view, recurrent_state_view)

Request admission
  -> KVCacheManager.get_computed_blocks
  -> HybridKVCacheCoordinator fixed point
  -> reconciled hit + uncached common-prefix length
  -> request.shared_prefix_boundary

Scheduling
  -> _mamba_block_aligned_split
  -> optional early stop at missing shared-prefix boundary
  -> MambaManager allocates current tail state block

Worker
  -> preprocess_mamba copies previous state to current tail
  -> GDN metadata selects state block id
  -> causal conv + chunk/recurrent KDA updates page in place

Cache commit
  -> MambaManager.cache_blocks attaches prefix hash
  -> reachable_block_mask keeps replay/boundary/interval states
  -> later request finds the rightmost matching KDA state
```

这部分调用链可以由固定提交中的源码与测试确认。

## MooncakeConnector 用于 Prefill/Decode 传输，MooncakeStoreConnector 提供共享 prefix 存储

vLLM 里有两个名字相近但语义不同的 Mooncake connector：

```text
MooncakeConnector
  P/D disaggregation 间直接搬运请求对应的 cache blocks

MooncakeStoreConnector
  把 cache block 按 hash 存进共享 Mooncake Distributed Store
  供后续请求 lookup
```

直接 `MooncakeConnector` 已经加入 hybrid FA + GDN 的 group-aware block 传输：它保留每个 cache group 的 block id，跳过 Mamba null placeholder，并且在 P/D 模式下按 `N-1` 状态交接，让 decode 端重算最后一个 token。相关 scheduler 逻辑见 [`MooncakeConnectorScheduler`](https://github.com/vllm-project/vllm/blob/387189c42997b27e2c04b5d97ef8190ffa2bf909/vllm/distributed/kv_transfer/kv_connector/v1/mooncake/mooncake_connector.py#L629-L752)。

但这里的测试标题和注释都写的是 GDN，测试 `mamba_type=GDN_ATTN`，没有以 Kimi Linear KDA 做端到端验证。KDA 确实继承 GDN base，并报告同一个 `GDN_ATTN` backend enum；这说明接口分派能走到同一类 `MambaSpec`，却不能自动证明 Kimi 的两种状态和布局都被正确搬运。

在本文固定的 vLLM 提交中，Mamba raw-page layout 已统一为单个完整 raw tensor，但直接 Mooncake worker 的 Mamba 注册分支仍按 tuple 解包：

```python
conv, _ = cache_or_caches
cache_list = [conv]
```

见 [`MooncakeConnectorWorker.register_kv_caches`](https://github.com/vllm-project/vllm/blob/387189c42997b27e2c04b5d97ef8190ffa2bf909/vllm/distributed/kv_transfer/kv_connector/v1/mooncake/mooncake_connector.py#L1653-L1717)。对应单测仍手工传 `(gdn_conv_state, gdn_ssm_state)` tuple，见 [`test_mooncake_connector_hybrid_mamba.py`](https://github.com/vllm-project/vllm/blob/387189c42997b27e2c04b5d97ef8190ffa2bf909/tests/v1/kv_connector/unit/test_mooncake_connector_hybrid_mamba.py#L123-L163)。

因此，该固定提交中的 direct connector 与新 raw-page 接口仍需专项核对，现有证据不足以确认 KDA P/D 传输已经端到端可用。

## MooncakeStoreConnector 的数据结构能容纳完整 KDA page

共享 Store 路径在结构上更接近我们想要的 prefix cache：

```text
one ChunkedTokenDatabase per cache group

PoolKey
  = model
  + tp / pcp / dcp / pp namespace
  + group id
  + chained prefix hash

value
  = one or more memory segments belonging to that group's physical block
```

key 格式见 [`PoolKey`](https://github.com/vllm-project/vllm/blob/387189c42997b27e2c04b5d97ef8190ffa2bf909/vllm/distributed/kv_transfer/kv_connector/v1/mooncake/store/data.py#L98-L163)。worker 注册 cache 时按底层 raw storage 去重，并用 `region_len / num_blocks` 得出每个 block 的完整 page 大小，见 [`MooncakeStoreWorker.register_kv_caches`](https://github.com/vllm-project/vllm/blob/387189c42997b27e2c04b5d97ef8190ffa2bf909/vllm/distributed/kv_transfer/kv_connector/v1/mooncake/store/worker.py#L1205-L1276)。

因为 KDA 的 conv 和 recurrent state 已经被打包到同一个 raw page，Mooncake Store object 在数据面上可以保存完整 `S_l(t)`，不需要 Store 理解 KDA 数学。

配置层也显式接受 `MambaSpec`，但要求它的 block size 与 cache block size 相同，也就是 align 模式。见 [`MooncakeStoreConnector._validate_kv_cache_config`](https://github.com/vllm-project/vllm/blob/387189c42997b27e2c04b5d97ef8190ffa2bf909/vllm/distributed/kv_transfer/kv_connector/v1/mooncake/store/connector.py#L98-L126)。

外部 lookup coordinator 还会复用各类 cache manager 的命中规则，对 full attention、SWA、Mamba 做 fixed-point 协调，并生成每组 load mask。见 [`MooncakeStoreCoordinator`](https://github.com/vllm-project/vllm/blob/387189c42997b27e2c04b5d97ef8190ffa2bf909/vllm/distributed/kv_transfer/kv_connector/v1/mooncake/store/coordinator.py#L60-L177)。

所以从数据结构看，这条映射是成立的：

```text
prefix hash @ group=MLA
  -> MLA page object(s)

same prefix hash @ group=KDA
  -> KDA raw state page(s)
     -> every KDA layer's conv + recurrent bytes
```

如果 Store 里已经同时存在 P_1k 的 MLA pages 与 `C(P_1k)`，consumer 可以协调出 1k hit，并把两组数据装回各自 GPU blocks。这是“接口形状允许”的部分。

## Mooncake Store 尚未打通缺失分叉 checkpoint 的自动补算

需要继续确认的是：当 `C(P_1k)` 不存在时，系统能否发现这个缺口并自动补算。

本地路径依靠三项信息：

```text
reconciled hybrid hit
longest single-group hit
shared_prefix_boundary = 两者之间的缺口终点
```

挂上 connector 且模型含 Mamba layer 后，scheduler 走特殊分支：它调用 `find_longest_cache_hit_per_group`，随后把 `num_new_local_computed_tokens` 设成所有 group hit 的最大值，并把 `request.shared_prefix_boundary` 清零。代码见 [`scheduler.py`](https://github.com/vllm-project/vllm/blob/387189c42997b27e2c04b5d97ef8190ffa2bf909/vllm/v1/core/sched/scheduler.py#L711-L759)。

这条分支原本服务 P/D connector：注释说明 full-attention 本地命中可以避免重复传输，而 Mamba state 由 NIXL worker 无条件传输。这套传输假设不能直接套用于共享 Store 的 prefix lookup。

对前面的 req1/req2 例子：

```text
local MLA hit = 1k
local KDA hit = 0

本地无 connector 路径
  -> reconciled hit = 0
  -> shared_prefix_boundary = 1k
  -> scheduler 停在 1k 补 C(P_1k)

connector 特殊路径
  -> max(per_group_hits) = 1k
  -> shared_prefix_boundary = 0
  -> shared_prefix_boundary 补点信息丢失
```

Mooncake Store 自己的外部 coordinator 也只返回最终协调后的 hit length 与 load mask，没有向 scheduler 返回“某个 group 曾命中更长，因此这里存在待补分叉点”。因此，当 Store 只有 P_1k 的 MLA object、没有 KDA object 时，它会返回 0 hit，却不会告诉 scheduler 应在 1k 停一次。

还有两个需要验证的边界：

1. Store 的 save mask 只接收 prompt replay boundary，没有接收 `shared_prefix_boundary`。即使 scheduler 恢复补点，也需要把分叉点的 pin 信息继续传到 Store retention 层，否则稀疏 retention 可能再次丢掉它。入口见 [`MooncakeStoreCoordinator.store_mask`](https://github.com/vllm-project/vllm/blob/387189c42997b27e2c04b5d97ef8190ffa2bf909/vllm/distributed/kv_transfer/kv_connector/v1/mooncake/store/coordinator.py#L179-L253)。

2. align 模式的 KDA block table 含有大量 `NULL_BLOCK_ID`。直接 MooncakeConnector 显式过滤 null，而 MooncakeStore 的 `ChunkedTokenDatabase.prepare_value` 直接用逻辑位置取 block id 并计算地址，见 [`data.py`](https://github.com/vllm-project/vllm/blob/387189c42997b27e2c04b5d97ef8190ffa2bf909/vllm/distributed/kv_transfer/kv_connector/v1/mooncake/store/data.py#L196-L214)。当前 Store HMA 端到端测试覆盖的是 SWA + Full，不是 Mamba/KDA，见 [`test_mooncake_store_hma_e2e.py`](https://github.com/vllm-project/vllm/blob/387189c42997b27e2c04b5d97ef8190ffa2bf909/tests/v1/kv_connector/unit/test_mooncake_store_hma_e2e.py#L1-L4)。

因此，在本文版本上不能把下面这条链写成已完成：

```text
req1 stores MLA(P_1k...) + KDA C(P_4k)
  -> req2 detects remote MLA-only P_1k boundary
  -> req2 computes exactly to P_1k
  -> Mooncake Store persists C(P_1k)
  -> req3 remotely reuses MLA(P_1k) + C(P_1k)
```

本地 cache core 已具备识别分叉点的机制，Mooncake Store 数据面也能保存完整 raw page；缺失的是把分叉点信号继续传递到 connector scheduler、Store metadata 与 Store retention。

## 把 SGLang、vLLM 与 Mooncake 放在同一张链路图上

两边都面对同一个数学约束：有限状态只能向前推进，不能从 `C(P_4k)` 回滚到 `C(P_1k)`。差异发生在 checkpoint 的创建、索引和序列化方式上。

```text
阶段                    SGLang                         vLLM
────────────────────────────────────────────────────────────────────────────
KDA GPU 状态            跨层 Mamba slot               每层 raw state page

prefill 中间状态        kernel 可返回 h                当前 Kimi 路径只提交末状态

本地 prefix 索引        radix node + component         block hash + cache group

本地分叉补点            从大 forward 的 h 抽取         scheduler 在分叉点截断

Host staging            HiCache MambaPoolHost          connector 注册 GPU raw pages

Mooncake value           temporal + conv objects        group raw-page object/segments

完整 KDA hit 条件        全部 temporal/conv 存在         KDA group 对应 page 可加载

远端缺失分叉点         HiCache 下暂不自动 fill         connector 分支丢 boundary
```

能力状态可以更精确地归类为：

```text
能力                         SGLang 本地   SGLang + HiCache/Mooncake
Kimi KDA prefix correctness  有专项 e2e    数据结构与调用链支持 Mamba sidecar
大 forward 抽中间状态       已实现        同一 kernel 基础可用
完整 checkpoint 远端读写    不适用        temporal/conv batch put/get 已实现
缺失分叉 checkpoint 自动补  已实现        当前显式跳过
Kimi + Mooncake 专项 e2e     不适用        本文快照未发现

能力                         vLLM 本地     vLLM + MooncakeStoreConnector
Kimi KDA 状态页              已实现        raw-page 数据结构可承载
大 forward 抽中间状态       未暴露        未暴露
缺失分叉 checkpoint 自动补  已实现        boundary 未传播
完整 checkpoint 远端读写    不适用        接口允许，KDA 专项端到端证据不足
Kimi + Mooncake 专项 e2e     不适用        本文快照未发现
```

SGLang 的 Kimi `extra_buffer` prefix-cache 回归测试会跑 branching、KL 与 GSM8K，见 [`test_kimi_linear_models.py`](https://github.com/sgl-project/sglang/blob/297f9336c8bf81e2fcf06b930d2dd3551f7dec15/test/registered/models_e2e/test_kimi_linear_models.py#L20-L80)。UnifiedRadixCache 的 HiCache L3 测试已经覆盖 hybrid Mamba + file backend，但模型是 Qwen3-Next，不是 Kimi，见 [`test_unified_radix_cache_kl_mamba.py`](https://github.com/sgl-project/sglang/blob/297f9336c8bf81e2fcf06b930d2dd3551f7dec15/test/registered/radix_cache/unified_radix_tree/test_unified_radix_cache_kl_mamba.py#L137-L202)。Mooncake 单测验证 standalone mapping 会计入 Mamba temporal/conv buffers，但仍不是 Kimi 远端 replay e2e，见 [`test_mooncake_standalone_dummy_mamba.py`](https://github.com/sgl-project/sglang/blob/297f9336c8bf81e2fcf06b930d2dd3551f7dec15/test/registered/unit/mem_cache/test_mooncake_standalone_dummy_mamba.py#L21-L143)。

## Mooncake Store 在整条链中负责什么

Mooncake Store 的接口是 key/value bytes，而不是 attention-aware cache。两套 adapter 最终都会调用同一类 API：

```text
register_buffer(pointer, size)
batch_is_exist(keys)
batch_put_from(keys, source_pointers, sizes)
batch_get_into(keys, destination_pointers, sizes)
```

Python binding 对应源码见 [`store_py.cpp`](https://github.com/kvcache-ai/Mooncake/blob/3ae17993c15a7339229cd5cde386b0eda6397438/mooncake-integration/store/store_py.cpp#L2685-L2818)。Store client 的 batch put/get 再负责对象元数据、目标位置与实际传输，入口见 [`RealClient::batch_put_from`](https://github.com/kvcache-ai/Mooncake/blob/3ae17993c15a7339229cd5cde386b0eda6397438/mooncake-store/src/real_client.cpp#L3690-L3717) 和 [`RealClient::batch_get_into`](https://github.com/kvcache-ai/Mooncake/blob/3ae17993c15a7339229cd5cde386b0eda6397438/mooncake-store/src/real_client.cpp#L4262-L4287)。

Mooncake 的 master 管理逻辑空间、对象放置与逐出；store service 提供可被远端访问的连续内存。实际数据可以在 SGLang/vLLM 与 store service 之间直接传输，不必经 master 中转。官方架构说明见 [`SGLang HiCache integration guide`](https://github.com/kvcache-ai/Mooncake/blob/3ae17993c15a7339229cd5cde386b0eda6397438/docs/source/getting_started/examples/sglang-integration/hicache-integration-v1.md#L60-L84)。

因此职责边界是：

```text
引擎 / adapter 负责
  token prefix hash
  cache group / component namespace
  checkpoint 边界
  pointer、size、dtype/layout 一致性
  hybrid hit 协调
  缺失 checkpoint 的补算策略

Mooncake Store 负责
  object existence 与生命周期
  分布式容量和副本
  buffer registration
  RDMA/TCP/本地等数据传输
  把 opaque bytes 放到指定 destination buffer
```

### SGLang 和 vLLM 不能默认跨引擎复用同一个 KDA object

即使两边连接同一个 Mooncake 集群，也不能认为 SGLang 写入的 KDA checkpoint 能被 vLLM 直接读取。原因至少有三层：

```text
key namespace 不同
  SGLang: radix hash + rank/component suffix
  vLLM: PoolKey(model/parallel/cache-group/prefix-hash...)

value layout 不同
  SGLang: all-layer temporal buffer + conv buffer components
  vLLM: each KDA layer's raw page

checkpoint policy 不同
  SGLang: mamba_cache_chunk_size / tracked h
  vLLM: align step-end state / scheduler split
```

Mooncake 不会转换这些格式。跨引擎共享需要额外定义稳定的模型版本、token hash、并行 rank、layer 顺序、dtype、shape、byte layout 与 checkpoint boundary ABI；当前两套 adapter 尚未实现这样的公共 ABI。

## 同一个 req1 / req2 / req3 案例怎样穿过两条链

设：

```text
req1 = P_4k
req2 = P_1k + A_1k
req3 = P_1k + B_1k
```

### SGLang 本地

```text
req1 大 prefill
  → 可以在最后一个可追踪边界保存 C(P_t)

req2 匹配到更长 Full/MLA prefix、没有等长 KDA state
  → 产生 mamba_branching_seqlen=P_1k（按 chunk 对齐）
  → req2 的大 extend 返回中间 h
  → 抽取并插入 C(P_1k)

req3
  → radix node 同时有 Full/MLA prefix 与 C(P_1k)
  → CoW 后从 P_1k 继续
```

### SGLang + HiCache + Mooncake

```text
Mooncake 已经存在 Full/MLA(P_1k) + C(P_1k)
  → exists 协调出 P_1k
  → batch_get_into Host pools
  → load_back GPU
  → req3 远端复用成功

Mooncake 只有 Full/MLA(P_1k)，没有 C(P_1k)
  → KDA sidecar miss，最终 hit 缩短
  → 当前 HiCache 不产生 branching_seqlen
  → 不会自动借 req2 补出并上传 C(P_1k)
```

### vLLM 本地

```text
req1 只有 C(P_4k)
  → req2: MLA hit=P_1k, KDA hit=0
  → shared_prefix_boundary=P_1k
  → scheduler 把 req2 首次 prefill 截到 P_1k
  → step end 生成并 pin C(P_1k)
  → req3 本地命中 P_1k
```

### vLLM + MooncakeStoreConnector

```text
Store 已有 MLA(P_1k) + KDA raw pages @ P_1k
  → 数据结构允许协调并加载完整 checkpoint

Store 只有 MLA(P_1k)
  → connector 特殊路径不传播 shared_prefix_boundary
  → Store coordinator 也不返回落后 cache group 的分叉边界
  → req2 不会自动沿用本地的分叉点截断机制补算状态
```

## 补齐两条远端复用链分别需要什么

### SGLang + HiCache + Mooncake

最小改动是让 HiCache-aware match 同时返回：

```text
final_hybrid_hit
longest_full_prefix
best_kda_checkpoint
missing_branching_boundary
```

当 `longest_full_prefix > best_kda_checkpoint` 时，允许 scheduler/backend 继续利用现有中间 `h` 抽取分叉 checkpoint；随后确保该新 node 进入 `BACKUP_HOST → BACKUP_STORAGE`，并由 Mooncake component lookup 验证 temporal/conv 全部落盘。

### vLLM + MooncakeStoreConnector

最小改动是让本地已有的分叉点信息穿过 connector：

```text
1. local + external lookup 都保留 per-group hit
2. scheduler 对合并结果做 hybrid fixed point
3. missing_boundary > final_hit 时设置 shared_prefix_boundary
4. _mamba_block_aligned_split 在 missing_boundary 结束 forward
5. Store ReqMeta / save mask pin 住新 KDA state
6. KDA group 保存完整 raw page，过滤 NULL placeholders
```

两边都应补同一个测试矩阵：

```text
local branch fill
  req1=4k, req2 shares 1k, req3 shares 1k

remote complete hit
  Store 同时存在 MLA(P_1k) 与 C(P_1k)
  加载后 logits 与无缓存 baseline 一致

remote partial-group hit
  Store 只有 MLA(P_1k)
  req2 只付一次补算，随后上传 C(P_1k)
  req3 在另一实例完整命中

object integrity
  temporal/conv 或 raw-page 任一部分缺失必须判 miss
```

## 配置时应如何理解两套引擎的旋钮

### SGLang

```text
--mamba-radix-cache-strategy extra_buffer
  允许用额外 track slots 保存 prefix checkpoint

--page-size
  radix 与 HiCache 的 page 粒度；会参与 mamba_cache_chunk_size 计算

--mamba-track-interval
  decode 状态追踪间隔，不等于强制 prefill forward 大小

--chunked-prefill-size
  scheduler prefill budget；可以大于 checkpoint 粒度

--enable-hierarchical-cache
--hicache-storage-backend mooncake
  启用 GPU→Host→Mooncake 层级链路

--hicache-storage-prefetch-policy
  best_effort / wait_complete / timeout 决定等待远端 prefetch 的策略
```

Mooncake 官方 quick start 的最小 SGLang 启动参数见 [`hicache-quick-start.md`](https://github.com/kvcache-ai/Mooncake/blob/3ae17993c15a7339229cd5cde386b0eda6397438/docs/source/getting_started/examples/sglang-integration/hicache-quick-start.md#L42-L58)。它展示的是通用 HiCache 部署；对 Kimi 还必须额外验证 KDA sidecar 与模型正确性。

### vLLM

```text
enable_prefix_caching
  必须启用，Kimi 才进入 Mamba/KDA prefix cache 配置

mamba_cache_mode=align
  当前 Kimi 的实际模式；all 不受模型实现支持

enable_chunked_prefill
  align 模式要求开启，但不代表全局 budget 必须设成 1k

max_num_batched_tokens / long prefill budget
  可以保持较大；本地 scheduler 只在实际分叉点额外截断

prefix_match_unit
  调整 hash 命中粒度，不创建 KDA checkpoint

VLLM_PREFIX_CACHE_RETENTION_INTERVAL
  调整已创建 checkpoint 的保留密度，不创建 checkpoint
```

验证时不要一开始就把两边的 prefill budget 都降到 1k，否则无法区分“按需补点生效”与“所有请求本来就被机械切成 1k”。如果目标是 Mooncake Store，也不能只看 server 能否启动或 Store 是否出现 Mamba/KDA key；必须检查 object 完整性、hybrid hit、补点传播和 replay logits。

## 六个常见误区

### 1. 把最后 3 个 token 理解成卷积输出

KDA conv cache 保存的是投影后、短卷积前的 Q/K/V 历史。卷积后的 q/k/v 是当前 KDA 计算输入，不是下一步直接平移保存的同一对象。

### 2. 把一个逻辑 checkpoint 理解成一个 tensor

`C(P_t)` 是所有 KDA 层状态的集合。vLLM 用一个逻辑 block id 索引每个 KDA 层的 raw page；SGLang 用一个逻辑 Mamba slot 索引跨层 temporal/conv buffers。

### 3. 认为 hash boundary 等于 state snapshot

`prefix_match_unit` 只产生可寻址边界。没有算子输出或 forward step end，就没有对应的 `C(P_t)`。

### 4. 认为 retention interval 会补历史状态

retention 只能删选已有 checkpoint，不能从 `C(P_4k)` 派生 `C(P_1k)`。

### 5. 看到 Mamba/KDA 数据面支持就认为可以自动补算分叉状态

SGLang 已能把 Mamba temporal/conv sidecar 写进 Mooncake；vLLM 的 `MambaSpec` 也能让 KDA raw page 进入 group-aware layout。但数据面可搬运不自动解决分叉点发现、scheduler/backend 补点、Store pin 与端到端正确性测试。

### 6. 认为同一个 Mooncake 集群天然提供 SGLang ↔ vLLM 互操作

Store object 是 opaque bytes。两套引擎的 key namespace、并行 rank 编码、物理 layout 与 checkpoint policy 不同；没有额外的公共 ABI，不能跨引擎直接复用。

## 最终判断

回到 req1/req2 示例，可以分三层判断：

> req1 的 4k prefill 如果只留下 `C(P_4k)`，req2 第一次共享 1k 时确实必须重新计算这 1k；`C(P_4k)` 无法回滚，MLA pages 也不能替代 KDA state。

> SGLang 本地可以让 req2 的大 extend 跨过 1k，再从 kernel 返回的中间 `h` 抽出并插入 `C(P_1k)`；vLLM 本地则把 req2 动态截到 1k，利用 step end 补出并 pin `C(P_1k)`。两边都不要求把所有请求的 prefill budget 固定成 1k。

再加上外部缓存限定：

> SGLang + HiCache 已把 KDA 的 temporal/conv checkpoint 接到 Mooncake 的完整读写数据面，但 HiCache 模式暂时跳过 branching-state fill；vLLM 本地已有共享前缀分叉点截断机制，但该信号尚未完整穿过 `MooncakeStoreConnector`。两条链都能复用一个已经存在且完整的 `C(P_t)`；但在本文固定版本中，当远端只有 MLA 命中而缺少 KDA checkpoint 时，系统仍不会自动补算该状态。

优化目标不是机械地每隔 1k 切一次 forward，而是在出现可复用分叉时仅补算一次，并把该边界持续传递到本地 radix/scheduler、Host staging、Mooncake key/value、lookup 与 retention policy 各层。
